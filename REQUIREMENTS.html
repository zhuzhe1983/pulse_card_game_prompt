00 · 产品目标、冻结决策与范围

版本：1.0.0；状态：可实施基线，尚未完成真实硬件认证与充分平衡测试。中文产品名「脉冲对决」，英文显示名 PULSE，技术 slug pulse-card。角色视觉和卡片印刷稿可以更换；更换显示名不能隐式改协议 ID。族群扩展是未启用草案。本章的冻结决策仍然只覆盖现有基础牌。

1. 要做成什么

一个以 M5 设备为角色灵感、用 NFC 实体卡建立收藏与身份、在不同屏幕和通信硬件上共享同一种策略对战的游戏。玩家拿起玩家卡登录，刷英雄卡认识新角色，使用收藏或公共借用模板组出 10 张牌，与 AI 或另一设备对战；离开前再刷玩家卡，带走已确认保存的进度。

核心体验是“我愿意为这一小局多花哪张牌”。首局落后不等于整场失败；保留资源、诱导投入、入场顺序与 PASS 决策形成复盘。NFC 提供仪式感、角色归属与实体交换，不负责制造卡牌本身缺乏的策略深度。

本规格借鉴经典昆特的多小局、保留手牌和 PASS 思路；具体牌数、投入上限、整数局积分和角色效果均为本项目原创首测设计，不是任何官方昆特规则的复刻声明。外部事实依据见第 10 章，产品设计无需假装存在外部背书。

4. 两条完整玩家旅程

4.1 新玩家

首次开机 → 选择试玩或扫描/创建玩家卡 → 识别玩家与本地/卡存档 → 查看借用牌组 → 刷英雄卡 → 预览卡模式并确认领取 → 本地原子提交 → 开盒展示个人收藏 → 与教学 AI 完成一场 → 看到“本机已保存，玩家卡未更新” → 点击保存或进入明确保存扫描上下文 → 再刷同一玩家卡 → 完整写入并回读验证 → 显示“玩家卡已更新，可在其他设备继续”。

创建玩家卡只能在用户明确选择“初始化玩家卡”后对已验证可写介质执行；不能把英雄卡或未识别卡自动格式化。新玩家 ID 和快照 ID 用真实随机 UUIDv4，不取 UID 作玩家 ID。

4.2 跨设备与离线朋友局

A 设备读到卡 S0 → 本地玩到 S3 → 不导出时，B 仍只能读 S0 → A 明确保存后卡变成 S3 → B 导入 S3 后产生 S4 → 写回成功后 A 再登录可比较已知历史并导入 S4。任何一步只进行了线上对战，都不自动把本机收藏转移到 B。

若 A 与 B 在同一个旧卡 S0 上分别发展，形成 A3 和 B2：它们是两个分支。不能按时间戳大的一边偷偷覆盖另一边，不能把两边碎片相加。备份两份，显示冲突原因；由用户选择保留哪一支，若要写回卡仍须显式保存。该冲突边界保护用户数据；它不改变普通同机“本机较新就用本机”的要求。

5. 玩法与收藏的关系

标准对局借用范围为 content/core_pack.json.standard_loan_template_ids，v1 覆盖全部 14 模板。收藏决定“这是我的哪位角色”、名字、外观和来源；同一模板的公用版与收藏版进入 reducer 后完全相同。对手只收到出场单位模板与可选展示，不收到玩家卡 UID、完整收藏、获取日期或私有存档。

可以制作固定角色的赠礼卡、活动卡和每日随机卡。卡片标签必须明确其模式、游戏日边界以及是否属于收藏稀有类别。重复奖励的抽取概率公开显示；v1 不加入付费抽取、现金交易或暗中改变概率。若未来改变商业模式，单独评审，不能让代理自行加入商店。

6. MVP、扩展与明确边界

MUST： 规则/收藏/每日领取/显式迁移、标准教学 AI、目标平台可用 UI、至少一种可互通网络路径、持久化与恢复、版本协商、能力检测与测试输出。

MAY： 同屏轮流对战、局域网发现、ESP-NOW、其他 RF、异步长期对局、服务器签发领取回执、观战 UI、纸卡打印器、手机作为 Grove/USB 桥。协议已预留观战投影，但客户端不必首版实现完整观战产品。

不在 v1： 真正全球限次、强防克隆玩家卡、自动房主迁移、P2P 公平密码学裁判、服务器跨设备同步收藏、自动强制胜负计时、新成长战力、多于 2 名玩家、交易市场、复杂连锁牌效。

7. 成功与失败的判定

首版成功：两个独立客户端可以完整打完同一局，得到相同公开结果；实体卡进度迁移没有含糊成功提示；新玩家 5 分钟内理解“抢分”和“留牌”的取舍。后者是待测目标。

试玩重点记录：玩家是否为了下一局主动放弃一局、是否能复述输在哪里、是否连续再来一局、战术牌是否成为必弃选项。不能用抽卡次数或页面停留替代玩法验证。每一项数值改动都发布新内容 hash，已经开始的对局继续锁定原包。

  • 上表名称是以 M5 设备为灵感的游戏角色名，不表示某款真实设备在游戏中提供算力加成，也不要求购买对应硬件。

1.4 免费教学牌组：8 个角色 + 2 张战术

默认 10 张依次为：core2_guard、atom_scout、stickc_operator、dial_router、paper_archive、echo_booster、cardputer_hacker、stamp_sentry、signal_boost、signal_jam。它们全是公共借用卡（loan），未登录试玩与没有收藏的新玩家都能使用这套牌组完整对战。

“公共借用卡”只表示系统持续提供的可用模板，不自动给玩家生成 10 个永久个人收藏条目。玩家通过英雄卡得到同模板的个人收藏后，可以用自己的名字、外观或收藏编号替换借用展示；基础分、合法排位、效果、投入次数完全一致。

standard14 标准模式中，全部 14 个模板均可免费借用；“教学 10 张”只是推荐预设，并不是其余 4 张的付费门槛。玩家可从同一公共 14 模板池合法组成 10 张牌，至少包含 6 个单位。借用不得到期、因每日次数耗尽而消失，或在完成教程后被回收。英雄卡奖励带来个人收藏／命名／外观归属，不解锁独占的标准对战选项。未来若做收藏限制房间，必须另行协商模式与规则，不属于 v1。初次核心玩法验证统一使用默认 10 张。

2. 一句话玩法与产品边界

每人带 10 张牌参加一场最多 3 小局的较量。双方轮流打出 1 张牌，或选择 PASS 停止本小局投入。每小局最多打 5 张；场上分数高者得 2 局积分，平局各得 1 分。已经打出的牌本场不再回来，未打出的牌留到下一小局。玩家需要决定：现在多花一张赢下这一局，还是保留更好的组合去争后两局。

本版本的趣味来源是跨小局分配手牌、控制投入、选择入场顺序、安排前后排、判断对手是否愿意继续跟牌。收藏提供人物归属和可选外观，不承担把一场不好玩的对局“养成后变好玩”的职责。

2.1 必须实现

  • 10 张数字手牌、两排部署、每小局 5 次投入上限、PASS、至多 3 小局及确定性结算。
  • 12 种角色模板、2 张通用战术与默认 10 张免费借用阵容。
  • MVP 必需：本地单人 AI 与双设备同步在线对局。
  • 可选扩展：同设备双人轮流操作，以及建立在协议持久恢复之上的异步对局 profile；不要求每个 ESP32 客户端一次实现全部模式。
  • 玩家卡登录／保存入口；英雄卡抽卡／收藏入口；对战可完全使用数字手牌。
  • 同一规则引擎与同一卡包内容，供浏览器、手机、桌面、PaperMono、Dial 及其他设备适配器调用。

2.2 明确不属于 v1

角色 HP、共享电量、攻击速度、硬件算力优势、回合外抢操作、即时施法、抽牌、洗牌、复活、回手、重新触发入场、排位搬移、天气、长链触发、每回合持续伤害、卡片上记等级后直接增加 PvP 数值、地理定位争夺、付费随机数值强化。

“DAMAGE”是引擎中的减分效果名称，不代表攻击生命值。界面统一写“使一个单位战力 -2”，避免沿用旧 RPG 的血条、死亡或伤害动画。

2.3 时间和节奏默认目标

实时对局的体验目标约为 5–10 分钟，属于待实测目标。每场最多投入 20 张牌，加上 PASS、交接与结算；不能在未经测试时承诺每场固定 3 分钟。异步对局可以跨小时或跨天，规则不因等待时间改变。

连接检测、失联宽限与恢复采用冻结契约中的统一配置。v1 不提供 resign 或自动超时判负：失联只进入连接／房间暂停状态；明确关闭房间记录为 aborted，不产生竞技胜负。客户端不根据本机时钟自行补 PASS、替玩家出牌或修改比分。

3. 术语、数量与合法性

3.1 牌组校验

  1. 开场时每方恰好 10 张。
  2. 每张都来自本场锁定的同一卡包内容版本，且玩家具有使用资格：个人收藏条目对应的模板或系统借用资格；standard14 标准模式的全部 14 个模板均可免费借用。
  3. 同模板最多 1 张。每个模板至多存在一条个人收藏记录。重复获取增加该记录的 draw_count 并按奖励规则增加碎片，不制造额外可出战副本。
  4. 牌组在开场后不可编辑；跨小局也不能换卡。
  5. 每副牌至少 6 张为单位。v1 开局时 10 张全部可用；没有牌库、抽取顺序、起手重抽或小局补牌。
  6. 如果两端内容版本不一致，不得“各按自己的卡面计算”。进入匹配前修复版本，或拒绝开场并显示可理解的更新说明。
  7. 默认教学牌组不需要访问玩家付费记录、真实硬件清单或实体英雄卡库存。

3.2 场地限制

每方各有 front、rear 两排。每小局最多成功投入 5 张卡，单位与战术合计计算；不是每排 5 张，也不是最多 5 个仍有分数的单位。v1 没有额外的每排容量限制。合法的极端布局可以是前排 5 张、后排 0 张。

若一张单位被减到 0 分，它仍留在原排，仍占本小局一次已投入名额，仍可作为允许的目标，也仍算“另一排已有单位”。没有死亡、退场或空位回收。

4. 对局状态机

4.1 逻辑状态

下面是实现所需的逻辑阶段，而不是新定义的线协议字段：

逻辑阶段 可发生的玩家行为 进入下一阶段的条件
DECK_READY 选择并确认合法牌组；退出准备 两方准备完成，规则与内容版本一致
MATCH_START 只读开场信息 权威裁判确定首局先手并建立初始状态
ROUND_ACTIVE 只有当前行动方可以打牌或 PASS；其他方查看公开信息 一次有效行动被原子接受；或双方均已 PASS
ACTION_PENDING 本地等待已提交行动的结果；可以查看但不能再次提交其他行动 收到接受、拒绝，或恢复到权威状态
ROUND_RESULT 查看已记录比分、局积分与最新手牌数量；仅在记录充分时显示本局投入明细，不能修改本小局 按规则立即确定整场结束或建立下一小局
MATCH_COMPLETE 查看比分结果；有裁判本地日志时可选复盘；申请新的一场 新建另一场对局，不复用旧场的手牌状态

网络上的 RECONNECTING、WAITING_FOR_PEER 是交互状态，不是可以改变战力的新玩法阶段。断线不能导致重新入场、返还卡牌或撤回已经接受的 PASS。

4.2 初始化

  • 双方局积分均为 0。
  • 双方手牌为锁定牌组中的全部 10 张。
  • 双方场地、弃牌区、已投入数和 PASS 标记为空／0／false。
  • 第一小局先手由会话统一 seed 确定；参考裁判用 seed_uint32 & 1 选择 0／1 座位，不允许每端各自取随机数或按设备速度抢先。
  • 唯一当前行动者为本小局先手。另一方不可以提前将本地选择广播成行动。
  • 开场时战斗不需要实体英雄卡在线；曾用于获得收藏的卡不需要放在读卡器上。

4.3 每次行动后的推进

  1. 原子应用本次有效行动。
  2. 若行动方手牌已经为 0，自动标记其 PASS。
  3. 若行动方本小局已投入数达到 5，自动标记其 PASS。
  4. 若双方均 PASS，立即结算本小局。
  5. 否则若另一方尚未 PASS，将当前行动者交给另一方。
  6. 若另一方已 PASS，而本方仍可行动，则当前行动者仍为本方；它可以继续出牌或主动 PASS。

PASS 不消耗一张卡，不增加已投入数，但结束该方本小局的所有后续操作。先 PASS 的一方可以继续查看详情、已收到的公开信息和已记录比分，不能用 NFC 刷卡解除 PASS。

4.4 小局转换

结算必须幂等，不能因为双方同时点“继续”、重连重放消息或渲染页面两次而重复加分。

  1. 读取两方最终场上总战力，确定胜者；高者获得 2 局积分，平局双方各获得 1 局积分。
  2. 将局数、最终战力、胜者与积分变化记录到 round_results。裁判生成的 round_ended 事件含最终场地、投入数与 PASS 状态，可供裁判端本地日志复盘；这些明细不进入状态的 round_results，v1 不保证向双方客户端交付或在重连时恢复完整事件。
  3. 给双方累加局积分，并把所有在场单位转入本场弃牌区、清空两排；战术此前已在弃牌区，不能重复加入。末局也执行清场。
  4. 若任一方局积分 ≥4，或当前已为第三小局，整场结束；比较局积分，高者胜，相同则平。结果 UI 读取已记录的结算分数，不能把清场后的 0:0 当成最终结果。
  5. 尚未完场时，局数 +1；本小局胜者成为下一小局先手，平局则交换本小局的原先手。已投入数归零、PASS 标记重置，场上临时增减分和防护状态随清场结束。
  6. 未打出的手牌保持原样。不抽牌、不把弃牌移回手牌、不改变收藏拥有状态。
  7. 进入下一小局之前处理没有手牌的玩家自动 PASS；必要时自动结算空小局。逻辑可以一次推进到下一个可行动状态；“本局结算”只是 UI 展示阶段，不要求双方点击继续才允许规则推进。

谁最后点“继续”、谁最后出牌、谁先 PASS、谁先收到网络消息，都不能决定下一小局先手。

v1 客户端必需恢复的是 round_results 中的可信比分／积分，以及该玩家自己的最新过滤视图。完整回放只作为裁判端本地日志的可选能力，不扩展 SNAPSHOT 承载完整历史。若没有收到某小局的终盘场地，结果页只展示已有比分、局积分和最新手牌数量；手牌变化或投入明细仅在前后记录充分时展示，不猜测或补画完整布局。

4.5 无牌边界

  • 新小局开始时一方无牌、另一方有牌：无牌一方自动 PASS，以 0 场上战力等待。另一方可出牌争胜，也可 PASS 接受 0:0 平局。
  • 在小局进行中打完最后一张牌：自动 PASS，但已在场单位和战力保留至本小局结算；不能因为手牌为空立即清掉场地或把战力归零。
  • 双方无牌、整场尚未结束：新小局立即按 0:0 平局结算，双方各 +1 局积分。若仍需第三小局，再按相同规则结算，直到达到完场条件。
  • 手牌中只剩无目标的战术不等于手牌为空；规则不自动把它们丢弃。玩家仍可以主动 PASS，AI 必须把 PASS 当成合法行动，界面不得卡死在无法出牌的手牌页。
  • 自动空局仍是正式小局；应出现在结果记录中，不应卡在“等待没有牌的玩家操作”。
  • 例：第一局 A 胜后为 2:0，第二局双方耗尽且 B 胜后为 2:2；第三局自动 0:0，整场局积分 3:3，判平局。
  • 例：前两局局积分为 3:1，双方随后无牌；第三局自动平局，最终 4:2，A 获胜。

5. 打出一张牌：选择、取消、提交和应用

5.1 本地预览不是已出牌

玩家依次选择手牌、单位的合法排位、需要的目标，然后确认。战术跳过排位选择，使用 null 排位。任一确认前步骤都可以取消，回到原手牌状态，且不消耗卡、不占投入数、不触发任何效果。

对手看不到本地正在选哪一张、旋钮停在哪个目标、是否刷过候选英雄卡，或取消过多少次。只有权威裁判接受后的行动才对对手公开。

5.2 合法性清单

裁判在同一次原子应用前验证：

  • 对局和小局仍处于允许行动的状态。
  • 提交者是当前行动者，并且本方尚未 PASS。
  • 本小局已投入数小于 5。
  • 卡仍在本方本场手牌中，模板与锁定卡包一致。
  • 单位排位属于该模板允许的集合；战术排位必须为 null。
  • 目标符合效果允许的阵营、排位和“其他单位”约束。
  • 提交对应的状态版本和防重复条件满足冻结契约。

任何一项失败，整次操作均不应用；不得先从手牌移除再发现目标非法，也不得只扣名额而保留卡牌。客户端恢复最新权威状态后，要求玩家重新选择受影响的目标。

5.3 目标选择与“空放”

BOOST 与 DAMAGE 在已有合格目标时必须选择一个目标，不能故意提交空目标跳过效果。没有合格目标时，单位可以作为基础分单位部署、入场效果略过；预览写明“当前没有可选目标，本次只获得基础分”。战术没有合格目标时不可打出，必须保留在手牌中。

这里的“合格目标”按阵营和是否为已经在场的其他单位判定。BOOST 可以选择任意排的己方已在场单位，DAMAGE 可以选择任意排的敌方已在场单位；v1 不设额外目标排位限制。stable 单位和带防护的单位仍可以成为规则上合格的目标；它们可能抵消效果。玩家可以选择它们，但预览必须说明实际变化为 0，不能让对手从无效选择中获得隐藏信息。

自己刚打出的单位不是 BOOST 的“其他己方单位”，因为目标候选在它入场之前确定。禁止让帮腔给自己 +2，也禁止把尚未提交的另一张手牌当成目标。

5.4 唯一结算顺序

  1. 从本方手牌移除所选卡。
  2. 本方本小局已投入数 +1。
  3. 单位以基础分部署到选定排，初始化其 stable 或 shield_once 特性；战术不进入场地，直接进入本场弃牌区。
  4. 解析本次出牌的一次效果。SELF_BOOST_OTHER_ROW 在此时检查己方另一排是否已有至少 1 个单位；BOOST 和 DAMAGE 使用提交时选定且已验证的场上目标。
  5. 根据下节增减分规则，应用实际效果。
  6. 重新计算两方前排、后排和场上总战力。
  7. 记录公开规则事件；客户端只根据实际收到的事件和最新过滤视图更新显示，不假定持有完整历史。
  8. 执行自动 PASS、行动权转移或小局结算。

整段应由同一个纯逻辑应用入口完成。动画、音效、震动、网络重试都不能再次调用入场效果。

6. 五类效果的完整语义

NONE 是没有操作的内容标记。规则包含三个有操作的效果和两种单位特性，共五类行为；正式 op 枚举为 NONE／BOOST／DAMAGE／SELF_BOOST_OTHER_ROW，traits 为 shield_once／stable。禁止开发者用角色名字暗示未定义的被动。

6.1 BOOST（+2）

  • 对一个符合条件的已在场己方其他单位尝试增加 2 分。
  • 若目标 stable，实际增加 0。
  • shield_once 不阻挡友方增分，也不会因此消耗。
  • 两张不同卡可以分别给同一个普通单位 +2，增益线性叠加。没有倍增、二次触发或“收到增益时再增益”。
  • 默认免费 10 张有 Echo 与加一把两个定向增分来源；完整内容池还包括 ATOM Matrix。不要新增未写入数据卡包的隐性增益。
  • 增加的是当前战力，不改变卡包基础分，也不写回个人收藏条目。

6.2 DAMAGE（-2）

  • 对一个符合条件的敌方在场单位尝试减少 2 分。
  • 判定顺序：stable → shield_once → 按最低 0 计算实际减分。
  • stable：实际变化 0，保持原值。
  • 防护尚可用：整个本次 DAMAGE 被抵消，实际变化 0，防护消耗；包括目标当前已经为 0 的边界情形。这一“阻挡减分操作”的语义与参考裁判保持一致。
  • 否则：新当前战力为 max(0, 原当前战力 - 2)。
  • 目标不退场、效果不失去、投入名额不返还。把无防护的 1 分单位减 2 的实际变化为 -1。

6.3 SELF_BOOST_OTHER_ROW（满足另一排条件时自身 +2）

  • 只在该单位成功部署的这一次检查。
  • 如果己方另一排至少存在 1 个在场单位，自己 +2；0 分单位也满足“存在”。
  • 如果另一排为空，不增加；以后另一排再来牌也不会补发。
  • 该单位可以先被增到 5，再被对方减到 3；它不会自动回到 5。
  • 对可放双排的 Dial，判断基于玩家这次实际选择的排。例如己方只有前排单位时，Dial 放后排获得 +2，放前排不获得。

6.4 shield_once

  • 是单位自带的、仅作用于自己的 1 次防减分特性。
  • 第一次针对该单位的 DAMAGE 被完整抵消，随后防护失去；即使当前为 0，也消耗这次防护。若同时具有 stable，则优先由 stable 抵消，防护不消耗。
  • 不抵消其他单位的减分，不保护整排，不在每回合或每次查看时刷新。
  • 增分、查看、换到下一位玩家的操作、网络恢复都不恢复防护。
  • 清场时单位离开本小局，防护状态随该场上实例一起结束。v1 不存在使该单位再次入场的机制。

6.5 stable

  • 该单位的当前战力不受任何增分或减分效果改变，包括己方增分和敌方减分。
  • 可以合法部署、计分、占投入名额，并参与“另一排有单位”的存在性判断。
  • 并非“只能免疫敌方效果”，不得给它加 +2 后再保留免疫。
  • 首发卡包只把这一特性赋予 存页，基础分 5。

6.6 一张卡只有一条基础效果

v1 表中的每张卡最多有一个 effect.op，单位可具有规定的 traits；首发卡表不叠加复杂组合。不要悄悄把“防护 + 入场增分”“stable + 全排光环”合并进一个模板。没有 on-damage、on-boost、on-pass、on-round-end 等事件级联；只在部署时触发一次入场逻辑，减分时检查目标的静态特性。

7. PASS、分数和整场胜负

7.1 PASS 的确认

PASS 是本小局不可撤销的投入结束。按钮文案为“停止本局出牌”，确认页至少显示：当前总战力、对手总战力、双方剩余手牌数、本局已投入数，以及“对手仍可继续出牌”。用户确认后才提交。

已收到裁判接受后，不能撤回；网络确认未知时，不能通过重新扫描玩家卡或返回主菜单回滚。v1 不提供整场投降入口。会话菜单可明确关闭房间并记录 aborted，但这不判定任何一方输赢，也不能与 PASS 共用同一按钮动作。

7.2 小局积分

小局场上战力 小局结论 局积分变化
A > B A 胜 A +2，B +0
A < B B 胜 A +0，B +2
A = B，包括 0:0 平局 A +1，B +1

7.3 整场结论

  • 任一方局积分 ≥4，立即完场。
  • 没有提前完场时，第三小局结束后比较局积分。
  • 相同则整场平局；不另开突然死亡局，不比较累计战力，不比较剩余手牌，不按先后手破平。
  • 4:0 可以在两小局后结束；3:1 必须继续，因为下一局可能变为 3:3。
  • 一胜两平可得到 4 局积分并获胜，所以规则页应写“最多三局、累计局积分决定胜负”，不能只写“三局两胜”让开发者误用胜场数。

所有场上战力都以整数计算；所有局积分也以整数计算。不得在某一客户端使用 0.5 分而在另一客户端使用 1 分。

8. 基础卡包下的可复算策略实例

8.1 赢了小局，却多花了两张牌

双方使用默认教学牌组，开场各 10 张。B 是本小局先手。以下历史在本规则下完全合法：

行动顺序 行动 A 总战力 B 总战力 说明
1 B 打探子 到前排 0 4 B 先低投入。
2 A 打厚壳 到前排 6 4 A 保持领先。
3 B 打细条 到后排 6 8 B 使用第二张。
4 A 打存页 到后排 11 8 PaperMono 5 分。
5 B 打加一把，给探子 +2 11 10 B 第三次投入；战术立即弃置。
6 A 打旋钮 到后排 16 10 己方前排已有厚壳，旋钮 3+2=5。
7 B 打 Stamp 到前排 16 14 B 已投入 4 张，但场上只有 3 个单位。
8 A PASS 16 14 A 保留 7 张，接受可能输这一局。
9 B 打帮腔 到后排，给探子 +2 16 19 帮腔身体 3 分、增益 2 分；B 第 5 次投入，自动 PASS。

本小局 B 胜，局积分 A 0、B 2；A 剩 7 张，B 剩 5 张。下一小局 B 先手。A 得到了更多后续选择，但 A 必须赢下后两小局才能赢整场；不能把这个示例解释成 A 已经必胜。

这是一段用于演示资源代价的可重放历史，不宣称 B 的全部早期投入都最优。核心教学问题是“B 愿不愿意多付一张拿到本局”，以及“A 愿不愿意承担后两局都要争胜的风险”。

8.2 同两张牌，顺序不同

己方场地为空，只比较细条与远呼：

  • 细条先到后排：4 分；远呼后到前排，另一排有单位，自身 3+2=5；总战力 9。
  • 远呼先到前排：3 分；细条后到后排：4 分；LoRa 不补发入场增分；总战力 7。

这不是屏幕刷新造成的先后差异，而是所有客户端共享的入场时机规则。

8.3 最后一局也需要选牌

假设最后一局自己还剩 7 张。由于本小局最多投入 5 张，不能简单全部倒空；需要选出本局的 5 张、决定排位、考虑 +2 的目标和对手的减分。

若双方进入第三小局时都只剩 3 张普通无效果牌，则该小局的战术空间确实会很小，可能主要由前两小局的资源分配决定。不要用无意义的反复刷卡、额外动画或隐藏按钮掩盖这一点。试玩时应记录这种“第三局只做算术”的发生率，再决定是否调整卡包，而不是直接叠加另一套 HP 系统。

9. 双 NFC 卡与玩法场景

9.1 两种卡各自做什么

卡类别 主用途 必须出现的明确场景 对战中的默认行为
玩家卡 识别当前玩家、进入其资料；在用户执行保存流程时写入允许保存的内容 登录／玩家资料／保存进度 不用于出牌；刷入另一个玩家时要求先结束或退出当前身份会话
英雄卡 固定角色兑换或盲盒领取，得到收藏；每玩家每物理英雄卡每天最多 1 次 抽卡大厅 默认仅尝试定位数字手牌或查看角色，绝不触发抽奖／发奖

9.2 英雄卡领取规则在玩法层的要求

  • 必须先进入已登录状态，再进入明确的“抽卡大厅”。未登录时显示登录入口，不进行奖励抽取。
  • 同一个玩家、同一张物理英雄卡、同一个 UTC+8 游戏日，最多成功领取一次。游戏日不是设备随意选择的本地时区，也不是“距上次刷卡 24 小时”。
  • 固定卡重复领取增加对应收藏条目的 draw_count 并按奖励规则给碎片；每模板只有一条个人收藏记录。盲盒的奖池、概率、保底、碎片数量与安全校验由奖励契约定义。本文不编造概率。
  • 读卡成功不等于领取成功。只有奖励服务或被批准的离线奖励机制确认后，才展示“已获得”；断网、重复刷、超时重试不得导致多次发奖。
  • 抽到的收藏不要求玩家继续持有实体卡才能使用。玩家登录后可以跨设备使用其合法收藏；写卡、同步与冲突处理由存档契约规定。
  • 抽卡次数用尽，不影响免费借用牌组、已有收藏、单人对战或好友对战。

9.3 对战不强制 NFC

默认战斗入口是屏幕中的数字手牌。用户点击／旋转选择一张牌，选择排位和目标，再确认，完整流程不需要实体英雄卡。

对战中的 NFC 英雄卡选择是可选快捷方式：如果对应模板确实在本场剩余手牌中，则聚焦这张数字牌并打开预览；如果已经打过，显示“本场已使用”；如果不在本场牌组中，显示“未加入本场牌组”。三个分支均不能调用抽卡接口，不能从收藏向进行中的手牌补卡。

单个 NFC 读卡器只提供卡片识别输入，不能假设它知道卡在桌上的哪一排、朝向或相邻关系。前后排与目标由界面明确选择，并随最终行动提交。

9.4 玩家卡写保存的交互边界

提供清晰的“保存到玩家卡”操作和写入结果；不要求每次出牌都贴着玩家卡写入。不把“刷玩家卡登录”“战斗提交”“英雄卡领取”“写入保存”合并成一个隐式动作。

已有一场活跃对局时，扫描其他玩家卡不能把当前数字手牌转移给新玩家。需要让当前会话按协议保留、退出或完成后，再切换身份。具体存储的数据、写入事务、身份可信度和恢复方式见存档／安全契约。

10. 可见信息与公平性

10.1 对手可见

  • 双方在场单位、当前战力、排位、stable／防护是否可用。
  • 双方前后排和总战力、已投入数、剩余手牌数量、PASS 状态。
  • 已公开的弃牌区、历史行动、小局结果、局积分、当前行动方。
  • 对局约定公开的玩家展示名、外观、规则和内容版本。

10.2 对手不可见

  • 本方尚未公开的手牌具体内容和排列、本地预选牌与目标、取消过程。
  • 尚未公开的构筑选择、个人收藏条目清单、NFC 原始内容、玩家卡保存内容。
  • 随机奖励结果生成过程或与本场无关的领取记录。

默认教学双方用同一套已知 10 张，熟练玩家可以通过已出的牌推算剩余牌。这是合法的公开信息推理，不是可靠的隐藏随机性。应如实把该模式定位为“分配资源与顺序博弈”。进入 14 选 10 等自定义构筑时，是否公开完整牌组应统一按模式约定，不能两端不一致。

朋友局的 trusted_host 裁判在技术上能接触完整状态，不能宣称状态哈希已经防止恶意房主作弊；公开展示层仍必须过滤私有信息。需要更强竞技信任时使用协议定义的 dedicated_server 部署，不能只把客户端标签改成“安全”。

10.3 AI 不偷看

AI 的决策接口只接收自己的手牌、公开场地和历史、对方剩余手牌数、双方局积分、当前局数和投入数，以及模式约定公开的信息。它不能直接读取宿主内存中的对手真实手牌、未公开牌组、候选操作、预览目标或奖励收藏。

可用的首版 AI：枚举自己当前所有合法部署和目标；计算立即战力差、是否能以较少投入超过已 PASS 对手、保留强牌的价值及是否必须赢当前小局；在几个合理行动间按可复现的 AI seed 选择。AI seed 用于策略选择，不改变规则本身的结算。

禁止通过“困难模式偷偷 +1”“读取用户手牌后精准留解”“玩家点下出牌后再反向改 AI 行动”制造难度。教程脚本可以拥有预先指定的公开关卡历史，但必须标为教学关。

11. 各种对战模式共用同一规则

11.1 单人 AI

本地或服务端 AI 都使用完全相同的合法行动入口和结算函数。AI 不直接改战力，不绕过目标校验，不拥有第 6 次投入。AI 思考动画不决定行动生效时间。可以暂停，因为没有实时对手。

11.2 同设备本地双人（可选 profile）

两人轮流持有同一设备。结束本方行动后进入交接遮罩，隐藏任何数字手牌，提示“请交给另一位玩家”；接手者明确点“查看我的手牌”才展开。公开场地可以显示，上一位玩家的私有预览不能留在遮罩后。

若另一方已经 PASS，本方连续操作，不应反复要求无意义交接。局末可让双方共同查看公开结果，再由下一局先手接设备。

11.3 两台设备实时在线

轮到谁由权威状态决定，连接快慢、动画完成时间、NFC 感应速度不影响先手。非行动方可查看场地、已记录比分和本端实际收到的公开信息，但提交按钮不可用。客户端恢复后以权威快照和已确认行动为准，不从屏幕元素重建真实游戏状态。

11.4 远程异步（可选 profile）

与实时模式保持完全相同的轮流出牌、PASS、目标和积分规则，只延长允许等待的会话时间。玩家退出再回来时先同步最新状态，再编辑本地选择。不能在等待对手时预提交会自动适配未来目标的条件脚本。

异步通知只需说“轮到你了”或“本局结束”，不能把未公开手牌写进公开通知。低功耗设备可以睡眠，唤醒后继续同一场，而不是重新开始小局。

11.5 暂停、恢复与关闭房间

v1 的规则终局只由正常小局计分产生，不含 resign 或自动超时判负。失联按会话协议进入恢复／暂停状态，不代替玩家 PASS，不改变战斗 revision 或比分。明确关闭或放弃房间只把房间元数据标为 aborted，表示这场没有正常完成，不为任何一方生成竞技胜负，也不把未结束的规则状态伪造成 points 终局。

界面区分“本场按积分结束”和“房间已关闭，未产生胜负”。未来若实现投降、定时判负或异步长回合裁决，需另行协商 profile 和完整状态契约；当前客户端不得自行添加相应命令、结果原因或胜场奖励。

12. 实现验收的不变量

开发者应把以下条件放入引擎测试或运行期断言；界面截图正常不代表规则正确。

  1. 任意时刻，每张本场卡只属于手牌、场上或弃牌区中的一个位置。
  2. 对同一方，本场手牌数 + 本场已打牌总数始终为 10。
  3. 本小局成功投入数不超过 5；取消、拒绝与重复消息不消耗次数。
  4. 任何在场单位当前战力都不小于 0。
  5. 场上总战力等于两排单位当前战力之和。
  6. 每次正常小局结算新增的双方局积分之和恰好为 2。
  7. 小局数量不超过 3；正常完成后局积分高者胜，相同则平。
  8. 对局结束后不能再接受正常出牌或 PASS。
  9. 同一有效行动应用一次和网络重复送达后只应用一次，结果一致。
  10. 同一初始状态、同一内容包、同一有序有效行动序列，在任意设备得到同样的结果。
  11. 把任何客户端的渲染器换成无界面测试程序，不影响结算。
  12. 开局后完全移走所有 NFC 英雄卡，仍能通过数字手牌完成整场。
  13. 接口传给 AI 或对手的观察数据中，不含未授权的真实手牌。
  14. 英雄卡抽卡大厅与战斗选牌的路由不能互相调用奖励或补牌动作。

13. 需要实测而不是先拍板扩展的地方

  • 先手是否明显更吃亏；胜者下局先手能否形成合理的投资压力。
  • 5 张小局上限是否保留第三局选择，同时过早限制了追分。
  • 有多少局由 PASS 产生明确的省牌／逼牌决策，而不是双方机械打满 5 张。
  • 固定 10 张教学阵容是否已经能让玩家想再打一场；如果不行，先调整卡包和小局决策，不增加地图或养成规模。
  • 单人 AI 是否能够主动保牌、在对手 PASS 后只付出足够赢的一张，而不是总打空。
  • 开放 14 选 10 时是否出现始终不被选择的模板，尤其两张零身体战术；低分牌可以是廉价试探，但不能把所有低分牌都解释为“战术牌”来回避实际无用。
  • 同样状态下，在 PaperMono 与手机上做出同一选择是否都清楚、可靠；测试不得以某台设备更快扫卡作为赢法。

14. 来源与假设标注

本章的数值、卡名、比赛制和交互规则是本项目的原创设计建议；它们不是 M5Stack 官方游戏规则，也不宣称与任何商业卡牌游戏完全一致。M5 产品名称仅用于角色原型识别。硬件型号、NFC 兼容性、显示能力与 Grove 接口约束，以项目硬件适配文档中的已验证官方资料为准。

若正式冻结契约决定改名或微调卡片，请同时更新本文、卡包文件、教学历史、回放 fixtures 和各端资源，不得只改某一端的显示文字。

02 · 视觉风格、交互与跨端体验规格

产品名：脉冲对决。英文显示名：PULSE。本文规定信息结构和交互语义，允许不同开发平台使用原生控件。所有页面消费同一份权威对局状态与卡包，不得在界面中重算出另一套规则。正式字段以 CONTRACT.json、协议规范及卡包为准。

视觉方向为“黑白电子漫画卡册”：清楚的硬件角色轮廓、漫画分格、短句效果、醒目的整数战力。彩色设备可以使用彩色主题，但不能增加黑白端看不到的战斗信息。界面战力来自规则，不从概念卡面读取。固定模板重制尚未进入仓库，第一轮生成稿不推荐。

1. 体验目标

用户应在任何设备上回答以下五个问题，而不需要打开说明书：

  1. 现在轮到谁？
  2. 我与对手各有多少场上战力？
  3. 本小局我已经投入几张，还能投入几张？
  4. 我还有多少未用手牌，它们会留到下一小局吗？
  5. 现在停止出牌会发生什么？

NFC 的角色分两层：玩家卡负责身份与可携带保存，英雄卡负责领取收藏和可选的卡片定位。完整战斗必须能只用屏幕上的数字手牌完成。不要把“手里找不到一张实体卡”变成“本来合法的回合无法行动”。

  • 战力是页面最强的数字层级；局积分次之；剩余手牌和已投入数必须能同时找到。
  • 不在小屏上以英文完整效果名代替中文短句。
  • 字号缩小到无法读清前，应切换为分步页面；不要把完整电脑界面硬缩到旋钮屏。

6. 战斗界面的共同结构

6.1 常驻状态

至少展示：第几小局、双方局积分、双方战力、双方剩余手牌数量、双方投入数、当前行动方、对方是否 PASS。窄屏可把局积分与手牌作为固定短行，详细单位放在二级页面。

双方排位是规则属性，不由屏幕上下决定。通常将对手后排放最上方、对手前排靠中线；自己前排靠中线、自己后排靠近下方。交换视角时，front／rear 值不能被交换。

6.2 单位最小显示

  • 角色缩写或短名。
  • 当前战力；详情中可看基础分与本局修正。
  • 前排／后排位置。
  • stable／防护状态。
  • 是否为当前目标或待部署预览。

被减到 0 的单位仍须清楚留在场上，显示“0”，不能消失或绘成已经死亡。防护被消耗时显示一次简短事件，并改成失效状态。

6.3 数字手牌

全场开局 10 张都可选择，但不要求同一屏同时显示 10 张完整卡面。列表、分页、卡册条带、旋钮逐张翻阅均可。

每张手牌展示当前是否可出、基础分、可放排位和短效果。不可出的牌保留可查看状态，并给出准确原因：不是你的回合、本局已 PASS、本局投入已满、战术暂无目标。不要统一显示“能量不足”。

对手只看到手牌数；自己的手牌排序由本地偏好决定，不改变服务器上的卡片身份。

6.4 一次出牌流程

  1. 选择一张本方手牌。可通过数字列表或可选 NFC 定位。
  2. 显示卡片详情。若单位只有一条合法排位，自动填入并清楚显示；若两排均可，要求选择。
  3. 若效果需要目标，聚焦合法目标；目标仍可选 stable／防护单位，但展示实际变化。
  4. 显示确认摘要：将打出的牌、排位／战术、目标、己方战力变化、敌方战力变化、剩余手牌数、投入数。
  5. 确认后进入提交等待；按钮禁用，原确认操作不可重复发送为另一个新行动。
  6. 收到权威接受后统一更新卡、战力、名额与行动方；收到拒绝后恢复最新状态并解释原因。

实际变化预览必须基于同一规则引擎的试算或相同的只读计算，不在 UI 单独维护另一张“各角色大概效果”表。

6.5 确认摘要示例

  • “Dial → 后排；另一排已有单位，获得 +2。我的战力 11 → 16；手牌 8 → 7；投入 2/5 → 3/5。”
  • “加一把 → ATOM；目标战力 4 → 6。战术不留场；投入 2/5 → 3/5。”
  • “Cardputer → 后排，干扰 PaperMono。目标具有稳定，减分不会生效；仍消耗这张牌，Cardputer 提供 3 分。”
  • “压一下 → Stamp；消耗目标防护，本次战力不变。仍消耗这张战术牌。”
  • “这是本局第 5 次投入，成功出牌后将自动停止本局出牌。”

7. 大屏、手机与 PaperMono 类页面

7.1 宽屏默认布局

页面上方是局积分和当前行动，中间是四个排区，下方是本方数字手牌与行动按钮。侧边可以放本端已收到的公开记录与弃牌查看入口；没有侧边空间时折叠到详情。不把这份局部记录标为可恢复完整对局的回放。

手牌滚动不带动整个战场离开屏幕。查看详情时仍能看到当前总战力与投入上限。手机竖屏优先让四排变为紧凑条带，每排进入后查看单位；横屏不应成为必需条件。

7.2 电子墨水屏适配原则

  • 以“一个被接受的行动 → 一个可读稳定画面”为默认更新单位。
  • 适配器根据具体屏幕和驱动能力决定局刷、全刷、灰阶和清理周期；不要把某一型号的刷新模式写进玩法引擎。
  • 页面不会要求持续移动的角色才能判断目标；所有关键信息都有静态终态。
  • 有残影风险时，局末、切换主要页面或达到适配器阈值后做整屏清理。清理过程中可显示适当的硬件反馈；不会因此重复提交出牌。
  • 不为倒计时每秒全屏刷新。低频更新剩余时间，在有状态事件时更新；真实截止时间由会话裁判保持。
  • 避免黑白全屏闪烁作为每张卡的“攻击动画”。短事件条、数值前后对照和一次可选提示音即可。
  • 支持“立即清屏”设备操作，但它只重绘当前状态，不重开比赛。

性能目标是输入有反馈、确认有结果、稳定画面无歧义。具体毫秒数必须在真实硬件测量后确定；不能用桌面浏览器渲染时间当作墨水屏硬件验收。

7.3 PaperMono 页面最小版本

首版可采用三页结构：战场总览、我的手牌、当前卡／目标确认。返回战场时保留未提交选择，但只在状态版本仍有效时允许提交；若对局状态变化则清除失效选择并提示重新选。

触控、实体按键或外接输入是否存在，由设备能力配置决定。不要在通用 UI 代码假定所有 PaperMono 装置都有相同按钮或触控驱动。

8.3 防误触

  • 所有消耗卡片和 PASS 的行为都必须经过明确确认页。
  • 打开详情的同一次按钮抬起事件不能再次触发确认；输入适配器需要完成去抖和事件消费。
  • 高速旋转跨过多张牌只改变焦点，不能连续出牌。
  • NFC 识别多次只聚焦同一张牌，不叠加提交。
  • 提交待确认时旋钮可以查看信息，但不能把另一张牌替换进已经发出的操作。
  • 待提交操作的取消只是停止本地等待界面，不保证撤销已经抵达裁判的动作；默认不提供带误导的“撤销出牌”。

9.3 玩家卡保存流程

保存页先显示要保存到哪个玩家、可保存进度概要，以及目前是否还有未同步变动。然后提示把玩家卡靠近并保持。

写入期间不允许用另一张英雄卡中途替换用途。只有规定的写入、读回与验证完成后，显示“已保存到玩家卡”；若结果未知，显示“尚未确认写入完成，请保持卡片或重新检查”。不要一收到 NFC 写入函数返回就先播放成功动画，再异步发现校验失败。

写入失败不修改游戏规则，不额外扣奖励，不把对局判负。原存档是否仍可恢复、如何选择新旧记录，按玩家卡保存契约处理，界面只展示可验证的事实。

10.3 结果页来源

参考引擎在小局结算后会清场，末局也一样。客户端结果页必需读取 round_results 中已记录的小局比分／积分，并恢复自己的最新过滤视图；不能读取清场后的实时 board 然后把结算结果显示成“0 比 0”。

v1 不保证双方客户端收到或恢复完整 round_ended 事件。没有终盘场地记录时，只显示可信比分、局积分与最新手牌数量；手牌变化或本局投入明细仅在前后记录充分时显示。不得猜测最后一手的排位、目标或完整布局，也不因缺少回放而阻止继续对局。完整回放是裁判端本地日志的可选能力；不要求客户端提供该入口，不扩展 SNAPSHOT 保存完整历史。

小局结果页的“继续”只是关闭本地展示，不应额外发送一条推进玩法的行动。如果服务器已经进入下一小局，用户关闭结果页后直接显示新的行动方。

11. AI 模式的表现

  • 显示对手为“教学 AI”或“练习 AI”，不假装真人。
  • 可以在教学关展示脚本目标和提示；普通对战不显示 AI 私有手牌。
  • AI 行动可以延迟一个短、可配置的阅读间隔，但决策不能等待玩家之后的本地选择来反向修改。
  • AI 已经确定并提交的动作只渲染一次；跳过动画不会跳过规则。
  • 赛后点评使用本局公开事实，例如“你用 3 张牌保住 7 张手牌进入下一局”，不要从玩家从未提交的候选点击推断其策略。
  • AI 难度通过策略质量与搜索预算变化，不通过隐藏基础分、额外手牌或偷看对手状态变化。

03 · NFC、角色领取与玩家卡存档

本章是 pcg v1 的业务与存储协议。CONTRACT.json、本章、JSON Schema 与 fixtures/ 必须一致；编码和确定性抽取的可执行定义见 11_REFERENCE_AND_DATA_CONTRACT.md。文中的“必须”是实现要求，“推荐”是可替换的工程选择。实体卡兼容性须按 05_PLATFORM_ADAPTERS.md 验收，不能仅凭卡片商品名宣布通过。

1. 已冻结的产品行为

  1. 玩家先刷玩家卡登录。本机没有该玩家记录时，从卡内完整快照建立本机记录。
  2. 登录后刷英雄卡领取固定角色或盲盒结果。英雄卡不保存玩家进度，不写每日使用标记。
  3. 每日限制默认以 (player_id, hero_card_id, game_day) 为键。其他玩家可以在同一天刷同一张英雄卡；每个账户独立计算。
  4. 领取成功后，角色、重复奖励、钱包变化和当日已用卡号必须在本机一次性提交。未成功持久化，不算领取成功。
  5. 本机游戏进度随业务事务持久化，但只有玩家明确再次刷玩家卡保存，才会写入玩家卡。登录、抽卡、退出、联网、对战结束均不自动回写卡。
  6. 同一设备再次登录同一玩家时，比较本机与卡上的内容修改时间，并核对谱系。确认本机较新，就使用本机且保留“尚未写卡”状态；不得用旧卡覆盖本机。
  7. 只有完整写卡并读回验证成功，更新才具备离线迁移能力。另一台设备看到的是卡上最近一次成功保存的版本。
  8. 对战消息、房间重连、牌组校验和对局结果同步，不是收藏迁移通道；不得顺便向另一设备或云端替换完整玩家存档。

2. 卡片角色、标识与识别顺序

2.1 玩家卡

玩家卡存放本章定义的 PlayerSnapshot，包含收藏、牌组、钱包、当日领取记录和时间高水位。player_id 是应用生成的 UUID，不是物理 NFC UID。换一张容量更大的玩家卡，可以继续保存同一个 player_id。

卡片可读 UID、可读 NDEF、可写 NDEF、可写自定义应用文件，是不同能力。普通 UID 和文件哈希不是不可复制的所有权证明；v1 的登录语义是“读取持有的玩家档案”，不是金融级身份认证。N03

2.2 英雄卡

英雄卡只有以下两种领取行为，二者均消耗该玩家当日对这张卡的资格：

类型 识别后做什么 必须记录
固定卡 按已安装内容包发放指定 template_id 稳定卡号、最终模板、领取键、时间、内容池标识与哈希
盲盒卡 按冻结的池和确定性抽取算法产生一个模板 同上；随机算法直接复用参考实现

固定卡的重复角色如何转换、盲盒概率及保底规则，以内容和经济规则为准。本章不额外发奖励、不把固定卡解释为“每天重新创建一个新卡号”。池更新、换设备、换显示名称，都不改变同日资格的去重键。

识别顺序如下：

  1. 优先识别有效的游戏发行 payload，读取稳定 hero_card_id。发行命名空间为 issued: 加规范小写 UUIDv4。
  2. 没有发行 payload 时，可以通过本机已安装的 legacy 卡片映射，识别官方赠卡的固定角色／盲盒配置。
  3. 未知卡只显示识别结果和“未登记为游戏卡”，不自动转成随机新英雄，不自动格式化。
  4. 玩家卡和英雄卡在 v1 中是互斥角色。一个标签同时出现冲突的两种游戏角色记录时拒绝执行；不能因为登录状态不同就随意解释同一段数据。

issued: 只是稳定标识命名空间，不代表数据天然可信。发行签名只有在提供签名、公钥与验签规则并成功验签时才能显示为已认证；casual_local 不强制启用发行安全认证。

2.3 Legacy UID 规范化

技术名固定为小写 ASCII 枚举：nfc-a、nfc-b、nfc-f、nfc-v。v1 的默认 legacy 领取适配仅接收已经确认 UID 稳定的 NFC-A 卡。

uid_hex = UID 字节的连续大写十六进制；无 0x、冒号、空格
identity_material = UTF8("pcg.hero.uid.v1\n" + technology + "\n" + uid_hex)
hero_card_id = "uid:" + lowercase_hex(SHA256(identity_material))

NFC-A 使用防冲突流程得到的实际 UID，通常为 4、7 或 10 字节。驱动负责处理级联协议中的 CT 字节；不得对最终 UID 中任意出现的 88 做字符串删除，也不得自行颠倒字节序。换 SDK 后须用同一实卡验证规范化结果相同。

随机 UID、会话 PUPI、空串、读卡失败后的随机 UUID，不能作为每日领取身份。后续支持 NFC-V／F 时必须明确各 SDK 的字节序和稳定性；仅增加枚举并不等于已通过兼容验收。Web NFC 不保证提供非空序列号，也不提供本规格所需的通用技术探测，因此不能承诺纯网页支持全部 legacy UID 卡。W02

2.4 未登记 legacy 卡与身份一致性

未映射的稳定 NFC-A 卡，只有在成功探测并确认无有效游戏发行描述符，或已验证发行 catalog 明确标记 legacy UID 后，才允许用户明确登记成默认 m5.roles.v1 盲盒卡。未登记状态本身不发奖。不支持/失败的 NDEF 读取不能当作“无 NDEF”降级；仅 UID 读头需要已验证映射。否则同一发行卡可能被一个客户端认作 issued:、另一个认作 uid:，产生重复每日身份。未来有发行注册表时应将这些映射分发到各客户端，但不改变已经登记的身份。

3. PlayerSnapshot 与本机附加数据

3.1 随卡迁移的完整根对象

3.2 不要求放入卡片的本机元数据

每设备按 player_id 隔离保存以下内容：

  • 当前完整快照及其 canonical 明文哈希。
  • last_card_snapshot_id、上次读到／验证写入的卡片哈希和写卡回执。
  • 已验证过的本地祖先索引，帮助识别超过 history_tail 长度的谱系。
  • 冲突双方的原始容器、解码快照、来源与选择记录。
  • 本机领取／对战历史 journal、UI 设置、未完成写卡操作记录。

last_card_snapshot_id 表示曾实际读到或验证过的卡上版本，不能在本机内容更新时顺便更新。历史 journal 可以保留更多天；卡片必须至少包含当前账本规定的全部同日资格，不得为了腾容量悄悄删掉当日已领取卡号。

4. 游戏日与每日领取事务

4.1 固定日历

day_id = floor((utc_ms + 28_800_000) / 86_400_000)

这相当于固定 UTC+08:00 的自然日，用于本游戏的 Asia/Shanghai 日界线。它不读取手机当前显示时区，不应用设备切换时区来刷新资格，也不用运行时长代替 UTC。人类可读日期由 day_id 换算，仅用于界面。

v1 参考实现的有效领取时间范围为 UTC 2000-01-01T00:00:00.000Z 至 2100-01-01T00:00:00.000Z（两端包含），即 946684800000..4102444800000 毫秒。范围外返回时间不可用；范围内也仍需有效的来源状态，不能只看整数大小。

day_ledger = {
  day_id: integer,
  claims: [{
    hero_card_id, template_id, claim_id, claimed_at_ms, pool_id, pool_hash
  }]
}

clock = {
  high_water_utc_ms: safe_integer,
  high_water_day_id: integer,
  last_source: "unknown" | "manual" | "device" | "network" | "server"
}

初始时间未知时，高水位为 0，last_source = "unknown"。没有有效绝对日期时，拒绝领取，但允许训练、查看收藏和保存已有存档。RTC 存在不代表 RTC 已设置正确；驱动必须明确给出时间是否有效。

若观测日早于 clock.high_water_day_id，返回 CLOCK_ROLLBACK，保留账本并暂停新领取；不得退回旧日或清空 claims。相同日内正常校时不会刷新资格，高水位只增不减。向未来改日期再改回来，可能需要等日历追上或明确执行时间修复；时间修复是有记录的管理动作，不能隐蔽地重置领取次数。

新日首次成功领取时，原子地建立新日账本，再写入本次 claim；旧日统计可留本机 journal。仅打开界面、读玩家卡或计算“今天还没领”不要求生成一个空的新存档版本。

4.2 领取键与抽取分工

claim_id = lowercase_hex(SHA256(PCG-C14N-1({
  "domain": "pcg.claim.v1",
  "player_id": player_id,
  "hero_card_id": hero_card_id,
  "day_id": day_id
})))

其中 SHA-256 输入是 canonical JSON 的 UTF-8 字节。pool_id、pool_hash 和客户端版本不进入去重键。盲盒抽取种子包含池哈希，具体 ordinal 抽样和固定卡结果记录方式必须直接使用参考实现及黄金向量，不另用 Math.random()、语言内建 hash() 或各平台独立随机流程。

4.3 本地领取的事务边界

执行顺序必须为：

  1. 确认已登录、没有未解决的存档冲突；识别合法英雄卡和当前内容配置。
  2. 获取有效 day_id；校验时间高水位；查找当前 (player_id, hero_card_id, day_id) 是否已经提交。
  3. 在该玩家的串行事务内重新检查资格，冻结内容池，计算固定／盲盒结果和重复补偿。
  4. 同时修改收藏、钱包、day_ledger.claims、时间高水位以及快照谱系。
  5. 将完整新快照持久化成功后，才发出 HeroClaimCommitted 并播放最终结果。

事务失败时，旧快照继续有效，不扣资格、不扣碎片、不显示最终中奖成功。事务已成功但界面或设备随后中断时，下次刷同一卡返回已提交结果；不得再次发放。只依靠 UI 按钮禁用不足以防重复，底层事务必须按 claim_id 幂等。

每个玩家的每个 day_ledger 内，hero_card_id 必须唯一。不同玩家共用同一实体英雄卡，分别在自己的账本记录，互不消耗。英雄卡在这个过程中没有任何写操作。

5. 业务状态机与重复感应

状态 允许的输入 处理与下一状态
LOGGED_OUT 玩家卡 读取、校验、对账；进入 ACTIVE 或 CONFLICT
LOGGED_OUT 英雄卡 提示先刷玩家卡；不领取、不登记当日资格
ACTIVE 且处于抽卡大厅 英雄卡的新一次感应，玩家确认领取 执行原子领取；成功后仍是 ACTIVE，本机可能比卡新；对战/卡册扫描只定位或查看，不领奖
ACTIVE 明确保存意图 冻结待保存版本，进入 SAVE_ARMED

持续把同一张卡放在天线上，不是一次次新的刷卡动作。可以确认离场的驱动应在稳定检测到移开后再重新武装；不提供可靠离场事件的 API 必须使用单次扫描会话或明确 UI 操作来重新武装。特别是登录后的同一轮检测回调，不能被误解释为“再次刷玩家卡保存”。

在 ESP32 等可以可靠检测移开／再贴的设备上，主动再次贴当前玩家卡可直接作为保存意图，无需强行增加额外确认页。在 iOS 或纯 Web 会话中，可以用“保存到玩家卡”按钮建立一次写会话，然后要求玩家再贴卡；这仍然满足主动刷卡保存，不是后台自动同步。平台差异见第 05 章。

换玩家时，本机已经持久化的进度继续保留。若当前玩家比卡新，界面显示尚未写卡状态；不能自动把当前玩家数据写到新玩家卡上。对战进行中或还有未提交业务事务时，不开始存档写入；先结束当前安全边界，再要求明确的保存操作，不能在后台悄悄排队写卡。

6. 登录时的版本选择

6.1 先验证，再比较

只有完整容器校验、解压、canonical 校验和 Schema 校验通过的快照，才参与比较。比较的是 payload 的 modified_at_ms，不是卡片文件时间、写卡时间、NFC 扫描时间或 slot_generation。

“A 是 B 的祖先”需要在 B 的 parent_snapshot_id、history_tail 或本机已经验证过的祖先索引中找到 A。save_seq 大、时间新、writer_device_id 相同，都不能单独证明祖先关系。

本机 L 与卡上 C 的关系 必须行为
本机没有该 player_id 原子导入 C；登录完成；不回写
ID 和明文哈希相同 使用已有相同版本；不新建修订、不写卡
C 是 L 的已知祖先，L 的 seq 和修改时间均更大 使用 L，标记比卡新；不自动写卡
L 是 C 的已知祖先，C 的 seq 和修改时间均更大 备份 L，原子导入 C；不回写
同一 ID 对应不同哈希 冲突或损坏；保留原件，不自动择一
修改时间相同但 ID／哈希不同 冲突；不能按设备名或读取顺序猜测
已知谱系与 seq／时间先后矛盾 冲突；不能仅因为时间更大覆盖
两个不同 ID 的先后关系不能证明 冲突，包括并行分支；不同 writer 尤须保守处理
卡上是未来不可写版本 可按兼容规则只读；旧客户端不得降级覆盖

冲突页显示双方的修改时间、seq、设备标签、收藏数和钱包摘要，用户选择整份副本。选择前保存双方原始字节和校验值。不得自动相加碎片、合并领取奖励、取两个账户余额的最大值，或把两个分支的盲盒结果都收入收藏。

选择一份副本不是一次新的领取，不需要伪造新的奖励事务。下一次真正修改以选中的快照为父；放弃的分支保留在本机冲突备份中。没有已验证副本时，读取失败不能解释为空白新玩家。

6.2 写入前必须再读一次

保存按钮按下后，卡上版本可能已经被另一设备修改。写前必须重新读取当前卡，并用当前本机快照进行同样的对账。如果发现新的分支，进入冲突处理；不能因为“登录时读过”就覆盖。

若当前卡上已经是相同快照，记录“已一致”，无需消耗一次写入。如果卡上是本机的正常旧祖先，允许保存较新的本机。若卡上是本机的较新后代，先按规则导入；不把旧本机写回去。

7. 保存事务与迁移承诺

7.1 唯一成功路径

明确保存意图
→ 本机最新完整快照已持久化
→ 读目标卡并对账
→ 冻结该快照并编码、测量容量
→ 写卡
→ 从卡重新读取完整数据
→ 解压与 SHA-256 / 头 / Schema 校验
→ 与待写版本的 snapshot_id、完整明文哈希一致
→ 本机记录已验证回执
→ 显示“已保存，可换设备”

写入过程中暂停该玩家新的内容修改，避免 UI 同时抽卡导致“刚保存完又少了一张”。不要求暂停网络心跳或对战房间的只读消息。

写卡只导出已经存在的不可变快照。卡写失败、卡移开、电池断电或读回不匹配时，本机当前快照不回滚，也不从钱包中撤销已成功的领取；显示“进度在本机，写卡未验证成功”。

7.2 失败语义

情况 卡片承诺 本机与 UI

容量未知或容量不足 不开始覆盖 显示所需／可用字节；保留本机，可换大卡

写操作报错 不承诺卡仍可读 本机有效；可显式重试或修复

断电恢复后，如有 pending write 回执，先读卡核对其目标 snapshot_id 和哈希。匹配则补记成功；不匹配则保留本机并等待用户下一次保存，不自动重写。

8. PCSV v1 二进制容器

8.1 明文编码

payload 是完整 PlayerSnapshot 的 PCG-C14N-1 UTF-8 JSON。它是本项目受限 canonical JSON，不是完整 RFC 8785 JCS：

  • 对象键必须是非空 ASCII，按 ASCII 顺序排列。
  • 字符串值保留原 Unicode 标量，不做 NFC／NFD Unicode normalization；不允许孤立代理项。
  • 使用 JSON 必需的转义，不增加无意义空格或换行。
  • 数值仅允许安全整数 [-9007199254740991, 9007199254740991]；禁止 float、NaN、Infinity；具体字段可再限制为非负。
  • 数组保持原有顺序；最大嵌套深度为 32。
  • 解压后的明文最多 65536 字节。

逐字节输出以参考实现与 fixtures 为准。SHA-256 始终计算完整、解压后的 canonical 明文字节，其中包括 snapshot_id；snapshot_id 本身是 UUID，不参与递归求哈希。

8.2 精确 96 字节头

所有数值为无符号 little-endian。UUID 是 RFC 常规字节顺序的 16 字节；不是 Windows GUID 的混合端序布局。

偏移 长度 字段 v1 值／校验
0 4 magic ASCII PCSV：50 43 53 56
4 1 container_version 1
5 1 storage_profile 1=NDEF_SINGLE；2=RAW_DUAL
6 1 codec 0=canonical JSON；1=zlib
7 1 flags v1 为 0；未知位不能忽略后覆盖
8 2 header_bytes 96
10 2 snapshot_schema_version 与 payload save_schema_version 相同
12 4 stored_len 头后有效存储数据长度，不含填充
16 4 plain_len 解压后的 UTF-8 长度，1..65536
20 4 slot_generation 物理容器写入代次；首次写入为 1
24 16 snapshot_uuid 与 payload snapshot_id 相同
40 32 payload_sha256 完整解压后 canonical 明文的 SHA-256
72 8 modified_at_ms 与 payload 相同且在安全整数范围内
80 8 save_seq 与 payload 相同且在安全整数范围内
88 4 header_crc32 下述 CRC，覆盖字节 [0, 88)
92 4 commit_marker 有效为 ASCII DONE：44 4F 4E 45

CRC 为 CRC-32/ISO-HDLC：反射多项式 0xEDB88320，初始值 0xFFFFFFFF，最终 xor 0xFFFFFFFF，输入／输出反射；等价于 zlib.crc32(header[0:88]) & 0xFFFFFFFF。CRC 不覆盖自身及 commit marker。CRC 与 SHA-256 用于损坏检测，均不是来源认证。

codec=1 指 RFC 1950 zlib 包装、内部 DEFLATE；不是 gzip，也不是裸 DEFLATE。禁止 preset dictionary。解码器必须限制输出长度，恰好消费 stored_len 字节，只接受一个完整压缩流，拒绝尾随数据、截断流和解压长度不匹配。不同压缩器可以生成不同压缩字节，但必须解出同一个 canonical payload；互操作比对以明文哈希为准。

slot_generation 与 save_seq 相互独立。重新导出同一份内容可以产生新的物理代次；不得把代次当作玩家内容的新旧顺序。达到 0xFFFFFFFF 后拒写，不能静默回绕；如需重新配置卡片，走显式初始化流程。

8.3 容器解析顺序

  1. 检查头长度、magic、版本、profile、flags、marker、header CRC。
  2. 检查 stored_len、plain_len 和实际剩余容量，先做边界检查再分配内存。
  3. 读取正好 stored_len 字节，按 codec 解码，确认明文长度不超过上限。
  4. 校验 SHA-256；严格解析 JSON；拒绝重复对象键、非法 UTF-8 和不支持的值。
  5. 重新 canonical 编码并要求与原明文字节相同；验证 Schema。
  6. 比较头与 payload 的 schema、UUID、seq、修改时间，全部相同才接受。

9. 两个存储 profile 与真实容量

9.1 NDEF_SINGLE：一条完整 NDEF 记录

使用一个 MIME record，类型为 ASCII application/vnd.pulsecard.save，共 30 字节；无 record ID。record payload 为 96B PCSV 头 + stored payload。v1 的参考编码固定使用非 short-record、非 chunked 的单条记录（MB=1、ME=1、SR=0、IL=0、TNF=MIME，首字节 0xC2）。

NDEF message bytes = 6 + 30 + 96 + stored_len = 132 + stored_len

因此，若平台实际报告的最大 NDEF message 长度是 8192 字节，stored_len 最多为 8060。这个 8192 不包含标签自身 CC、TLV、文件管理和 NLEN 等存储开销；不能直接拿芯片广告容量代入。

高层 NDEF API 通常覆盖整条消息。即使放两份 record，也不等于两个独立随机写槽；掉电时可能连整个 NDEF 消息都不可读。本 profile 的 DONE 只用于格式有效性，不承诺写入原子性或保留旧快照。写失败的恢复源是本机已持久化副本。只有获得特定卡型／驱动的实测保证，才可增加更强的硬件能力声明。A02 D02 W02

玩家卡是游戏专用卡。若当前 NDEF 消息还有未知业务记录，v1 不默默删除它们：应拒绝专用卡写入，或在独立初始化流程中明确处理。不得将旅游票、门禁卡等未知卡自动转换为存档卡。

9.2 RAW_DUAL：可靠随机写入的双槽

本 profile 的逻辑有效区固定为 8192 字节。它可以映射到一个合适的应用文件，也可以映射到两个独立 4096 字节文件，但驱动必须保持以下逻辑布局：

区域 逻辑偏移 长度 内容
slot 0 0 4096 96 字节头 + 最多 4000 字节 stored payload
slot 1 4096 4096 同上

头之外的尾部为无意义填充，不属于哈希范围。每槽独立校验。只有明确的新卡初始化流程可以建立首份快照；虚拟卡以全零 8192 字节表示未初始化卡，首写 slot 0、generation=1。一个非空但没有有效槽的卡是损坏／未知卡，不能自动当作新卡覆盖。

存在有效槽时，选择最高有效 generation 作为已提交版本，下一次写另一槽，generation 加一。两个有效槽的 player_id 不同、同 snapshot_id 但内容 hash 不同，或 generation 相同但内容不同，都属于容器冲突，不按槽号猜测。给卡换绑定玩家必须走显式重新初始化流程，不能留下混合玩家的两个有效槽。

扫描两个槽时，必须区分“普通损坏／未提交槽”和“可识别但本端不理解的未来格式”。发现未来容器版本、codec、flags 或未来 Schema，不得把它一律当坏槽忽略，再选旧 v1 槽进行覆盖；保留原字节并进入只读／升级处理。允许回退的是已经确认无效的中断写槽，不是可能有效的未来存档。

严格写入步骤：

  1. 保持当前有效槽不变，选另一个槽为目标。
  2. 将目标 commit_marker 清为 00 00 00 00，读回确认无效后才改目标其他内容。
  3. 写目标 payload 和头的前 92 字节；不要触碰另一槽。
  4. 重新读取目标内容，按“未提交”模式校验除 marker 外的完整预期数据。
  5. 最后写 DONE marker，再读回整个槽，通过正常解析器验证。
  6. 保留旧槽；不必再写一个共享“当前槽指针”。

这个恢复模型以以下能力为前提：驱动确实支持独立地址／文件写入；写目标槽的掉电不会重写另一槽；底层写粒度、擦除粒度、卡上事务／备份文件行为已经核实；底层不会把整个应用文件透明重写。若这些条件不成立，必须降级为 NDEF_SINGLE 或拒绝声明 RAW_DUAL。

双槽保障是“在已验证故障模型内，提交失败仍保留旧有效槽”，不是“任意 NFC 卡永不损坏”。不得把 NDEF message 中两个数组元素叫作抗断电双槽。首次初始化前没有历史有效槽，也不存在可恢复的旧卡存档。

10. 未来版本、损坏与信任层

未知字段必须原样保留其语义值并参与 canonical 编码和哈希。旧端无法保留未来字段，或未来字段超出 PCG-C14N-1 子集时，只读或拒绝写入；不得反序列化成旧结构后丢掉字段再保存。未知 save_schema_version、容器版本、codec 或 flags，同样不得降级覆盖。

默认信任层是 casual_local：本机是当前进度的持久化权威，卡是用户明确导出的离线副本。校验和、确定性 claim_id 和时间高水位能避免常见重复回调、误操作和单机回拨，但无法在完全离线的多设备之间证明全球只领取一次。同一旧卡快照可在两台设备上产生分支，改时钟／恢复旧备份也不能靠普通标签彻底防止。

可选 server_verified 可以让服务端签发每日领取回执、验证时间和资格，或者将竞技牌组限定为服务端认可集合；它是独立能力，不得成为本地模式的强制联网条件。服务器也不得把在线对战接入解释为自动云迁移授权。

11. 最小验收项目

完整恢复测试见 07_ACCEPTANCE_AND_RECOVERY.md。本章至少要求：

  1. 玩家卡只登录，保持在读头上不触发写卡；移开后再次明确保存才写。
  2. 固定／盲盒卡同玩家同日重复扫描只产生一个领取；另一玩家可以领取。
  3. 本地事务前后分别模拟崩溃，奖励和账本始终同时存在或同时不存在。
  4. 本机较新、卡较新、同时间异 hash、并行分支、谱系超出 16 代均有明确处理。
  5. 领取后不写卡换设备，只能看到旧卡版本；验证写卡后换设备能恢复完整收藏及当日资格。
  6. NDEF 模式写一半失败，本机仍完整；不能假定卡上旧消息必然可读。
  7. RAW 模式在清 marker、写 payload、写头、最终 marker 各阶段掉电，只选择校验通过的槽。
  8. 容量边界、解压超限、未知字段、坏 CRC／SHA、非法 UTF-8、重复 JSON key 均能拒绝。
  9. Web／iOS 无法即时新鲜读回时停在待验证状态，不能提前显示“可迁移”。
  10. 虚拟卡文件适配与真机采用相同容器和业务状态机；虚拟测试通过不等于硬件掉电测试通过。

04 · PCG/1.0 通信协议

状态：v1 可实现契约。本文中的 MUST / MUST NOT / SHOULD / MAY 分别表示必须、禁止、建议、可选。规则语义由核心规则文档与 reference engine 的 golden fixtures 规定；本章定义消息、会话、裁判边界、传输与恢复。schemas/envelope.schema.json、schemas/frame.schema.json 和 examples/wire_examples.json 是本章的机器可读配套。

协议名 pcg；线路版本 1.0；基线规则 pcg.core.v1；基线内容包 m5.core.v1。消息中的 rule_id 与规则状态中的 ruleset_id 指向同一个不可变规则契约，数值必须相等。

1. 互战的边界与裁判

一场对战 MUST 只有一个逻辑 AuthorityAdapter。它可以运行在专用服务端，也可以运行在可信房主设备上。所有玩家把意图提交给它；只有它调用 reducer、分配 revision、记录结果并生成各玩家的可见状态。ESP32、Android、iOS、Web MAY 使用不同 UI、动画和通信模块，但 MUST 使用完全相同的命令语义。客户端本地模拟仅用于预览；不得把模拟结果作为其他玩家的权威状态。

组件 输入与输出契约 不可替代的职责
TransportAdapter 发送/接收一份完整 envelope 的字节串；报告连接关闭与传输错误 可靠、有序、允许重复地交付消息；实现 WebSocket、字节流或本章分片
认证上下文 已验证的对端身份、当前 session、对应玩家/旁观者权限 把 sender_id 映射到玩家，不接受消息自报的 seat 或权限

ViewAdapter 完整状态 + 已认证观看者 → 可见状态 本人手牌列表、对手手牌数量；旁观者看不到任何私有手牌

authority_mode=trusted_host 是明确的信任房主模式，适合朋友局和离线局。房主程序能够接触裁判的完整信息。authority_mode=dedicated_server 才是本规格的排位部署基线；客户端自行声称这个枚举不产生信任。服务器运营方的认证、持久化和访问控制仍须成立。PCG/1.0 不宣称通过状态哈希就能证明房主没有作弊。

NFC 在此系统里承担实体卡的识别、导入与选择。它不是远程战斗传输链路。NFC 原始 UID、实体卡身份材料和收藏所有权证明 MUST NOT 放进公开战斗 snapshot 或发给对手；战斗使用本局实例 ID，例如 p0:00。

2. 标识、编码与规范 JSON

2.1 基础值

  • 所有协议 ID 使用 ASCII，匹配 ^[A-Za-z0-9][A-Za-z0-9._:-]*$，长度 1–64。大小写敏感，不自动 trim、改大小写或做 Unicode 标准化。版本字符串及 opcode 也使用此约束。
  • 所有 JSON 对象键 MUST 是非空可打印 ASCII（U+0020–U+007E）。协议定义的键使用下划线形式。用户展示名字可以是 Unicode 值。
  • 所有整数绝对值 MUST ≤ 9007199254740991（2^53−1）；计数、seq、revision、时间间隔 MUST 非负。协议禁止浮点、NaN、Infinity、指数记数法和 -0。涉及更大空间的标识使用字符串。
  • SHA-256 表示为 64 个小写十六进制字符。ID、散列值、牌名和 token 不可互换。
  • 每个完整 envelope 的规范 UTF-8 字节长度 MUST 为 1–8192；PCG-C14N-1 与本 wire profile 的嵌套深度上限均为32（根值 depth=0，进入数组元素或对象值加1）。超过上限拒绝，不能截断后执行。基线接收方 MUST 能处理 8192 字节。

2.2 PCG-C14N-1

所有发送的 envelope、规则状态/可见状态哈希输入和幂等比较输入，使用以下精确定义的规范 JSON 子集：

  1. 拒绝重复对象键、非法 UTF-8、BOM、孤立 UTF-16 surrogate。禁止把解析错误静默替换为 U+FFFD。
  2. 递归按对象键的原始 ASCII 码值升序排列。数组保持原顺序。
  3. 不输出 token 之间的空格、换行或其他空白。
  4. 整数使用十进制、无前导零、无加号，不输出 .0 或指数。布尔和 null 分别为 true、false、null。
  5. 字符串中的 " 与 \ 必须转义；U+0008/0009/000A/000C/000D 使用 \b/\t/\n/\f/\r；其他 U+0000–001F 使用小写 \u00xx。
  6. 其余 Unicode 标量直接编码为 UTF-8，不转义 /，不把汉字或 emoji 改成 \u 序列；不执行 NFC/NFD 等 Unicode 标准化。é 和 e 加组合重音是不同字节。
  7. SHA256(canonical_utf8_bytes) 对规范字节计算，不对内存结构、带缩进 JSON 或平台默认 serializer 输出直接计算。

本子集参考 RFC 8785 的字符串、Unicode 保留和规范序列化原则，但通过 ASCII 键与安全整数 缩小输入范围；不允许用“任意合法 JSON”代替它。[S2] Python 的 json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False) 只有在先验证这些输入限制后才适用。JavaScript 需递归排序键，不能把一次 JSON.stringify 当作排序器；使用 Number.isSafeInteger 验证数字。Android/iOS/ESP32 也必须明确编码选项。

接收流程为：限制字节数 → 严格解析并检测重复键/非法 token → 检查值范围/深度 → 规范重编码 → 与收到的字节逐字节比较 → JSON Schema → 会话/游戏语义。重编码不同则报 NON_CANONICAL_JSON，不得悄悄改写后执行。Schema 本身无法检测重复键、数字原始写法或 UTF-8 字节长度，不能省略这一层。

Session 是双向连接的逻辑标识。A 和 B 加入同一 match_id 时使用不同 session。客户端的 seq 与 authority 对该客户端的 seq 各自递增，不能混用整个房间的一根计数器。

只有 HELLO 使用 session_id=null,seq=0,ack_seq=0。认证完成后客户端发送一次 HELLO；裁判返回 seq=1 的 CAPS 并赋予 session_id。重连创建新的 session，重新从 1 计数。旧 session 上的消息不得进入新 session。

msg_id 重用且内容不同是 MESSAGE_ID_CONFLICT。已经交付过的 (session_id,sender_id,seq,msg_id) 重复消息不再次执行，必要时重发接收确认。同 seq 但不同消息视为协议错误。正常 Adapter 保证有序；若接收 seq 大于期望值，报 SEQ_GAP 并重新建会话/RESUME，不在客户端猜测缺失的意图。ack_seq 不能倒退，也不能超过本端已发送的最大 seq。

收到普通消息后，如果 100ms 内没有其他出站消息带回累计 ack_seq，SHOULD 发 ACK。收到 ACK、PONG 或 ERROR 不单独触发 ACK，避免确认循环；后续消息仍带累计序号。这依赖底层 Adapter 的可靠有序交付。ACK 丢失不能导致重复扣牌或重复执行动作。

4. 协商与状态机

4.1 开局路径

  1. Adapter 建立经过认证的链路，authority 将它绑定到账户/临时玩家或只读旁观者。房间码只定位房间，不自动等于玩家身份认证。
  2. Client → HELLO：支持的线路版本、规则 ID、缓存内容 manifest 的精确 hash、effect opcodes（含trait能力）、features、资源限制和请求的 match。
  3. Authority → CAPS：确定线路版本、认证后分配的玩家 ID、房间 match、authority 模式、共同 features 和限制。HELLO 中的 client_id MUST 等于 envelope.sender_id；CAPS.authority_id MUST 等于其 sender_id。
  4. Authority → SELECT：唯一选定 selection_id + rule_id + content_pack_id + content_version + content_hash + required_features + required_opcodes + room_policy。客户端须真正加载并验证该 manifest，不能仅把 hash 字符串抄回。
  5. 各 Client → READY：回显相同 match、selection、rule、content_hash，并私下提交有顺序的 deck_template_ids[10]。所有参与对战玩家的牌组验证通过且均 READY 后，authority 才建立初始规则状态并发送各自 SNAPSHOT。旁观者不阻塞开局。
  6. Client → COMMAND → Authority → RESULT + 各自 SNAPSHOT，直到规则状态 finished。

trait能力与opcode共用数组，不增加第二个traits字段：包中的 required_ops 保留原名，required_traits 则添加 trait: 前缀。因此core需要 NONE,BOOST,DAMAGE,SELF_BOOST_OTHER_ROW,trait:shield_once,trait:stable。HELLO用 effect_opcodes、SELECT用 required_opcodes，未知trait与未知op一样拒绝。platform支持esp32/android/ios/macos/windows/linux/web/test。

基线共同 features 固定为 pcg.snapshot.v1、pcg.command.v1、pcg.resume.v1、pcg.canonical.v1。SELECT 所需 feature/opcode/trait 必须是该客户端 HELLO 宣告支持的子集。rule_id、content_hash 和完整必需 opcode/trait 支持必须全部通过；“卡片显示得出来”不代表能执行它的效果。

新内容的获取是 ContentLoader 的职责，可通过预装、HTTPS、经认证桥接传输或本地安装同一个包完成。PCG/1.0 战斗消息不夹带图片或整包文件。若内容尚未就绪，客户端发非 fatal 的 CONTENT_MISSING / UNSUPPORTED_EFFECT 等 ERROR，保持未 READY；加载成功后再 READY。此时不得运行开局时限。authority 更换 SELECT 后会清空旧 READY，必须生成新的 selection_id。对局开始后 SELECT 不可变。

如果 HELLO 没有共同线路/规则版本，authority 在已认证链路上分配临时 session 后发送 fatal ERROR 并关闭。不得自动选择近似规则。客户端若仅实现未来主版本，必须另实现 v1 协商 shim 或使用独立入口；不能将不可解析的未来消息伪装为 1.0。

4.2 牌组提交与房间策略

SELECT.body.room_policy 是authority发给所有参与者的同一份不可变房间策略：

字段 约束与语义
mode casual 或 ranked；ranked只能使用经过认证的专用server authority
deck_source shared_pool：所有玩家使用同一允许池；verified_collection：authority还须检查玩家的已验证可用资格
allowed_template_ids 10–128个互异模板ID，全部来自锁定manifest；对所有玩家公开
turn_timeout_ms v1固定0：无自动回合判负、无强制PASS
reconnect_grace_ms v1固定300000：失联5分钟仍未重连时房间suspended，纯规则状态保持不变

READY的deck_template_ids必须是恰好10个不同模板ID的有序数组，均在允许池中，且按core.v1至少有6张unit。客户端提交只表达选择；服务端必须自行验证包、模板、数量与访问资格。该数组只发给authority，不广播对手。数组顺序对应本局p0:00..09或p1:00..09实例的创建顺序，不能被某个平台自行排序。seed只控制规则规定的先手；不要自创洗牌算法。

某个 selection 的第一次合法 READY 锁定该玩家有序牌组；相同 selection、rule、content_hash 与同一有序 deck 的重复 READY 不改变状态。若重连时看到 waiting，但在重发 READY 前房间已刚刚开局，authority 对上述重复 READY 只向该认证观看者返回当前 SNAPSHOT，不重建 match、不重新发牌、不改变 revision，也不把原牌组当成一次修改。尚未开局时，修改牌组或 room_policy 需要 authority 签发新的 selection_id 并清空所有 READY。开始后牌组、rule、hash 及 room_policy 不变化，不接受不同牌组的 READY。RESUME 不携带新牌组；只能恢复原局。

缺一份牌组、牌组不合法、未知模板、访问资格失败或能力不全时，authority发ERROR且不创建规则状态。shared_pool的免费基础池是默认试玩方案。verified_collection所需身份/收藏验证通过独立认证数据路径完成，不把原始玩家卡、UID或所有权证明泄漏给对手。

HTTP-WSS profile 的默认连接心跳为空闲每15秒 PING；45秒没有收到所请求的 PONG 或其他有效已认证 PCG 响应，标记失联并显示重连。PCG-F1 适用第9.4节的传输计时例外：完整 envelope 可能传输超过45秒，不能仅因没有完整应用消息而提前关闭仍在合法传输的 link。房间的5分钟重连宽限从 TransportAdapter 确认失联或关闭连接时开始，不从一个大包开始发送或最后一条完整 envelope 的时刻开始。宽限到期仍未恢复，房间层标记 suspended，不修改战斗 revision，不替玩家 PASS，不判输赢。房间与幂等日志至少保留24小时以供原玩家恢复。关闭/放弃房间记录为房间元数据 aborted，无竞技胜负；纯规则引擎仍只有 points 产生的正常终局。定时判负、resign 操作及异步长回合策略需未来独立协商 profile 及完整状态契约，v1不能宣称已实现。这些连接/房间状态与墙钟不加入纯规则状态 hash。

5. 命令、幂等与 revision

5.1 固定命令

{"action_id":"player_a-000001","card_instance_id":"p0:00","expected_revision":0,"kind":"play","match_id":"match_demo_01","row":"front","target_instance_id":null}

play 的 card_instance_id MUST 非 null。若所选模板为 unit，row MUST 为该模板允许的 front 或 rear；若为 tactic，row MUST 为 null。Schema允许play.row为null，具体单位/战术校验由authority对照锁定的manifest执行。目标可为实例 ID 或 null，是否必须指定、能否选择该排位和该目标，由规则与卡包决定。pass 的 card_instance_id,row,target_instance_id MUST 全部为 null；不能用省略或空串代替 null。

命令中没有 player、actor 或 seat 字段。authority 从已认证 session 映射到 seat0/1，然后调用 reducer。p0:00..p0:09 和 p1:00..p1:09 只表示本局固定实例；收藏卡编号与实体 NFC UID 不进入 reducer。

客户端 MUST 在发送前持久保存未完成动作的 action_id 与原始七字段。一个 action_id 在该玩家该局里只能对应一个确切意图。

5.2 裁判处理顺序

  1. 校验身份、session、房间权限、消息大小及 schema。
  2. 查询幂等键 (match_id,authenticated_player_id,action_id)。存在且规范命令 body 相同：返回已记录的 同一 RESULT.body；不能先因 expected_revision 旧而拒绝。存在但 body 不同：ACTION_ID_CONFLICT，不覆盖原记录。
  3. 新 action 的 expected_revision 必须等于当前 revision；否则返回 status=rejected,error_code=STALE_REVISION 和当时的当前 revision，并发送新 snapshot。
  4. reducer 进行回合、手牌、目标、排位、通过状态等规则校验。合法动作调用一次 reducer。
  5. 一个已接受动作让 revision 精确 +1，包括动作引起的小局结算；纯显示、PING、ACK、拒绝和重复动作均不增加 revision。
  6. 原动作、命令摘要、结果与新状态 MUST 一起持久提交，再发送 accepted RESULT。若 advertise pcg.resume.v1，进程重启后也必须保留已提交的幂等结果。先发成功再保存会产生重复执行风险，不符合此规格。
  7. 按每位已认证收件者重新生成 snapshot；先向发命令者发 RESULT，再发最新 snapshot。对手只需要自己的 snapshot，不能接收发命令者的私有响应副本。

被规则拒绝的新 action 也保存原始 RESULT；重复它仍返回原来的拒绝结果。用户修改意图或按新 revision 重试时必须使用新 action_id。若只是不知道第一次是否已送达，必须复用原 action_id 与完全相同的 body，并使用新的 envelope.msg_id/seq。

每局每玩家至少保留 1024 个动作结果；超出协议资源限额时停止接纳新的 action 并发 RESOURCE_LIMIT，不得丢弃尚可重试的旧记录。终局后至少保留 24 小时的状态及幂等日志；服务可保留更久，但必须对到期返回 MATCH_EXPIRED，不能把旧 action 当作一场新局。速率限制可在动作入列前返回 ERROR，不形成已执行的 RESULT。

RESULT.revision 是该动作原始处理时的 revision，不保证等于此刻最新 revision。因此重复 RESULT 的旧 revision 不能让客户端回滚。客户端如果需要最新状态，应用另发的 snapshot 或 RESUME。error_code=null 当且仅当 status=accepted；accepted 的 snapshot_required=true。

6. 可见状态与重连

6.1 Snapshot

SNAPSHOT.body.view 是规则定义的 viewer-filtered 状态。自己的玩家记录带 hand:[{instance_id,template_id}]；对手记录只带 hand_count。所有玩家的公开 board、discard、小局结果和比分可见。旁观者的两位玩家都只有 hand_count。完整随机 seed、对手隐藏实例 ID、完整牌组/未公开收藏记录、原始实体卡内容不可出现。authority 内存里的 full-state 不可直接 json.dumps 后广播。

view_player_id MUST 与认证上下文对应；旁观者为 null。view_hash=SHA256(PCG-C14N-1(view)) 只保证本次可见状态的稳定校验；不能使用 authority 完整状态 hash 冒充它。完整状态 hash 仅供服务端/引擎 golden fixtures 校验，不作为客户端判断隐藏信息的依据。

客户端检查 body.revision 与 view.revision 相同、rule_id 与 view.ruleset_id 相同、content_hash 与已选 hash 相同，再校验 view_hash。只应用比本局当前 revision 更新的 snapshot；相同 revision 与相同 view_hash 为重复，同 revision 但不同 hash 是 STATE_CONFLICT，需要暂停输入并 RESUME/诊断。比较必须限定同一 match 与同一观看者。view 不放本地时钟、动画位置或临时网络 RTT，避免同 revision 的 hash 随 UI 改变。

权威快照允许跨过多个 revision，客户端无需收到每个事件才可恢复。不得为补一帧动画先应用比当前状态更旧的 snapshot。

6.2 Resume

断线后重新认证，创建新 session，走 HELLO/CAPS/SELECT。客户端重新验证 SELECT，然后发送 RESUME（此时不另发 READY 重开棋局）：

{"content_hash":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","last_revision":7,"match_id":"match_demo_01","pending_action_ids":["player_a-000004"],"rule_id":"pcg.core.v1"}

上面 hash 是测试占位，实际值来自所选内容包。authority 根据认证身份找回同一个玩家 seat，不能因客户端提供 player_id 而换座。即使 last_revision 已是最新，基线实现也返回当前完整 viewer-filtered SNAPSHOT；随后返回 pending_action_ids 中仍在日志中的原始 RESULT，最多 16 个。未找到的 pending action 不伪造成功；发命令者可用原七字段重发，幂等处理照常。

若 last_revision 大于 authority 当前 revision，返回 REVISION_AHEAD 并暂停自动恢复，避免隐藏服务端回滚或错误房间。规则/内容不同返回 CONTENT_MISMATCH 或 RULE_MISMATCH；客户端不能自动迁移正在进行中的对局。旧 session 的 seq/msg_id 不转移，新封装可携带同一历史 RESULT.body。

客户端超时只能显示等待/重连，不能自行判负、通过、移动牌或推导对手动作。v1默认失联后仅suspended；终止房间记aborted，不创造reducer timeout/resign动作或竞技胜负。墙钟与重连宽限不进入纯 reducer 的状态哈希输入。跨 Authority 接力、自动主机迁移与双裁判容错不属于 v1；房主丢失时恢复原房主持久状态，或明确结束对局，不允许双方各选一个新结果。

7. 已知与未知消息

  • 已知消息的未知顶层字段、未知 body 规则字段：INVALID_MESSAGE。不能把拼错的字段静默忽略。
  • 已知 body 的 presentation 中未知字段：可忽略；不得执行脚本、改变牌力或权限。展示值也受 JSON 范围、深度和尺寸上限限制。
  • 未知 type 如果匹配 ^X_[A-Z0-9_]{1,48}$：消费 seq、可确认并忽略，不改变规则状态。对端不能依靠这种消息实现不可省略的功能。
  • 其他未知类型：UNSUPPORTED_MESSAGE。在 match 开始前拒绝所需 feature；运行中出现未协商的必需消息则 fatal，关闭并诊断。
  • 已认识 template_id 但其内容包含未知 opcode、schema major 或必需字段：拒绝 READY/开局。绝不能跳过效果后继续打。
  • 客户端处理未知 ERROR.code 时仍尊重 fatal/retryable，显示安全的 message 或通用错误；不得把“未知错误”当作成功。

基线错误码：INVALID_MESSAGE、NON_CANONICAL_JSON、JSON_DUPLICATE_KEY、JSON_KEY、JSON_INVALID_UNICODE、JSON_INTEGER_RANGE、JSON_FLOAT、JSON_DEPTH、JSON_INVALID、JSON_TYPE、UNSUPPORTED_PROTOCOL、UNSUPPORTED_MESSAGE、UNSUPPORTED_FEATURE、UNSUPPORTED_EFFECT、CONTENT_MISSING、CONTENT_MISMATCH、RULE_MISMATCH、UNAUTHENTICATED、NOT_AUTHORIZED、SESSION_EXPIRED、SEQ_GAP、MESSAGE_ID_CONFLICT、ACTION_ID_CONFLICT、STALE_REVISION、REVISION_AHEAD、STATE_CONFLICT、MATCH_EXPIRED、RATE_LIMITED、RESOURCE_LIMIT，以及核心引擎的规则拒绝码。ERROR.message 不回显私有手牌、认证 token 或原始卡数据。解析坏包可以直接关闭；不得向不可识别/未认证的来源反射大段 ERROR。

8. 大 MTU 与字节流传输

8.1 WebSocket 基线

  • WebSocket 子协议名为 pcg.v1，跨互联网使用 WSS；玩家凭证通过认证适配器建立，不放在战斗 body。统一房间服务/WSS接入的创建、加入、seat bearer与pcg.auth.v1前导认证由本项目房间接入文档（第12章）定义；该认证JSON在HELLO之前，属于TransportAdapter，不是PCG envelope，不调用reducer。
  • 每一条 binary WebSocket message 恰好是一份 PCG-C14N-1 UTF-8 envelope。不加长度前缀，不使用 PCG-F1。WebSocket 自身 frame fragmentation 由其库复原后再交给 PCG。
  • 不得把多条 JSON 拼接在一个 message；也不得把一条 JSON 拆成多个应用 message。基线拒绝 text message；实现不能只按字符串发送却宣称通过基线互通测试。
  • 完整解压后也必须满足 8192 字节上限；v1 不要求压缩。推荐关闭 WebSocket 扩展压缩以简化 ESP32 实现和资源上限。

8.2 可靠字节流

用于 TCP/TLS、USB/串口桥、可靠 BLE GATT 字节流等：

uint32_be byte_length | byte_length 个 canonical UTF-8 字节

长度 1–8192；0 或超上限立即报协议错误/断开。接收器必须支持长度头分多次到达、JSON 跨多次 read、一次 read 同时包含多条消息。不得用 \n 找消息边界，也不能假设一次 read 等于一条 envelope。BLE Adapter 须处理 GATT 分块和顺序，不能把每个 ATT notification 当成一份 PCG 消息。

认证后的可靠传输必须把鉴权结果传给 authority，不以连接地址、客户端自报 sender_id 或设备型号代替身份。离线自动化测试可以使用明确标记的 in-process 已认证 fixture；这不等于生产端可省略认证。

9. 低 MTU 数据报：PCG-F1

ESP-NOW、支持足够应用负载的 RF 数据报和它们的桥接链路可使用 PCG-F1。每一份完整 JSON 被顺序切片，receiver 重组后才进行 envelope 解析。Frame checksum、frame ACK、envelope ACK、RESULT 是四种不同含义：分别为传输损坏检测、片接收、消息接收、动作裁决。

9.1 MTU 与链路打开

frame_mtu 表示 Adapter 认证/加密封装之后仍可提供给 PCG-F1 的一包最大字节数，包含本章 24 字节头。基线支持 128，推荐同能力双方选 200；固定到本 link 结束，不在中途改变。Espressif 官方文档说明 ESP-NOW v1 最大数据长度为 250 字节，v2 为 1470，混合版本要遵守 ≤250 的兼容边界；因此本规格不把新版大包作为共同能力。[S1]

若真实物理包仅能承载 20/32 等更小字节数，须由该 Adapter 提供可靠字节流或经桥接聚合，不能直接发送一个装不下的 PCG-F1 frame。不能以“有无线”推断两端原生互通。

PCG-F1 在已经绑定到认证对端的数据报链路上工作，不用于广播秘密信息。Client 生成非零 uint32 link_id，发 OPEN；Authority 选定参数回 ACCEPT。控制帧本身只有 32 字节，在 128 的基线下可收。Client 收到有效 ACCEPT 后才发送 HELLO；Authority 收到 HELLO 后才发送 CAPS 等应用消息，所以 ACCEPT 丢失不会造成服务器提前发送大包。重复同一个 OPEN 回相同 ACCEPT，不重置已建立的链路状态。参数改变或 link_id 改变须建立新会话并 RESUME。

OPEN 最多初次发送 + 4 次重发，每次等待所请求的 RTO。无 ACCEPT 则失败关闭；不是无限重试。认证适配器 MUST 防止旧 OPEN 在已使用的 link_id 上重置计数；link_id 是路由/重组标记，不是身份密钥。

9.2 精确二进制头

所有多字节整数 big-endian/network byte order。无结构体 padding、无 C ABI 对齐、无字符串终止符。payload 直接紧随第 24 字节。

起始 offset 大小 字段 值/约束

2 1 frame_version 1
3 1 kind DATA=1、ACK=2、OPEN=16、ACCEPT=17
4 4 link_id 非零 uint32，绑定已认证对端
8 4 transfer_id DATA/ACK 为 1..2^32−1；OPEN/ACCEPT 为 0
12 2 total_len 完整 JSON 的字节数；DATA/ACK 为 1..8192；控制帧为 0
14 1 frag_index DATA 为 0..frag_count−1；其他为 0
15 1 frag_count DATA/ACK 为 1..128；控制帧为 0
16 2 payload_len 当前 payload 字节数，不能由无线库的 buffer 容量代替
18 2 flags v1 固定 0；其他值拒绝
20 4 crc32 下节定义，编码为 big-endian uint32
24 payload_len payload 当前帧内容

actual_datagram_length MUST 恰好等于 24+payload_len 且 ≤ frame_mtu。任何多余字节、缺失字节、未知 version/kind/flags、非法 index/count 或 CRC 错误都丢弃，不确认该片，不分配大 buffer。

CRC32/ISO-HDLC：reflected polynomial 0xEDB88320，init=0xFFFFFFFF，xorout=0xFFFFFFFF，refin/refout=true。计算对象为 header[0:20] || payload，不含 offset20..23 的 crc 字段。Python zlib.crc32(first20 + payload) & 0xffffffff 与此定义等价。CRC 在头中仍以 big-endian 写入。测试标准串 123456789 的 CRC 为 0xcbf43926。

CRC 只能发现损坏，不能阻止伪造、篡改或重放。私有 battle 数据必须经认证且具完整性/保密性的 Adapter 传输：例如 WSS/TLS 或正确配对并使用非默认密钥的加密单播链路。ESP-NOW 支持 CCMP 保护，但不可因此把任意明文广播或 MAC 地址自动视为已认证。[S1] 裸 RF 的实现须补齐安全 Adapter 或只接到可信本地桥，不得宣称已经达到排位安全边界。

9.3 各 kind 的 payload

OPEN / ACCEPT 的 payload 固定 8 字节：

payload offset 大小 OPEN 含义 ACCEPT 含义
0 2 maximum_frame_mtu：128 或 200 selected_frame_mtu：双方最大值的较小者
2 2 max_envelope_bytes：固定 8192 固定 8192；不支持则拒绝连接
4 4 minimum_rto_ms：1000..60000 双方最低 RTO 的较大者，1000..60000

header 的 transfer_id/total_len/frag_index/frag_count 都为0，payload_len=8。既定参数随后由 HELLO/CAPS.limits 反映；HELLO/CAPS 不重新调整 frame_mtu。CAPS 内容与实际 Adapter 参数不符就断开，不能偷偷重解释后续分片。

DATA：设 C=frame_mtu−24，N=ceil(total_len/C)。frag_count 必须等于 N。第 i 片承载 JSON 字节 [i*C:min((i+1)*C,total_len)]；非最后片 payload_len=C，最后片恰好剩余字节。UTF-8 字符可能被切开，必须完整重组后解码。MTU128 的 C=104；MTU200 的 C=176。最大 8192 字节在两档分别需要 79、47 片，都在128片上限内。

ACK：复制所确认 DATA 的 transfer_id、total_len、frag_count；frag_index=0；payload_len=16。payload 是 128-bit 接收 bitmap；第 i 片的位为 payload[i//8] & (1 << (i%8))。1 表示该片已收到并通过结构/CRC校验。索引≥frag_count 的所有位必须0，不能将bitmap当作整数再按平台端序处理。ACK 不再被 ACK；任一合法重复 DATA 会触发新的累计 ACK。

9.4 发送、重组、重试与限额

  • 每个已认证对端、每个方向同一时刻最多 1 个 transfer。双方可各有一个反向 transfer，但半双工无线 Adapter 要排程发送。
  • 基线发送窗为 1 片：发送最低尚未确认的 index；收到包含该位的有效 ACK 再发下一片。不要求实现滑动窗口或压缩。
  • 每片初次发送后启动选定的 RTO；无确认则原字节重传，最多4次。初发与四次重发分别在0、RTO、2RTO、3RTO、4RTO；5RTO仍未确认则关闭该 link，报告传输失败并重连/RESUME。不能换新 action_id 来“绕过”失败。
  • 接收端收到任意合法片都可初始化该 transfer 的缓冲区，不要求先收到 index0；支持乱序、重复与跨回调到达。只在 bitmap完整且恰好 total_len 后交付 envelope 一次。
  • 对正在重组的 transfer，total_len/frag_count 必须保持一致。同 index 重复 payload 不同，或同 transfer 参数冲突，视为损坏/攻击并关闭链路，不任选一个版本。已完成 transfer 的旧片也 MUST 核对 metadata 和对应片的 payload SHA-256；不一致关闭链路，一致时只回复原完整 ACK，不再次交付。
  • 收到每一片有效 DATA 之后立即发累计 ACK；如果重复片来自已完成 transfer，则回该 transfer 的完整 ACK，不再次交付。最后一片 ACK 遗失也靠此规则恢复。
  • 每个方向的 transfer_id 从1递增，不循环使用。到2^32−1后须新 link/session。重发沿用同 transfer_id。若当前 transfer未完成却收到新的 transfer_id，则拒绝新 transfer并关闭/恢复；正常 stop-and-wait sender不会产生这种顺序。
  • 已完成 transfer 的 metadata、各片 payload 的 SHA-256 与完整 bitmap 只缓存最近8个完成 transfer；每项 TTL 为 max(60000,6*RTO) 毫秒，新增第9项时允许先淘汰最旧项，不承诺每项都存满 TTL。超过容量或 TTL 而不在缓存中的旧片，只要不大于最高完成 ID 就丢弃，不能当新消息。向前的新 transfer 只能是预期的下一个 ID。
  • 单个未完成 transfer 无任何新片超过6RTO即清理并关闭 link；重复片不延长此计时。硬期限从第一片开始为 (frag_count+6)*5*RTO，超过则清理，无限慢滴数据不能无限占内存。
  • F1 链路空闲时可每15秒发一条 PING 探测，不能让它插队或中断已开始的 transfer。已有活跃 transfer 时，按以上片 ACK、重试、6RTO 与硬期限判断传输失败；不得套用 WSS 的45秒完整消息阈值关闭仍有合法传输进展的链路。PING 已完整交付且没有活跃 transfer 时，等待应用 PONG 或其他有效 PCG 响应的探测期限为 max(45000,5*RTO) 毫秒；收到有效响应即结束本次探测，不重复堆积 PING。探测期限或以上传输期限耗尽时 Adapter 才报告失联，并开始房间的5分钟重连宽限。
  • 每个已认证对端至多一个8192字节入站重组缓冲区；出站也至多一个。设备可以限制同时认证 peer 数量，拒绝超额连接。CRC/长度验证先于按 total_len 分配内存。
  • ACK丢失、DATA丢失、重复、乱序都只影响交付时延，不增加 reducer 执行次数。低带宽 RF 的 RTO 和 airtime 限制可能让一条消息花很久；这不适合高频实时对战，但可承载本项目的离散回合消息。

schemas/frame.schema.json 是解码后字段的检查形式，JSON 本身不发送到无线链路。它不能替代 CRC、index<count、精确切片尺寸、位图空位、实际长度等跨字段校验。二进制 codecs 必须通过 examples 中的原始十六进制向量。

2.1 共同接口语义

  • openSession(intent)：intent 区分登录、英雄领取、保存、读回验证、初始化。保存授权只属于当前会话／玩家，不在后台永久保留。
  • readTag()：返回标签句柄和能力；句柄失效后禁止复用旧会话进行写入。
  • readPlayerContainer()：从卡获取新鲜的完整数据，不用 OS 缓存代替写后验证。
  • queryWritableCapacity()：报告真正可写的 NDEF message 或应用文件容量；未知就是未知。
  • writePlayerContainer()：仅接受已经本机持久化、完成容量检查的冻结快照。
  • verifyPlayerContainer()：重新读取、解压、校验，再与待写版本比较。
  • closeSession()：撤销待写操作，释放读卡器；离开页面、后台或设备断开时执行。

同一读卡器一次只由一个游戏会话占用。UI、后台自动发现、保存流程不能各开一套互相竞争的 NFC 轮询。多张卡同时在场时拒绝写入，要求只放一张。

4.2 官方库存在的细粒度差异

核实时，M5Unit-RFID 的支持表列出 DESFire 2/4/8K 的 ISO-DEP 原始／文件访问，但同时指出 M5Dial 内置小天线不能可靠激活 NFC-B，NFC-B 应使用外接 Unit RFID2。因此项目共同玩家卡优先评估 NFC-A / Type 4；不能仅凭 Dial 产品页的 A/B 标注承诺所有 Type B 卡。H06

M5Unit-NFC 的部分共享示例将 Dial／RFID2 接入列为 detect-only，这不等于 M5Unit-RFID 自身没有读写能力。移植必须选对库与示例层，实际跑通读取、容量查询、完整写入和读回，而不是停在示例输出 UID。H05

库支持表也不能替代卡上应用权限配置。DESFire 等卡的文件尚未创建、密钥未知或文件只读时，ISO-DEP 通信成功仍不等于可以保存玩家数据。不得尝试格式化非本游戏初始化的未知卡。

4.3 Grove 与 USB 的边界

Grove 是接线生态，不是统一 NFC 命令。适配配置必须记录供电电压、I2C／UART、地址、波特率、引脚和时序。对软件 I2C 时序不满足驱动要求的板子，应更换硬件 I2C 路径或报告不支持，不能只延长 UI 超时掩盖底层错误。

ESP32 上的 USB-C 插口可能用于供电、下载、Serial/JTAG 或 USB OTG；是否能给外部 USB 读头提供 host 模式与 VBUS，必须按具体板级设计验证。v1 不把“有 USB-C”视作 USB CCID 即插即用保证。

4.4 本机存储和显示调度

本机玩家存档使用一个完整快照事务。可以选择经过验证的 NVS blob 日志、文件双副本，或可保证原子提交的存储层；不能分别写 wallet 和 day_ledger 两个键就宣称它们必然一起提交。驱动只有在数据已经满足本机持久化承诺后才返回成功。

NFC 读写、网络心跳和界面刷新分开调度。墨水屏刷新时不得阻塞网络超时或导致重复轮询领取。PaperMono 官方文档目前提醒特定 M5GFX 波形仍需谨慎，应采用当时官方推荐的 OTP／稳定刷新配置并实测；本规格不保证某个毫秒级刷新值。H01

Dial 至少始终可访问：双方分数、谁行动、谁已过牌、剩余手牌数、场上单位及效果详情、玩家卡是否已保存。旋钮翻页和详情弹层可以改变布局，不能使对手持续效果在小屏端不可查询。

5. Android 原生

5.1 内置 NFC

使用 android.nfc 发现标签，再按 Tag.getTechList() 选择 Ndef、IsoDep 或其他已实现技术。Android 官方将 MIFARE Classic 等支持列为可选；不能假设所有安卓机都能读任何 MIFARE 卡。D01

NDEF_SINGLE 实现顺序：

  1. 获取 NDEF 对象并连接；确认可写。
  2. 用 getMaxSize() 获取最大 NDEF message 字节数，比较完整编码后的消息。
  3. 调用 writeNdefMessage()。
  4. 使用 getNdefMessage() 重新从卡读取并验证；不能使用 getCachedNdefMessage() 作为写后读回。
  5. 关闭连接；处理 TagLostException、权限与 IO 错误。

上述 I/O 不放在主 UI 线程。官方 API 明确区分缓存数据与当前卡数据，写入 API 也可能因离场而失败。D02

RAW_DUAL 需要独立实现 ISO-DEP/APDU 与卡上文件协议，或对应卡型块访问。IsoDep.transceive() 是传输能力，不会自动完成 DESFire 认证、文件创建、容量推导或断电恢复。

5.2 USB 外接读头

Android USB host 负责枚举设备、申请用户授权和读写 endpoints；不是自动把所有 USB NFC 读头变成内置 NfcAdapter 的 tag。应用必须接入明确型号的厂商 SDK、已验证的 CCID 实现或 reader 专有协议。D03

支持名单必须记录手机是否有 USB host／OTG、连接线、读头 VID/PID、供电、驱动版本与可用协议。ACS 官方提供面向 USB host 的 Android 库和指定读头支持，可作为候选；仍需验证具体玩家卡与 NDEF／应用文件读写。D04 P03

内置 NFC 和 USB 读头共用 PlayerCardService；不得复制一套不同的每日领取规则。SQLite／Room 等本机存储实现必须把完整快照更新和 claim 幂等记录放在同一事务，事务提交失败不能只保留其中一半。

6. iOS / iPadOS 原生

6.1 首选 Core NFC 的内置读卡路径

Core NFC 官方提供 NDEF 读写与 ISO7816、ISO15693、FeliCa、MIFARE 等协议接口；是否可用仍要检查设备及 readingAvailable。SDK 中存在符号或 iPadOS availability，不等于每台 iPad 具有相应 NFC 硬件。A01

实现必须配置 NFC capability、必要 entitlement、NFCReaderUsageDescription。ISO7816 自定义应用访问需声明允许的 AID；标准 NDEF Type 4 路径与自定义应用文件路径分别适配。A03

NDEF 保存使用 queryNDEFStatus 获取可写状态与 message capacity，写入后再执行 readNDEF 并验证。系统写入回调无 error 并不代替本协议的完整读回校验。A02

6.2 刷卡交互与系统会话

iOS NFC 是受系统管理的会话，不把它模拟成永久后台读头。读取登录结束后，再点“保存到玩家卡”开启一次保存会话并重新贴卡。保存 intent 必须先于写操作；不能把登录的检测回调直接改成写卡调用。

发生后台切换、系统取消、超时或卡离场时，关闭会话并保持本机进度。未完成新鲜读回时停在待验证状态；可以另开明确的验证会话要求再贴一次卡。只有验证成功才显示可迁移。

6.3 USB、CCID、External Accessory 的真实边界

不能写成“iOS 完全不能接 USB 读卡器”。Apple 官方已说明 iOS 16／iPadOS 16.1 及以上对合规 CCID／NFC PIV 智能卡提供原生认证等支持；但这不自动保证游戏标签能经任意 USB NFC 读头完成读写。A05

可评估的外接路径分为：

  • 系统可枚举的智能卡槽 + CryptoTokenKit。核实目标 SDK availability 与 entitlement，确认 TKSmartCardSlotManager 能看到读头，并以 TKSmartCard 建立会话、发送 APDU；再验证实际标签、文件命令与供电。Apple 提供这些接口，但不能将 PIV 认证功能等同于全部自定义 NFC 标签协议都已适配。A06
  • 厂商明确支持的配件／SDK。以其 reader、iOS 版本与 API 为准。ACS 对特定型号列有 iOS APDU 工具，可以作为验证起点，不能据此扩展为所有 ACS 或所有 USB 卡机都支持。P03
  • External Accessory / MFi。这是针对受支持配件协议的框架，官方说明涉及 MFi 配件及厂商对第三方应用的授权；不是一个向所有 USB-C 设备开放的通用 USB API。A04
  • BLE／网络读头。仅在已经实现的协议和原生宿主中启用。BLE-only 配件不因连接 iPhone 就自动需要 MFi；也不因此自动与本游戏兼容。A07

v1 的默认 iPhone 用户路线仍是内置 Core NFC。外接路径在能力表中标为条件支持，未验收前 UI 不能宣称可完整保存。

7. Web

7.1 Android Chrome 的 Web NFC

Web NFC 的公开能力以 NDEF message 为中心，不支持通用 ISO-DEP、NFC-A/B/F 原始命令、P2P 或 HCE。需要安全上下文、用户手势与权限，且页面保持可见；手机锁屏／页面隐藏时不能按常驻读卡器设计。W01

因此纯 Web NFC 的 v1 合同是：

  • 支持发行 payload 为 NDEF 的英雄卡。
  • 支持 NDEF_SINGLE 玩家卡；不支持自定义 RAW 双槽应用文件。
  • 通过 NDEFReader feature detect 决定按钮是否可用；没有 API 就显示具体替代路径。
  • serialNumber 允许为空，且不能提供本规格的完整技术／UID 规范化保证；不得为空值临时生成 hero_card_id。W02
  • 接收未知网页 URL 记录不等于识别到游戏卡；必须解析本游戏 MIME／发行记录。

7.2 Web NFC 的容量与读回限制

Web NFC 标准接口没有对应原生 queryNDEFStatus／getMaxSize() 的通用容量查询方法。本项目只能在容量由已验收、预配置卡片 profile 或桥接层可靠提供时允许完整写卡；能力未知时返回 CARD_CAPACITY_UNKNOWN，转到原生／桥接初始化工具。不能从现有短消息长度推算标签最大容量，也不能先破坏性覆盖再把失败当容量探测。

原生工具预配置卡片时，可以关联一个精确的卡片 profile／文件布局供网页使用；这一配置必须对应实际可写 NDEF message 字节数，不能仅填写“8K 卡”。每次网页写入仍比较实际编码长度。

容量配置属于读头／卡片适配资料，不能仅凭 player_id 推断，因为同一玩家可以换不同容量的卡。若浏览器不能可靠绑定到已验证的物理卡或专用发行批次，默认允许读取但拒绝写入，使用原生或桥接路径完成保存。不要为了显示 Web“全功能”而假造一个容量值。

write() 成功后，新的 reading 数据必须确认为写后读取，不能拿写前缓存的事件验证。若浏览器无法立即提供可靠的新鲜读回，显示“已写入，移开再贴完成验证”，重新开启验证会话。只有读回 payload 与目标完全匹配才标记成功。

初始化网页／PWA 后可以离线运行已缓存的业务与内容。持久化使用 IndexedDB 的完整事务；应在 transaction complete 后才承诺本机提交。浏览器清站点数据、隐私模式或存储回收会影响本机持久性，因此界面要清楚显示是否已完成玩家卡保存；不得把浏览器缓存叫作已写入实体卡。

7.3 桌面 USB NFC：默认 PC/SC 本地桥接

普通网页的 WebUSB 不是所有 USB 设备的通行证。WebUSB 规范将 Smart Card 接口类 0x0B 列为 protected interface class；常见 CCID 读头不能作为普通网页的通用直接访问方案。W04

推荐桌面结构为：

游戏 Web UI → 本机桥接服务 → 系统 PC/SC／厂商驱动 → USB 读头 → 标签

这是一条实现路径，不是零安装承诺。Windows 使用 WinSCard，Linux 可使用 pcsc-lite，macOS 使用可用的系统智能卡接口／厂商驱动；实际卡命令仍由标签 profile 实现。P01 P02

本地桥接至少要做到：

  1. 默认只监听 loopback，限制允许的 UI origin，并使用一次配对令牌或同源会话；不向任意网页开放写卡。
  2. 推荐由桥接提供同源本地 UI；若远程 HTTPS 页面连接 loopback，必须实测浏览器的混合内容、Local Network Access 与权限策略，不能假定跨浏览器一致。
  3. 提供读卡器列表、能力报告、互斥会话、请求 ID、取消和有上限的消息长度。
  4. 同一次写入重试保持相同请求语义，并先读回判断是否已完成；不能把重试变成重复领取。
  5. 只有 PlayerCardService 明确请求保存时执行写入；后台 PC/SC 卡出现事件只做发现／读取。

Web Smart Card 是另一条专门路线。核实时官方 HOWTO 已说明 ChromeOS Chrome 143+、Smart Card Connector 与 Isolated Web Apps 的使用条件；它不能推广成所有桌面浏览器或普通网页已有通用 PC/SC。W05

7.4 Web + Grove / MCU 桥接

网页不能直接访问一根 Grove I2C 线。MCU 必须作为 NFC 主机，实现标签协议，再把受控读写能力通过 USB serial、受支持的 vendor USB、BLE 或局域网 API 暴露给客户端。

首选简单开发路线是桌面受支持浏览器的 Web Serial 或本地桥接连接 MCU；浏览器和 OS 支持要 runtime detect。若使用 WebUSB，接口必须符合浏览器允许的类别与驱动约束，不能依赖绕开 CCID 保护类。W06

MCU 桥接在返回保存成功前必须完成真实卡读回校验。浏览器不能仅因为串口收到 OK 就假定卡片内容可靠，除非这个 OK 的协议定义明确包含目标 snapshot_id 与验证后的 payload SHA-256。

8. 虚拟卡文件是默认开发入口

没有真机型号、SDK 或卡容量信息，不应阻塞规则、UI、保存状态机和跨平台对战开发。所有平台先接入 VirtualCardAdapter，读取同一组 fixtures：

  • NDEF profile：一份完整、可解析的 NDEF message 文件。
  • RAW profile：8192 字节逻辑卡映像，含两个 4096 字节槽。
  • 英雄卡：固定 payload／legacy UID 的输入事件。

设备本机存档与虚拟玩家卡文件必须分开。领取只更新 device store；只有显式保存事件才修改 cardfile。切换虚拟 device_id／清空第二台设备 store，再从 cardfile 登录，应准确复现“未写卡不能迁移”。

虚拟驱动应能注入：只读、容量不足、卡移开、部分写入、读回不匹配、无有效时钟、重复发现、两张卡在场、不同谱系。测试通过只能证明业务和容器逻辑，不能宣称射频读写、系统权限、掉电可靠性或苹果配件认证已经完成。

06 · 版本与兼容策略

目标：独立开发的 ESP32、Android、iOS、macOS、Windows、Linux、Web 客户端可以共享同一场对战；增加设备、展示或卡片时，不把所有现存设备一起变成不可用。本文定义发布与升级契约，不表示每个客户端已实现全部功能。

1. 五个版本轴，内容另用精确哈希锁定

不要用一个“App v2”决定所有兼容性。以下版本轴独立变化：

轴 示例 由谁判断兼容 变化规则
应用版本 app_version 0.1.0 平台发布器/安全策略 可修UI、驱动和功耗，不自动改变战斗规则
线路协议 protocol_version 1.0 HELLO/CAPS 明确协商双方实现的相同版本；基线PCG/1.0
规则契约 rule_id / 状态 ruleset_id pcg.core.v1 引擎与SELECT/READY 语义不可变；新行为需新ID或明确的新规则扩展
保存格式 save_schema_version 已发布存档schema规定的整数版本 存档读取器/迁移器 旧程序不能直接改写未来格式；备份并显式迁移
实体卡格式 container_version / hero_schema_version 已发布卡片schema规定的版本 CardReader/卡片解析器 能读NFC不代表理解卡片内容；未知格式不猜测

内容另有 content_pack_id（例如 m5.core.v1）、content_version（发布标签）和 content_hash（精确规则内容的SHA-256）。version便于人读，hash用于证明双方装载了同一份规则材料。改了卡片数值或合法排位，即使还叫同一个模板名，也不能继续用原hash。

PCG-F1 的 frame_version=1 只是数据报封装版本。它不同于 PCG envelope 1.0，也不同于 ESP-NOW 硬件/SDK所谓的 v1/v2；禁止把这几个“1”当作同一含义。

保存/实体卡文档如果使用带命名空间的实际版本字段，以它们的schema为准；本表表达独立的生命周期，不要求把两个版本字段硬塞进战斗envelope。

2. 一场对战的兼容判定

能一起开局须同时满足：

  1. 双方通过认证连接到同一个AuthorityAdapter；已协商的PCG版本相同。
  2. SELECT指定的规则ID被客户端实际实现，且实现通过该规则ID的golden fixtures。
  3. 客户端已验证本地内容包，对SELECT的content_hash作精确一致比较。只比较pack名、版本字符串或拥有某张NFC卡不够。
  4. SELECT的每个required_feature与required_opcode都存在于客户端能力集（trait以trait:前缀纳入opcode数组）；所有选定卡片满足内容schema和该引擎的约束。
  5. 客户端在 READY 中回显同一个 selection、rule 与 content_hash，并提交有顺序的 deck_template_ids[10]。authority 按房间允许池与规则验证每人的牌组；所有牌组有效且最后一个玩家 READY 之前，不能开始。

如下情况可以互战：M5Dial App0.1.0与iPhone App0.8.0都实现PCG1.0、pcg.core.v1和同一content_hash。反过来，两台都显示App0.8.0但加载了不同数值包，仍不能进入同局。

can_start = authenticated
         AND same_selected_wire_version
         AND exact_rule_id_supported
         AND exact_content_hash_loaded
         AND all_required_features_supported
         AND all_required_opcodes_supported
         AND all_submitted_decks_valid
         AND all_players_ready_for_same_selection

这不是客户端自由裁决的布尔值；authority必须最终检查所有已认证玩家的READY。客户端也必须本地验证，不能盲目相信房主写来的“compatible=true”。

3.1 展示更新不能伪装成规则更新

展示字段只能出现在明确的presentation或资源分支中。新客户端可以理解更多纯展示字段；旧客户端忽略它们时，合法动作、随机流程、分数、目标、出牌次数和结果必须完全一样。

content_hash计算范围由内容包规格规定，wire层不另发明第二种hash算法。只有内容规格明确排除的展示资源可以独立更换而不改hash；如果某个展示字段仍位于被hash的manifest范围，修改它也必须产生新hash。发布器不能“认为只是头像”就继续冒用旧散列值。

3.2 新卡能否热加载

符合以下全部条件，新卡可以走数据包热加载，而不要求刷全部固件：

  • 卡包schema被客户端支持；数值/长度/枚举都在基线界限内。
  • 效果只用客户端已经实现且通过测试的opcode与参数结构。
  • 包中没有脚本、远程执行表达式、动态原生代码或未知强制语义。
  • 卡包按规格验证hash与发布来源；验证通过后以不可变文件/记录安装。
  • 内存、完整snapshot大小、实例数和JSON深度仍在PCG/1.0上限内。
  • 仅在新局或未开局的新SELECT后启用，不在一局中途替换。

能识别template_id、能画卡面、能显示effect说明，三者都不能替代opcode支持。若新牌包含未实现的效果，旧客户端可在收藏图鉴里以“暂不支持对战”显示纯展示信息；不得把它当作无效果牌出场。

4. 保留一个稳定的基础模式

每个发布周期 SHOULD 保留pcg.core.v1实现、受支持的基础内容manifest及对应golden fixtures。更新包可以增加模式，不必替换已有core引擎。资源紧张的ESP32可以只装core与少量已验证包；手机/Web可同时支持多个规则，但具体每局只能锁定一个。

界面建议区分“可对战”和“需要新能力”，而不是看应用版本是否最新。创建房间时列出实际共同支持的规则/卡包；缺新内容的朋友可以选择大家都有的旧基础包。若没有共同受支持规则，就明确说明所缺ID/效果能力，不能自动把不同卡改成近似效果。

旧内容manifest是复盘、重连、存档和排查问题的依据，SHOULD 保留只读副本。若服务因安全或严重规则问题禁用某个旧hash，应同时保留其解释材料用于历史查看；不要把旧记录指向修正后的新数值。

每个已开始的match至少固定：match_id、规则ID、内容hash、内容包标识、参与者、初始完整状态/必要种子、动作日志与结果日志。种子及完整状态仅由authority保存，不下发对手。重放使用原规则与原manifest，不按“今日最新牌面”重新计算旧比赛。

5. 不允许悄悄变化的契约

5.1 相同ID意味着相同语义

以下改变不能继续假称原来的规则ID：回合顺序、通过后是否还能出牌、结算时机、平局处理、稳定/护盾优先级、目标合法性、随机算法、实例ID生成方式、动作revision增长方式。修复实现使其回到已经冻结的规范属于应用修复；改变规范本身则属于新规则契约。

同一个content_hash不能对应两份不同规则材料。SHA256是内容一致性标识，不是发布者签名或身份认证；客户端需要通过可信发布通路/已有签名机制确认来源。校验hash不意味着可以执行任意来源的代码。

5.2 协议的向前兼容有范围

PCG1.0已知消息使用封闭schema，未知规则字段按错误处理，避免target_instance_id拼错仍被当作无目标。只有presentation内未知字段和明确可省略的X_*消息可忽略。

后来增加的新必需能力必须在HELLO/SELECT中显式协商。服务器不得给旧客户端发新字段并寄望它“忽略也差不多”。若新消息是可省略展示消息，用X_*；若缺它会改变玩法、身份、安全或持久化行为，它就不是optional。

wire minor版本的新增能力也必须取双方实际实现的交集，不能仅因主版本都为1就按最新版解析。每条消息的protocol_version等于本session已协商的版本，禁止混发。

6. 存档读写和迁移

旧应用不得把未知未来save读成空收藏后覆盖。存档读取采用如下策略：

存档情况 允许行为 禁止行为
schema已支持，规则/内容已安装 正常读写、启动该规则的离线模式 自动切换到新hash重新计算
schema已支持，缺旧内容包 保留数据并提示安装该hash的包；展示已知元数据 用“相同名字”的最新卡包顶替
schema比客户端新 保留原始文件；只读已明确可解析的安全元数据，或明确拒绝打开 去掉未知字段再保存、初始化成新空档
老schema且有已验证迁移器 先备份，迁移到新副本，验证成功后原子切换 边解析边原地覆盖；失败后丢弃旧档
hash/校验失败或内容损坏 隔离损坏副本、提供恢复/重新获取路径 静默把未知值变成0或无效果牌

迁移器 MUST 是版本对版本的确定过程，并记录from/to版本、原文件摘要、完成状态。应保留原始备份、验证新文件schema与引用内容，然后原子替换指针。写入中断后只能看到完整旧档或完整新档。降级应用可以继续读其认识的旧档副本；不得把未来档“降级保存”而删除它不认识的内容。

账号云存档的并发冲突必须由存档服务版本号/ETag或等价控制处理；PCG对战的revision不是账号收藏档的revision。不能因为最后一次联网较晚，就用旧设备的空列表覆盖服务器收藏。

进行中的match恢复要求原规则、原hash和原裁判日志仍可用。没有这些材料就明确拒绝恢复；显示历史摘要可以，但不可编造同一match的延续结果。

7. 实体NFC卡兼容

CardReaderAdapter负责从设备可用读卡器读取字节；CardParser负责验证玩家卡 container_version／英雄卡 hero_schema_version 和内容。新增读卡器驱动不必改变规则；新增卡格式也不能强迫已发行旧卡报废。

兼容客户端 SHOULD 继续支持已发布的基础英雄卡格式。它可以把实体卡映射到同一template/个人收藏条目，再由当前房间选择的内容包解释战斗值。卡上的展示名、旧印刷数值和设备本地缓存都不能覆盖authority已经锁定的manifest。

未知卡格式、未知必需字段或不支持的身份机制，应提示具体能力缺口，并保留可安全显示的卡面信息。不要仅凭读到了UID，就把卡认作可信授权、生成永久资产或把未知效果默认为none。原始UID与身份证明不得随battle COMMAND或对手snapshot传播。

将卡面展示资源与规则模板分离，有利于同一实体卡跨多个内容版本继续使用；版本选择必须在房间中明确。收藏身份变化和转移按卡片/所有权规格处理，不由battle协议猜测。

8. 哪些情况才要求升级

可以要求升级的范围应尽量是具体服务或模式：

  • 修复认证、密钥处理、数据损坏等已知安全问题，当前在线服务不能安全继续接受该版本。
  • 用户选择的模式确实需要客户端没有实现的必需协议能力、opcode或save/card格式。
  • 服务明确停止支持某个已存在的线路版本，并给出可验证的替代支持信息。

仅因有新头像、更多设备适配、某人装了新版本，或运营想统一版本号，不应阻止旧基础模式。在线服务拒绝旧客户端时，旧应用仍可使用自己已支持、已保存且有效的离线规则/卡包和旧存档；不能为了逼在线更新而擦除它们。也不能承诺未来所有系统平台永远允许安装旧应用；这是平台生命周期，和游戏自己的版本拒绝策略不同。

用户取消升级后，应保留当前档案与卡片数据。无法玩新模式时显示所缺能力及能继续玩的模式。不能用“可能不兼容”替代明确的required_feature/opcode/schema原因。

9. 给独立AI coding agent的发布要求

每个平台实现者交付时必须声明：

  1. app/platform版本、支持的PCG线路版本、PCG-F1或流式Adapter情况。
  2. 实现的rule_id、required opcode/trait集合、可加载的内容schema范围与实际manifest hash。

  4. 对本项目共同golden fixtures、canonical JSON字节向量、二进制帧向量和错误案例的测试结果。
  5. 明确的认证/authority模式：本地可信房主或专用服务；不要用硬件名称替代安全与兼容声明。

08 · 开发代理实施契约与所需材料

1. 输出结构与责任分层

语言/框架由目标平台决定，概念模块必须保留清楚边界：RulesEngine、ContentLoader、PlayerStore、ClaimService、CardReaderAdapter、CardCodec、TimeProvider、AuthorityAdapter、TransportAdapter、LobbyAdapter、ViewModel/UI。允许同仓库不同目录；不强制某一种“万能框架”。

  • RulesEngine：完整状态与命令到下一状态，整数和稳定顺序；核心逻辑无 IO。
  • PlayerStore：本地事务、快照祖先索引、冲突备份、pending export、幂等操作 ID。
  • ClaimService：按日去重、确定性抽样、原子收藏/钱包变更，不直接渲染。
  • CardReaderAdapter：探测能力、读写物理介质、取消/移开/错误；不决定胜负或发奖。
  • CardCodec：PCSV/NDEF/UID 标准化；不把 unknown 当 blank。
  • Authority：认证身份到 seat、规则调用、持久幂等日志、按观看者过滤。
  • Transport/Lobby：发现、认证、字节完整交付、重连；不重写游戏动作。
  • UI：完整呈现可见状态、显式本地/卡保存状态；只提交意图。

2. 开发顺序

阶段 A：工程与兼容性探测

读目标配置和现有代码；核实真实板卡/读卡器/SDK。列出 supported / unsupported / untested 能力。保留现有用户文件，不能用“简化”理由重建覆盖工程。锁定依赖版本和构建方式。固件项目说明板型、分区、flash/PSRAM、Grove 引脚和供电；无材料不能编造引脚。

阶段 B：先完成可验证规则

移植 core v1 reducer 与 canonical 编码；加载同一 JSON 卡包。运行黄金向量，输出每一步 state hash、view hash。实现合法命令枚举与不读敌方隐藏手牌的教学 AI。先完成本地一整场，不从漂亮首页开始宣布完成。

阶段 C：完整本地玩家流程

实现持久化、玩家登录选择、收藏与两类英雄卡、游戏日、重复奖励、外观兑换、显式导出、容量预检和恢复。先用 MockReader 自动复现拔卡/满卡，再接真实 ReaderAdapter。MockReader UI 显示模拟标签，不伪装为实物。

阶段 D：互操作联机

有 IP 能力的目标接通 docs/12 的房间服务与 docs/04 协议；RF-only 目标可经实际桥接进入同一 authority，或按已定义配对的本地裁判 profile 互战，不把 JSON 相同等同于射频原生互通。无现成服务则附一个可运行的参考 authority（例如 Python/Node/Rust 任一适合环境的实现）。同一客户端开两个浏览器只是起点；必须给目标客户端和参考客户端对战脚本。加入丢包/重复/恢复，核对 privacy 和持久事务。

阶段 E：平台体验与交付

针对圆屏、电子纸、触屏与桌面输入调整界面；保留同样规则和完整信息。测核心流程、失败路径与资源上限。交付命令、源码、配置、测试报告和可复现截图/日志。没有设备时交付构建与 mock 测试结果，以及真实硬件待测清单，继续完成可做部分。

3. 状态与数据落盘建议

ESP32 可使用 LittleFS 文件与原子重命名/双记录 journal；Android/iOS/桌面可用 SQLite 事务；Web 可用 IndexedDB 单事务。具体库可选择，语义不可改变。对 flash 高频写入做去抖和事务批处理，但领取成功/出牌 accepted 前的必要提交不能延迟到“以后有空”。不要在每次 NFC polling 和每帧渲染时写 flash。

本地 profile record 至少包含：active snapshot、其 hash、祖先 ID 索引、最后一次从该玩家卡读到的 snapshot_id、最后验证导出的 snapshot_id/hash、pending export、冲突备份、读卡能力与错误日志。设备元数据不写入可携带 snapshot 的 hash；不能把连接 token 或服务器私钥塞入玩家卡。

4. 旧工程迁移

如果现有“RPG+宝可梦+卡片”工程存在：保留可复用的驱动、UI 外壳、角色图和用户数据。把旧战斗实现隔离为 legacy 模式；不能把 HP/经验加成偷偷带入 core v1。旧存档必须先给出字段样本和映射表才能迁移，不靠猜测重命名字段。迁移只建新备份与新快照，验证通过后再允许明确写卡；原始备份保留。

若旧模式仍需互战，使用不同 ruleset/protocol entry，不允许它自报 pcg.core.v1。用户说“兼容旧版”不意味着两个不同胜负算法能打同一局。

09 · 教学、试玩、规则验收与跨端检查

本章分清两类工作：规则验收用于判断“实现是否正确”，试玩用于判断“玩家是否觉得有趣”。通过哈希一致性测试不等于游戏好玩；玩家喜欢角色外观也不能替代规则一致性。

默认内容为 standard14：12 种角色 + 2 张通用战术均可免费借用。教学预设 10 张为 8 个角色 + 2 张战术。基础分、排位和效果以正式卡包为准；本章数字依据 content/core_pack.json；核心教学分支已用 reference/battle.py 复算。

本次文档核对已复算的结果：PASS 省牌题 16:19、余牌 7:5；部署顺序题 9 分／7 分；目标分支题 7:6／7:8；两次减分经过一次防护后为 6:3。这是参考实现的数值核对，不代表硬件驱动、真实联网或整套用户试玩已经完成。

1. 首次体验的完成定义

新玩家不读完整规则、不拥有实体英雄卡、不购买任何硬件角色，也能：

  1. 使用免费教学牌组开始 AI 对战。
  2. 看懂双方战力、手牌数和每局 5 张投入上限。
  3. 完成一次数字选牌、排位、目标和确认。
  4. 说出 PASS 的含义：本小局不再出牌，未出的牌留下。
  5. 在一个示例中理解“赢下小局可能多花牌，但多留牌也不等于稳赢整场”。
  6. 打完一场最多三小局的比赛。
  7. 在有读卡器的设备上，知道玩家卡和英雄卡用途不同。

默认先教对战，再介绍收藏领取。若用户主动选择“我想先刷卡”，可以进入抽卡教学，但不能要求完成领取才能开始对战。

2. 教学结构与时长假设

教学采用可跳过的小步骤，不在每次开局重复。以下时间是设计目标，待真实使用验证：

阶段 学习目标 建议目标时长 必需性
A · 认识数字 战力、投入、余牌、局积分互不混淆 30–60 秒 首次出现一次，可跳过
B · 两张牌的顺序 同样的牌，不同部署顺序可得不同分数 1–2 分钟 推荐
C · 目标与特性 增分、减分、防护、稳定、战术计投入 2–3 分钟 推荐，可分关完成
D · PASS 与省牌 用当前小局交换后续手牌资源 1–2 分钟 核心关
E · 一场练习 没有提示强迫的完整 AI 比赛 约 5–10 分钟 核心体验
F · 双 NFC 卡 登录、领取、保存与纯数字战斗 1–2 分钟＋实际读写 有硬件时可选
G · 找朋友 同规则跨设备同步对战 按环境 MVP 联网验收

最小首发可只做 A、D 的短引导和完整 E；B、C 可通过可重玩的训练题交付。不要因为完整教程插画未完成而推迟可玩的核心。

3. 教学必须调用真实引擎

3.1 不允许另写一套演出规则

教程可以限定玩家当前可选择的学习项、脚本控制 AI、展示预告和重开同一题，但所有接受后的行动都必须经过正式 reducer。不能让教学关的旋钮 永远 +2、让战术免费出，或用动画直接改总分。

每个教学练习使用正常的合法 10 张牌组。没有教学需要的其他牌可以被提示层暂时收起，但不能把它们从引擎手牌删除后仍声称是在标准对战。处于教学限制时页面标明“练习题”，结束后恢复完整自由选择。

教程重试建立新的受控练习状态；不是对真人已接受操作提供撤销。双设备对战中不能因进入教程界面回滚之前的一手。

3.2 训练题与完整对局的区别

训练题可以在完成本题目标后停止，并解释“你已完成这道练习”；不要伪造整场胜利或发放竞技胜场。完整 AI 练习必须按三小局积分规则走到真实终局。

教程里明确展示的 AI 预告属于教学脚本。普通真人对战只展示对方已经提交的行动，不应展示对方本地选牌过程。

4. 阶段 A：看懂局面与数字出牌

4.1 初始页面

显示双方 0 战力、双方 10 张手牌、双方投入 0/5、局积分 0:0、第 1/3 局。只用一句话说明：“本局比战力；整场还要把牌留给后面的局。”

让玩家通过数字手牌选择探子 到前排，再确认。

预期：己方战力为 4；手牌为 9；本局投入为 1/5；场上 1 个前排单位；局积分仍为 0。不要因一张牌超过对手就马上增加局积分。

4.2 取消练习

再次打开任意手牌，选排位后按返回，回到战场。预期以上所有数字不变，不出现公开“出了又撤回”的日志，不向对手传送候选牌。

如果玩家在旋钮屏按下一次短按就直接出掉了牌，或长按返回意外触发了 PASS，则属于交互错误；不应把它归因于玩家“不熟悉操作”。

5. 阶段 B：同两张牌，9 分或 7 分

此题可使用默认教学牌组。脚本对手在空场先 PASS，玩家可以连续投入两张牌。其他手牌保留，只是教程先聚焦这两张。

路线一：先探子，后旋钮

动作 计算 己方场上战力
探子 → front 探子基础分 4 4
旋钮 → rear 旋钮基础 3；另一排已有探子，立即 +2 9

结束说明：“先有前排，再放后排的旋钮，获得一次 +2。”

路线二：先旋钮，后探子

动作 计算 己方场上战力
旋钮 → rear 另一排为空，只得基础分 3 3
探子 → front 探子 4；旋钮不补发过去的入场效果 7

两条路线投入都是 2 张、余牌都是 8 张，差异只有入场顺序。练习完成后让玩家用自己的话选一句：“以后再放另一排，不会补发 Dial 的入场奖励。”

此题不要展示 2 点生命伤害、能量消耗或回合充能；那些都不属于当前玩法。

6. 阶段 C：选择目标、战术与特性

6.1 增益和减分练习

双方用默认牌组，A 先手：

顺序 行动 A 战力 B 战力 需要展示的理由
1 A：探子 → front 4 0 一个 4 分单位
2 B：PaperMono → rear 4 5 stable 单位
3 A：帮腔 → rear，BOOST 指向探子 9 5 帮腔身体 3；探子 4→6
4 B：敲键 → rear，DAMAGE 指向探子 7 8 探子 6→4；敲键身体 3

此时 A 选择“压一下”：

  • 选择 B 的 Cardputer：其 3→1，B 总战力 8→6；A 保持 7，因此场上暂时领先 7:6。
  • 选择 B 的 PaperMono：stable 抵消减分，B 仍为 8；这张战术仍然被消耗，A 暂时落后 7:8。

两条分支都是合法动作。教程应先让玩家看到确认预览，再决定；不能把 stable 目标在规则层判成非法来掩盖真实规则。

无论分支如何，A 此时都已投入 3 张、手牌 7 张，但场上只有探子和帮腔 两个单位；压一下已在弃牌区。要求玩家回答：“战术也占一次投入吗？”答案为“占”。

6.2 防护练习

双方使用默认牌组，A 先手：

顺序 行动 A 战力 B 战力 防护状态
1 A：Stamp → front 4 0 Stamp 有 1 次防护
2 B：敲键 → rear，DAMAGE 指向 Stamp 4 3 防护被消耗；本次未减分
3 A：探子 → front 8 3 立岗不会自动恢复防护
4 B：压一下 → 立岗 6 3 立岗 4→2；不退场

完成说明：“第一次挡住了，第二次会减分。防护保护自己一次，不保护整排。”

6.3 无目标的区别

己方场地为空时：

  • 帮腔作为单位可以进入后排，获得自身 3 分，BOOST 效果略过。
  • 加一把作为战术没有己方单位目标，不能打出。

敌方场地为空时：

  • Cardputer 作为单位可以进入后排，获得自身 3 分，DAMAGE 效果略过。
  • 压一下没有敌方单位目标，不能打出。

界面必须解释为什么，不应让玩家把战术拖到场上后静默无反应。只有无目标的战术留在手里时，PASS 仍然可用。

7. 阶段 D：用一局换两张牌

7.1 精确行动脚本

双方默认教学牌组、各 10 张牌；B 先手。脚本与 01_GAMEPLAY.md 保持一致：

顺序 行动 A 战力 B 战力 A／B 投入
1 B：探子 → front 0 4 0／1
2 A：厚壳 → front 6 4 1／1
3 B：细条 → rear 6 8 1／2
4 A：PaperMono → rear 11 8 2／2
5 B：加一把 → 自己的探子 11 10 2／3
6 A：旋钮 → rear；另一排有厚壳，自身 +2 16 10 3／3
7 B：Stamp → front 16 14 3／4

停在这里，让玩家选择：继续出牌，或停止本小局。

选 PASS 的示例后续：B 打帮腔 到后排，给探子 +2，B 从 14 变为 19。B 这是第 5 次投入，自动 PASS；双方均 PASS，立即结算。

结果：本小局 A 16、B 19；局积分 A 0、B 2；A 剩 7 张手牌，B 剩 5 张；下一局 B 先手。

7.2 复盘必须承认代价

解释：“你少用了两张，但输了第一局。对手再赢一局就能拿下整场；你需要争取后两局。”

不能解释成“PASS 是唯一正确答案”或“你现在有两张牌差，所以已经稳赢”。玩家也可能选择投入第 4 张，迫使 B 不愿继续；真正策略取决于余牌质量与后续目标。

7.3 额外分支的展示方式

允许在独立练习中从同一历史节点重试，比较“继续”和“PASS”的后果。比较页至少同时显示：本局胜负、各自用了几张、剩几张、局积分，以及下一局先手。

不要只比较本局最后比分，因为那会教用户永远把手牌投入到最大值。也不要只比较余牌数，因为那会教用户无条件让出第一局。

8. 阶段 E：完整 AI 对局

8.1 默认体验

  • 使用默认免费 10 张，允许玩家在开始前查看所有 14 个模板。
  • 不强制登录玩家卡，不要求实体英雄卡持续在场。
  • 第一场可给一次 PASS 提示、一次第五次投入提示；关闭提示后不再每手弹窗。
  • AI 使用自己的观察视图，不读取玩家私有手牌。
  • 结果页给出 2–3 条事实复盘，例如“第二局你先 PASS，保留了 4 张进入最后一局”。不要凭单局结果给出没有依据的“最优策略评分”。

8.2 AI 最低可接受行为

  1. 能选择合法目标，不用无目标战术卡死。
  2. 对手 PASS 后，如果可以用 1 张取得严格领先，不会无理由连续打出 3 张。
  3. 能识别本局必须争胜的情形，而不是始终机械在第 3 张后 PASS。
  4. 能在不同局面保留高分牌、投入较低分牌；不能每局按基础分从大到小出。
  5. 不对 stable 使用减分作为常规最优选择，除非它在合法行动中确实选择接受浪费或无更有意义的收益。
  6. 不偷改牌组、基础分、投入上限、对手已选动作。
  7. 相同 AI seed 与相同观察序列得到可重现的决策，方便诊断；正常游戏允许每场选不同 seed。

默认难度应让玩家能理解 AI 的行动。首版不需要实现复杂搜索才可测试乐趣；但仅按随机合法动作出牌的 AI 不能被当成已经验证了单人体验。

9. 阶段 F：双 NFC 教学

9.1 不混淆两个卡种

展示两张示意卡的文字用途：

  • 玩家卡：“我是谁，以及我保存过的进度。”
  • 英雄卡：“领取一个角色收藏；不是每手都必须拿出来。”

对卡片形状相似或无印刷标签的情况，应用应先读类型再显示用途，不凭颜色或卡背图案猜类别。

9.2 玩家卡登录与保存

  1. 在首页使用玩家卡进入资料。
  2. 展示当前玩家与保存状态。
  3. 完成一项实际进度变化后，明确选择“保存到玩家卡”。
  4. 写入并读回验证后再展示成功。
  5. 在另一设备读取该卡，按存档契约选择已验证的版本，确认恢复的是实际写入的进度。

若没有执行完整写卡，不应告诉玩家另一台离线设备已经能拿到本机最新收藏。跨端联网互战也不自动代表玩家进度已云同步。

9.3 英雄卡领取

  1. 已登录后进入抽卡大厅。
  2. 刷一张英雄卡，确认当前玩家、卡种和领取资格。
  3. 确认领取，只有原子持久化成功后展示收藏／碎片结果。
  4. 再刷同一张：显示当天已领，收藏和钱包不再次增加。
  5. 换另一个玩家：各自拥有自己的每日资格；不在物理英雄卡上写一个全球“今天所有人都用完了”的标记。
  6. 同模板重复获取只更新该模板的一条个人收藏记录的 draw_count 和碎片；不增加可重复携带数量。

9.4 证明战斗独立于实体卡

把全部英雄卡放到一边，仅保留数字界面，完成一次合法选牌、一次效果和整场结束。然后在另一个回合试扫英雄卡：只定位数字手牌，不扣抽卡次数、不增加收藏、不补手牌。

若完成这一步仍要求每手扫码，或者对战中刷卡触发盲盒，应判为实现不符合需求。

10.1 第五次投入的一个容易误测之处

如果对手早已 PASS，第五次投入可能立即结束本小局并进入下一小局。此时新的第一个行动当然可以再出牌。测试不得把“整场第六张牌”误认为“同一小局第六张牌”。

正确测试应检查小局的已投入上限、自动 PASS 事件、状态版本、行动方和局数。旧确认页面必须因版本更新失效；新的下一局页面可以正常出牌。

10.2 不用穷举替代关键边界

优先实现上述关键路径和跨语言 golden vectors。随机有效行动生成可以作为补充，用于检查数量守恒、终止和分数一致性；不需要为了视觉小改动重新运行大规模随机压力测试。

13. 跨设备互操作验收

13.1 MVP 范围

必需的是 AI 模式和两台不同实现连接到同一裁判进行同步对战。最低演示应选两种前端，例如 Web 与 Dial，或 Web 与 PaperMono。实际未持有的硬件必须标“未实测”，不能用模拟器截图宣称已经通过。

同机 hotseat、异步 profile、不同无线桥接可以后续做，不作为每个 ESP32 实现的首版强制清单。但协议恢复和重复消息正确性应从同步联网阶段就做。

13.2 推荐配对矩阵

配对 用途 至少检查

Web ↔︎ PaperMono 类墨水屏 普通屏与慢刷新显示等价 结算后最终分数、残影清理不重放行动
Dial ↔︎ PaperMono 两个硬件客户端直接互战体验 当前行动方、同一局积分、数字手牌完整可用
Android ↔︎ iOS／Web 不同移动运行时 规则内容版本、私有手牌过滤、恢复

是否通过 Wi-Fi、互联网、ESP-NOW 或桥接进入同一裁判，按适配与协议文档实现；相同 JSON 不能让不兼容的射频硬件自动互联。

13.3 同一行动脚本的对照

用阶段 D 的完整 9 步脚本在不同端逐步提交并核对。每次收到的最新 view 应具有一致的公开战力、当前投入和余牌数量，round_results 的小局比分／积分必须一致。各自手牌是私有视图，因此双方 view_hash 可以不同；不能要求 A、B 的私有快照哈希相同，更不能为了凑成相同哈希而广播双方完整手牌。客户端跨过结算直接收到下一局快照时，不要求还原未收到的终盘场地。

裁判完整规则状态可在本地测试中与 golden fixture 比较；各客户端恢复能力按当前协议与过滤视图校验。完整回放只作为裁判端本地日志的可选验收，不把缺少完整历史交付判为客户端不合格，也不为此扩展 SNAPSHOT。

13.4 故障插入

至少覆盖这些事件边界：

  • 用户确认前断线：不应出现已出牌结果。
  • 裁判已接受、返回包丢失：恢复后只出现一次卡片和一次效果。
  • 第五次投入时断线：恢复到已结算或当前可行动状态，不要求手动补 PASS。
  • 本局双方 PASS 后服务器先结算、客户端尚未渲染：结果页从 round_results 显示真实比分／积分，恢复最新 view，下一局先手正确；没有终盘事件时不编造布局或投入明细。
  • 客户端跨过多个行动或一次结算后重连：必需恢复可信比分和本人的最新 view，不承诺完整回放恢复；手牌变化只有记录充分时才展示。
  • 失联进入暂停：不自动 PASS、不自动判负，不修改战斗 revision；明确关闭房间只标记 aborted，不生成竞技胜负或 points 终局。
  • 墨水屏整屏清理、屏幕睡眠、前端刷新：不改变任何规则状态。
  • 读取同一实体英雄卡连续重复回调：不重复领取、不重复出牌。
  • 双方内容包不一致：在准备前阻止开局，而不是打到一半出现不同效果。
  • AI 与真人客户端的观察对象：确认不含对手未公开手牌。

14. 小样试玩：先判断缺的是什么

14.1 第一轮招募与玩法验证

建议找 8–12 位目标用户：一部分熟悉卡牌游戏，一部分主要喜欢 M5／实体卡。每人先进行一场简短教学，再自由打两场；其中一场不展示抽卡、经验、碎片和每日奖励入口。

人数用于发现明显问题，不用于宣称统计上已经证明平衡。可以先用网页／纸牌原型验证选择，再在 Dial 和 PaperMono 上验证输入；不要先把所有硬件驱动写完才第一次看别人玩。

14.2 主持人脚本

开始前只说：“每人 10 张牌，用这些牌争最多三局。你也可以选择本局不继续出。”

第一次观察尽量不提供策略指导。玩家问操作问题时记录问题点，再按当前 UI 文案回答；不要替玩家选择最优牌。完整一场后问：

  1. “哪一手你最犹豫？你在比较什么？”
  2. “你有没有故意让出一局？为什么？”
  3. “如果再打一场，你会改变哪一手？”
  4. “没有抽卡奖励，你愿意现在再来一场吗？”
  5. “实体卡哪一次让你觉得有用？哪一次只是多一道操作？”
  6. “这台设备有没有让你因为误操作而输，或者不知道现在轮到谁？”

避免问“你觉得这个功能是不是很好玩”之类暗示答案的问题。

14.3 观察记录

以下为研究记录概念，不是另加一套网络协议字段：

  • 使用的设备、输入方式、规则／内容版本、是否完成教程。
  • 对局时长、小局数、各局最终战力、投入、余牌与 PASS 时点。
  • 选择取消次数、误提交次数、误 PASS 次数、非法目标困惑点。
  • 需要主持人解释的 UI 文案。
  • 玩家说出的关键选择与下一场改变。
  • 是否自愿开始无奖励的下一场。
  • 数字手牌操作次数与可选 NFC 定位次数；对战误触发领取次数必须为 0。

逐局投入和 PASS 时点可由观察者现场记录，或从可选裁判本地日志取得；客户端没有收到的历史应标为缺失，不从最终快照猜测补齐。日志只收集与诊断有关的信息；不要把玩家卡原始内容、NFC 原始凭据、私有存档或隐藏手牌自动上传成公开分析日志。

有复玩意愿 8–12 人中，至少一半愿意立即无奖励再来一场，作为早期方向信号 先问缺的是选择、惊喜还是节奏，不先加奖励
单人可玩 AI 会保牌、最小追分，玩家能解释其行动 AI 评价函数与合法行动观察接口
跨端信息等价 所有平台都能在提交前看懂相同后果 小屏分步页、详情和预览，而非只改字体
第三局不常机械清空 记录“只剩无条件算术”对局比例，结合玩家抱怨判断 5 次上限与现有小效果，不立即叠加新资源
NFC 有实际作用 玩家理解登录／领取／保存，且数字战斗不断档 场景路由、卡册归属、减少无意义扫码

15.1 先后手与数值检查

先看真实对局轨迹，再做足量平衡统计。几十场内的胜率偏差很可能混合了玩家熟练度和设备使用经验；不能仅凭“先手赢了 55%”就断言规则稳定。

可以交换双方先后手、使用相同牌组和近似水平多次比赛，记录：首局先手胜率、第一局获胜者最终胜率、第一局故意 PASS 的成功率、两张战术的选择率、入场增分兑现率、被迫无收益出牌率。

任何永久排除的模板都值得检查。尤其零基础分战术如果在自由构筑中从不被选，应调整已批准的内容设计或承认其只用于教学；不要以隐藏额外能力在某一平台补强。

15.2 与旧 RPG 版本比较

如果能访问旧版，只比较可观察的体验：

  • 玩家在没有升级奖励时愿不愿意重复对战。
  • 每局是否能指出有后果的选择。
  • 用同一张角色卡，是否因时机／排位不同得到不同结果。
  • 跨设备操作是否更容易理解。

不要预设旧版失败一定因为 RPG。问题也可能来自 AI、节奏、反馈或没有清楚的目标；新玩法应通过实际游玩证明改善。

16. 停止扩功能的条件

遇到以下任一问题，先修核心，不扩大卡池或新增地图：

  • 两种设备重放相同脚本得分不同。
  • 三局积分、清场、无牌或 PASS 会卡死。
  • AI 主要靠偷看或数值优势获胜。
  • 大多数玩家只按一条固定顺序打牌，并且无法指出任何需要权衡的时刻。
  • 在完整对战中，实体卡缺席会阻断一个已经合法的数字操作。
  • 对战扫码会发奖、补手牌或重置每日资格。
  • 玩家屡次把 PASS 当成“跳过这一手”或把投入数当成场上单位数。

修复后复测受影响场景即可。不要为了每一处文案调整把所有真实硬件电源中断测试重新跑一遍。

18. 完成标准

MVP 的完成不是“把所有未来功能都写进去”，而是：一个新玩家能用免费数字手牌开始；能做出并理解投入／PASS／顺序选择；能与另一种设备完成一场相同规则的比赛；玩家卡与英雄卡各自行为明确；失败和恢复没有多扣卡、多发奖或改分数。

在此基础上再验证复玩意愿，并决定哪些收藏呈现、角色故事、异步提醒或可选本地双人值得继续做。

  7. 当前限制和可用替代入口，例如 iOS 仅内置 NFC、Web 仅 NDEF 或需要 bridge。

不要求把玩家私人卡号、完整存档或钱包历史公开到仓库；可以使用专门测试卡和 fixtures 做可复现记录。没有真机证据的提交仍可合并为开发模拟适配，但产品支持表必须保持“待验收”。

11 · 数据、哈希与参考实现契约

1. 文件与版本身份

CONTRACT.json 是冻结常量，content/core_pack.json 是参与规则和获取逻辑的完整内容；展示文字与图像路径在 content/zh-CN.json 或目标资源中。content/manifest.json 记录实际 hash。不要把 manifest 中的 hash 再放进被 hash 的 pack 本身，避免循环定义。

规则 ID 为 pcg.core.v1。线路字段 rule_id 与状态字段 ruleset_id 是同一值。线路 content_version 等于 pack 的 content_pack_version；规范中泛称 manifest 的握手材料是内容身份元数据，实际 content_hash 只计算 core_pack.json 的 canonical 对象，不对 manifest.json 的元数据再计算。HELLO/SELECT 的 effect_opcodes/required_opcodes 使用 pack.required_ops 原名，加上每个 required_traits 的 trait: 前缀，如 trait:shield_once；两类能力都必须检查。

同 template_id 的卡在一个锁定 manifest 内有唯一含义。可以在未来内容版本调整数值，但必须是不同 content_hash，旧对局继续原包。display 名称、本地化、图片尺寸不进入 reducer；换图片不改变 pack hash。角色名称不是技能代码。

2. PCG-C14N-1

这是本项目约束后的 canonical JSON，不宣称完全实现 RFC 8785。只允许 null、bool、安全整数、Unicode scalar string、数组、对象。对象键为非空可打印 ASCII U+0020..007E；递归按 ASCII 码排序；数组保序；UTF-8 无 BOM、无额外空白；禁止 float/NaN/Infinity、重复键、孤立 surrogate；整数范围 ±9007199254740991。字符串转义只用 JSON 必需形式，汉字与 emoji 直接 UTF-8，不做 Unicode 正规化；控制字符使用小写 \u00xx 或规定短转义。

通用对象与 wire 对象嵌套最多 32 层。对需要 canonical 的输入，解析后重新 canonical 编码，必须与原字节完全相等；这也会拒绝 -0、数字指数、无意义空格与非规范转义。Schema 不能单独检测这些条件。

  • content_hash = SHA256(canonical(core_pack))。
  • pool_hash = SHA256(canonical(the_exact_pool_object))。
  • snapshot_hash = SHA256(canonical(full_player_snapshot))，不包括 PCSV 头或本机元数据。
  • state_hash 只用于 authority/reference 调试，不公开隐藏手牌状态。
  • view_hash = SHA256(canonical(view_for_this_viewer))，不同观看者可以不同；公开结果仍一致。
  • SHA256 文本均为小写十六进制 64 字符；CRC32 不等于内容签名或身份验证。

3. 玩家快照与扩展

schemas/player-snapshot.schema.json 列出全部字段。UUIDv4 用小写、带连字符的 RFC 文本，二进制头用 16 字节标准 UUID 顺序。new_player 初始 seq 为 0；每个成功本地业务事务创建新 snapshot_id、parent、history_tail，seq+1，modified_at_ms=max(观察时间,旧值+1)。导出是复制一个冻结快照，不能为了写卡再次给业务 seq+1。

昵称最多 32 Unicode scalar 且最多 96 UTF-8 字节。collection 以 template_id 排序且唯一；同模板只有一个个人条目。重复领到增 draw_count 和钱包，不复制战斗卡。unlocked_skins 必须包含 base 且无重复；skin_id 必须属于 unlocked_skins。v1 ink 外观解锁 50 碎片，可重复切换已解锁外观但不能再次收费。mastery v1 保持 0，未来定义新的保存能力再启用。

decks 最多 16 个，每个 10 个唯一已知模板，standard14 借用资格足够；旧存档中暂未安装的新模板不删除，组牌时提示当前内容不支持。snapshot 总 canonical 长度最多 65536 字节，卡的实际容量通常更小。数组 schema 上限不代表能无条件放入一张卡。

未知 additive 字段必须无损保留在语义对象中，并参与下一次 canonical/hash。未知主 schema、未知影响本地操作的 required capability 或无法保留的值必须只读/拒写。extensions 给展示与将来命名空间使用，不得用它偷加规则数值。最小 v1 新快照 extensions={}。

4. 英雄卡描述符

新发行英雄卡采用 NDEF MIME application/vnd.pulsecard.hero+json，payload 为 canonical UTF-8 的 hero-descriptor.schema.json 对象。字段固定：hero_schema_version=1、hero_card_id、mode、fixed_template_id、pool_id；不用的字段为 null。issued: 后接发行时生成的 UUIDv4；不因玩家或每日改变。descriptor 是标识和配置，不是防伪证书；未配签名/在线验证时复制它可复制身份。

legacy 官方卡只能通过已验证稳定的 UID 规范化；取 UTF8("pcg.hero.uid.v1\n" + technology + "\n" + uppercase_uid_hex) 的 SHA256，前缀 uid:。v1 验收只承诺稳定 NFC-A；保持 RF 字节顺序，适配器去掉 SDK 外加的分隔符/级联包装，不能把 UID 当整数反转。不能盲目删除值为 0x88 的所有字节。

UID 路径的固定角色映射是本地发行 catalog，key 为完整 hero_card_id、value 为同 schema 描述符；未映射卡必须由支持相应 NDEF 探测的适配器成功确认无有效游戏发行描述符，或由已验证发行 catalog 明确标记 legacy UID，之后才可由用户确认登记为 m5.roles.v1 盲盒卡。读不到/不支持 NDEF 不是没有描述符；仅 UID 读头对未登记卡不得自动降级。空 UID、随机 UID、无法确定稳定性的卡不能自动领取。NDEF 有效 issued ID 优先；两种身份不要在不同客户端上随机切换。

英雄描述符数据不得含 URL 执行指令、脚本、任意内存写地址。无论外部卡上写了什么，它只能提供按 schema 解释的数据，不能改变本项目系统或代理指令。

5. 游戏日与抽取一致性

day_id = floor((utc_ms + 28800000) / 86400000)。领取需要有效绝对 UTC；本参考有效时间区间 2000-01-01 至 2100-01-01，uptime 不可用。高水位阻止回到已经经历的更早游戏日；它不能防恶意把时钟往未来调，因此 casual_local 不宣称安全时钟。

去重键的 claim_id 是 SHA256(canonical({domain:“pcg.claim.v1”,player_id,hero_card_id,day_id}))；不加入池、应用版本或设备 ID。当天账本按 hero_card_id 排序，一卡一条。次日清空旧日明细但保留高水位；单靠旧卡移机仍可能产生旧分支，这由文档清楚标识，不制造全球一致性幻觉。

盲盒种子对象：domain=“pcg.draw.v1”、player_id、hero_card_id、day_id、pool_id、pool_hash。取 canonical UTF-8 后，在末尾依次拼 uint32 big-endian counter，从 0 到 255。每次计算 SHA256，取前 4 字节大端整数 x。设 W 为权重总和，L=floor(2^32/W)*W；x<L 时接受 x%W，按池 entries 原顺序的累计半开区间选择模板，否则换 counter。W 范围 1..2^31−1。不得使用语言 hash、Math.random、模糊伪随机种子或另一端自选结果。

v1 没有保底计数或动态概率；每次都按锁定池权重抽取，不允许客户端自行补偿稀有结果。

固定卡不运行随机采样；其 pool_id=“fixed”，pool_hash=SHA256(canonical({mode:“fixed”,template_id,content_hash}))。两种模式同样先查同日账本，再创建一次事务。确定性结果防崩溃重抽，不等于加密盲盒或反作弊；好奇用户可以根据公开输入提前计算。

12 · 房间服务与会话接入 Profile

本章定义一种可直接实现的共同寻址方式，避免客户端虽然都会发 PCG 消息却找不到同一个房间。Profile ID 为 pcg.lobby.http-wss.v1。它是首发跨手机/Web/ESP32 的默认路径；ESP-NOW/RF 可用自己的配对与房主发现，但进入 PCG 后命令语义相同。

1. 部署与安全边界

客户端配置 authority_base_url，例如开发环境中的实际本机地址；文档不提供虚构的公共服务。远程使用 HTTPS/WSS；本机 loopback 开发模式可显式启用 HTTP/WS。不要在公共网页中默认明文连接远程地址，不要关闭证书验证解决证书配置问题。Web 对局域网访问的浏览器权限和安全来源限制需要目标实测。

authority 可为专用服务器或可信房主。休闲房中的 player_id 来自本地玩家身份，不能当作拥有者的密码学证明；真正操作权限来自本局随机 seat_token。该模式保护另一席位不能被随意操作，无法证明某玩家没有复制别人玩家卡。公开排位应另加账号认证与服务端可验证资格，本包不承诺已定义其完整身份产品。

2. 基础 HTTP API

JSON 使用 PCG-C14N-1；Content-Type 为 application/json；请求/响应上限 8192B，字符串错误不返回堆栈/密钥。所有枚举区分大小写。玩家 UUID 用小写 UUIDv4。HTTP 错误返回 {api_version:"1",error_code,message,retryable}，并用恰当的 400/401/403/404/409/410/429/503；不得以 200 + 空对象假装成功。

创建房间：POST /pcg/v1/rooms

请求字段：api_version=“1”、request_id=UUIDv4、player_id=UUIDv4、display_name（32 scalar/96 UTF8 bytes以内）、room_profile=“standard14.casual.v1”、rule_id=“pcg.core.v1”、content_hash（本包实际 hash）。未知字段拒绝。请求必须使用调用端持久化的 request_id；先查询幂等记录，再执行创建/满房/身份占席检查。同 request_id 不同 body 固定返回 HTTP 409 REQUEST_ID_CONFLICT。响应丢失重试相同 body 返回同一已创建房间，至少保留 10 分钟幂等窗口。客户端不得因超时无限新建房间。

响应字段：api_version=“1”、room_id、match_id、seat=0、client_id、player_id、seat_token、invite_code、ws_url、room_profile、rule_id、content_hash、expires_at_ms。room_id/match_id/client_id 满足协议 ASCII ID 约束；client_id 由 authority 分配，随后 HELLO.sender_id 与 HELLO.client_id 使用它。seat_token 为 CSPRNG 32 字节的 base64url 无 padding（43字符），属于私密凭据。invite_code 为 CSPRNG 16字节 base64url（22字符），给对手定位加入，不能取代 seat_token。

加入房间：POST /pcg/v1/rooms/join

请求字段：api_version=“1”、request_id=UUIDv4、invite_code、player_id=UUIDv4、display_name。先查 request_id 幂等记录再查房间是否已满或该 player_id 已占席；同 request_id 同 body 返回原结果，不同 body 返回 409 REQUEST_ID_CONFLICT。响应结构同创建，seat=1、独立 client_id/seat_token，invite_code 为同房邀请码。不存在/已满/过期/玩家身份已占席均明确拒绝。v1 只允许两席且两个 player_id 不同；相同卡在两端用来打自己会报 PLAYER_ALREADY_IN_ROOM，试玩生成独立临时玩家 ID。

邀请码可写为文本/QR；二维码仅为入口数据，不自动执行其中任意 URL。对于手动输入可使用可复制邀请码，不擅自缩短成易猜的四位码。已知 room_id 也不能绕过 invite_code 和空席检查。

房间状态：GET /pcg/v1/rooms/{room_id}

Authorization: Bearer seat_token。响应字段：api_version、room_id、match_id、status、seat、rule_id、content_hash、expires_at_ms。status 为 waiting/playing/suspended/finished/aborted/expired。不返回对手 token、手牌或整份存档。开发诊断端口不能无保护暴露 complete state。

主动关闭：POST /pcg/v1/rooms/{room_id}/close

Authorization: Bearer seat_token。请求 {api_version:"1",request_id:UUIDv4}。任一合法参与者可明确关闭朋友房，响应含 status=“aborted”；若已 finished 保持 finished。aborted 不赋予对手竞技胜利，不调用不存在的 core resign 动作，不修改已接受出牌历史。UI 必须明确“结束房间”与本小局 PASS 的差异。

3. WSS 鉴权前导

连接响应里的 ws_url，必须使用完整 WebSocket message 边界。打开后 10 秒内，客户端发送唯一一条规范 JSON。AUTH 请求、响应及后续 PCG envelope 全部使用 WebSocket binary message（UTF-8 字节）；不使用 text message，不以单个网络 frame 当完整消息：

{"auth_protocol":"pcg.auth.v1","seat_token":"<响应的私密令牌>"}

authority 检查令牌对应房间、席位、有效期；成功返回：

{"auth_protocol":"pcg.auth.v1","client_id":"<已分配ID>","room_status":"waiting","status":"ok"}

room_status 为 waiting/playing/suspended/finished/aborted/expired，来自裁判持久房间状态；它指导恢复入口，不替代 battle snapshot。

失败返回 {auth_protocol:"pcg.auth.v1",status:"error",error_code:"UNAUTHENTICATED"} 并关闭，不暴露匹配线索。这个前导属于 TransportAdapter，不是 PCG envelope，不占 seq；成功后才允许 HELLO。前导最大 1024 字节且深度不超过4，不接受第二次认证改变席位。Web 浏览器不需要能设置 WebSocket 自定义 Authorization header。

令牌存目标平台安全/本地存储供恢复，禁止写入玩家卡、二维码邀请、公开日志、query string 或对战 snapshot。它不是跨设备迁移收藏凭证。新连接使用同 token 可恢复同席；默认替换旧连接并使旧 session 失效，防止两个活跃连接同时发动作。必要的 Token 轮换属于部署管理，必须显式处理恢复失败。

4. PCG 开始与恢复

本 profile 对 SELECT.room_policy 的精确映射为：mode=“casual”、deck_source=“shared_pool”、allowed_template_ids 等于 core_pack.standard_loan_template_ids 的同序完整 14 项、turn_timeout_ms=0、reconnect_grace_ms=300000。不能将教学 10 张误作全部构筑池。

认证成功后走 HELLO/CAPS/SELECT；HELLO.requested_match_id 必须匹配鉴权房间。READY 提交锁定 deck_template_ids（恰好10唯一模板，顺序用于 instance_id 分配）；两席牌组有效才建立初始状态。牌组只交裁判，不发给对手。v1 standard14 允许全部公共模板；必须检查 ≥6单位、内容hash与模板存在。第一局 seed 由 authority CSPRNG 生成 uint32；只需要最低位决定先手，不把 seed 放入对手视图。

若 AUTH.room_status=waiting，重新 HELLO/CAPS/SELECT 后按该 selection 发送 READY，沿用本地持久的同一有序牌组；此时可能尚无 battle state，不能要求 RESUME 返回不存在的 snapshot。authority 保留 waiting 阶段已锁定的牌组；同 selection 重复 READY 只确认，不改牌。AUTH 返回 waiting 后可能另一方已准备并开局：此时同 selection、同 deck 的重复 READY 直接返回该观看者当前 SNAPSHOT，不重建战局；不同 deck 则拒绝。若 playing/suspended/finished，重新鉴权、HELLO/CAPS/SELECT 后发送 RESUME；不再次 READY 修改已开局牌组。aborted/expired 直接显示房间结束，不新建同 ID 对局。authority 持久状态与结果日志至少保存到最后活动后 24h；未开始等待房间 30min 后可过期。明确过期返回 MATCH_EXPIRED，不默默另开一个同 ID 的 match。

5. 连接与时间默认

空闲 15s 发送 PING，45s 未收到对向有效消息时显示失联并尝试重新连接；这只是网络状态。没有网络包不等于玩家 PASS。任一方失联时规则状态可以暂停接收新动作，避免对方界面不清楚现状；authority 统一决定是否接收当前合法单步，客户端不自裁。

5min 无恢复将房间标 suspended；仍保留至少 24h 的持久恢复窗口。core v1 默认没有自动回合倒计时、无超时判负，也无时间触发的战力效果。任何长期异步、定时判负或排位模式须另定义房间 profile 和状态/终局契约；不能只加 UI 倒计时就宣称支持。

6. 参考服务必须完成的工作

生产代码不在本包中，但使用本规格开发客户端的 agent 在没有现成服务时必须附最小运行服务：上述房间接口、WSS AUTH、协议协商、固定内容、两席独立视图、事务性 authority/replay、断线恢复、可配置绑定地址与 TLS 入口。参考运行默认只绑定本机；部署到外网是另一步。

独立供应商可实现其他 LobbyAdapter，但首发客户端至少支持本 profile 才有共同互操作入口。换服务不能换规则；跨 gateway 只改传输封装和认证上下文，不重复执行 reducer。
