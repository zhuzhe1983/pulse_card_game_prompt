# 02 · 视觉风格、交互与跨端体验规格

> 产品名：脉冲对决。英文显示名：PULSE。本文规定信息结构和交互语义，允许不同开发平台使用原生控件。所有页面消费同一份权威对局状态与卡包，不得在界面中重算出另一套规则。正式字段以 `CONTRACT.json`、协议规范及卡包为准。
>
> 视觉方向为“黑白电子漫画卡册”：清楚的硬件角色轮廓、漫画分格、短句效果、醒目的整数。彩色设备可以使用彩色主题，但不能增加黑白端看不到的战斗信息。界面上的数字来自规则，不从概念卡面读取。原卡两种面貌、已放弃的整卡试做，以及尚未验收的模板预览，见 `docs/16_CARD_FACE_STYLES.md`。
>
> 下面关于战力、小局、投入和停手的界面，描述的是已归档的 `pcg.core.v1`。回合战要让人同时看见基地生命、供电、攻击、耐久、护卫、墓地和牌库张数。画面资源这次不改。

## 1. 体验目标

用户应在任何设备上回答以下五个问题，而不需要打开说明书：

1. 现在轮到谁？
2. 我与对手各有多少场上战力？
3. 本小局我已经投入几张，还能投入几张？
4. 我还有多少未用手牌，它们会留到下一小局吗？
5. 现在停止出牌会发生什么？

NFC 的角色分两层：玩家卡负责身份与可携带保存，英雄卡负责领取收藏和可选的卡片定位。完整战斗必须能只用屏幕上的数字手牌完成。不要把“手里找不到一张实体卡”变成“本来合法的回合无法行动”。

## 2. 视觉语言

### 2.1 风格关键词与禁用方向

| 项目 | 应采用的表达 | 不采用的表达 |
|---|---|---|
| 角色 | 设备外形的人格化：屏幕作表情、按键作装备、接线作服饰细节 | 仅在普通卡框贴一张电路板照片；靠大量小字区别角色 |
| 卡面 | 粗细有层次的黑色轮廓、少量网点、清楚留白、紧凑效果句 | 满屏灰噪声、密集纹理压住数值、细线绘制小字 |
| 比赛 | 静态战场与明确的分数变化 | 以实时粒子、刷卡速度或动画连击承载规则 |
| 语气 | 轻松、短、略带硬件梗；结果明确 | 每次操作长篇旁白；把错误码当说明 |
| 收藏 | 卡册页、角色称号、命名、外观、来源记录 | 把收藏稀有度误画成 PvP 战力等级 |
| 进步 | 学会更好的投入顺序、解锁外观或角色故事 | 无提示地通过等级增加相同模板基础分 |

首版无需完整角色插画即可开发：使用原创简单轮廓占位、设备缩写和统一卡框。占位画面不能成为规则识别的唯一依据。正式插画替换时无需更改任何引擎字段。

### 2.2 黑白主题为基准

建议设计 tokens：

| Token 语义 | 黑白参考值 | 用途 |
|---|---|---|
| 纸面 | `#FFFFFF` | 页面与主要卡面背景 |
| 墨色 | `#000000` | 正文、战力、主要轮廓 |
| 次级背景 | 白底稀疏网点／斜线纹理 | 非当前区域、不可选项目；不只降低对比度 |
| 强调 | 黑底白字 | 当前行动、选中卡、主要确认 |
| 正变化 | `+2` 字样＋向上符号 | 明确显示增分；不依赖绿色 |
| 负变化 | `-2` 字样＋向下符号 | 明确显示减分；不依赖红色 |
| 不可修改 | 锁形图标＋“稳定” | stable |
| 一次防护 | 盾形图标＋“防护 1” | shield_once 可用 |
| 防护已用 | 破盾／空盾＋“防护已用” | 不得继续画成可阻挡 |
| 借用 | 小号“借用”文字章 | 卡册／牌组详情，防止误认永久拥有 |

小字号正文保持纯黑白；网点只用于大面积装饰或区分面，不覆盖数字。避免以灰度非常接近的两种卡框表达合法／非法目标。

### 2.3 彩色主题是同信息映射

建议彩色端以偏白纸面、深墨正文为基础，前排可用暖色小标签，后排可用冷色小标签；当前行动用蓝色强调，警告用橙色。颜色值由实现的对比度测试确定，不把某个 HEX 当成已经验证的无障碍保证。

必须同时保留前／后文字、排位图标、数值、盾／锁符号、选中边框。黑白模式截图转换后仍须能完成全部决策。禁止设置“只有彩色端能看见角色受了减益”“只有手机有目标预览”的差异。

### 2.4 字体与数字

- 中文使用目标平台许可和存储条件允许的清晰黑体；有资源条件时使用 Noto Sans CJK 等明确许可字体，具体文件与许可证列入素材清单。
- 数字宜使用等宽或固定数字宽度，避免从 9 变成 10 时让分数整体跳位。
- 战力是页面最强的数字层级；局积分次之；剩余手牌和已投入数必须能同时找到。
- 不在小屏上以英文完整效果名代替中文短句。
- 字号缩小到无法读清前，应切换为分步页面；不要把完整电脑界面硬缩到旋钮屏。
- 大字号设置、字体缺字和中英文切换不能改变布局中的目标对应关系。

## 3. 统一信息模型：区分三种数字

| 数字 | 建议标签 | 示例 | 不能叫作 |
|---|---|---|---|
| 场上总战力 | “战力” | 我 16／对手 14 | 血量、电量、总积分 |
| 已投入卡数 | “投入” | 3/5 | 场上单位数；战术也算投入 |
| 剩余手牌 | “手牌” | 7 张 | 剩余抽卡次数 |
| 整场局积分 | “局积分” | 我 0／对手 2 | 角色等级或当前战力 |
| 当前小局 | “第 1/3 局” | 第 2/3 局 | 第 2 回合；一局包含多次行动 |

最容易误导的情况是打了 1 张战术后：投入次数增加、手牌减少、弃牌增加，但场上单位数不增加。页面不能用“场上有几个卡框”替代投入计数。

## 4. 全应用导航

以下为逻辑页面，不强制要求都对应独立路由。窄屏可以逐页进入，宽屏可以用侧栏或标签页；同一操作语义保持一致。MVP 要求 AI 与双设备在线；同机双人、异步模式按能力实现，未实现的可选模式不显示伪入口。

| 页面 | 核心内容 | 主操作 | NFC 行为 |
|---|---|---|---|
| 首页 | 当前玩家／游客、继续对局、开始对战、卡册、抽卡大厅 | 继续／开始对战 | 玩家卡进入身份流程；英雄卡仅提示去抽卡大厅或查看角色 |
| 玩家资料 | 展示名、收藏概况、进度同步状态 | 保存到玩家卡、切换玩家 | 只处理对应身份／保存流程 |
| 保存进度 | 待保存概要、请保持卡片、明确结果 | 写入／检查结果 | 只处理玩家卡；不得发放英雄奖励 |
| 抽卡大厅 | 已登录玩家、固定卡／盲盒说明、当次领取状态 | 刷英雄卡并确认领取 | 英雄卡识别进入领取流程 |
| 我的卡册 | 自有收藏、借用模板、外观详情 | 查看、命名、加入牌组 | 英雄卡可定位已知模板；是否领取仍需进抽卡大厅 |
| 牌组 | 10 张、单位数量、重复／资格提示 | 使用默认阵容、保存牌组 | 可定位角色；不向活跃比赛补牌 |
| 对战模式 | AI、本地双人、联网、异步 | 创建／加入 | 不自动发奖 |
| 房间／等待 | 双方展示名、规则兼容状态、准备 | 准备、退出 | 不用于抢先手 |
| 战斗 | 双方战力、局积分、手牌、排位、PASS | 出牌／停止本局出牌 | 可选手牌定位，不触发抽卡 |
| 小局结果 | round_results 的比分／积分、最新余牌；记录充分时显示用牌变化 | 查看下一局 | 不改变已经结算的状态 |
| 整场结果 | 胜负／平局、三局轨迹、复盘 | 再来一场、返回 | 不直接改当前战斗记录 |
| 帮助／设置 | 教程、文字大小、主题、声音、设备连接 | 按需设置 | 读卡自检与正式领取分离 |

首页优先提供“继续进行中的对局”。不要在用户恢复时默认新开一场，也不要用一张通用加载页长时间掩盖“未登录、等待联网、内容包不兼容”这几种不同状态。

## 5. 通用输入动作与设备映射

所有前端应将硬件输入映射为统一的本地交互意图；这些不是直接发往裁判的新协议命令：

- 上一个／下一个焦点。
- 选中／进入。
- 返回／取消未提交的选择。
- 打开卡片详情。
- 进入出牌确认。
- 进入 PASS 确认。
- 提交当前确认的行动。

| 操作 | 触屏／鼠标 | 键盘 | 旋钮＋按键 | 仅方向／确认键 |
|---|---|---|---|---|
| 选手牌 | 点选／水平滚动 | 左右键 | 旋转 | 左右或循环切换 |
| 查看详情 | 点详情或再次进入 | 详情键／Enter 进入 | 短按进入卡片页 | 确认进入 |
| 选排位 | 前排／后排按钮 | 上下或左右 | 旋转选项、短按 | 方向键＋确认 |
| 选目标 | 点明确标记的单位 | 焦点移动 | 按公开列表顺序轮转 | 焦点移动 |
| 返回 | 返回按钮 | Esc | 长按返回，或明确的“返回”选项 | 返回键／返回选项 |
| 确认出牌 | 点“确认出牌” | 确认 | 聚焦确认后短按 | 确认 |
| PASS | 独立“停止本局出牌”按钮，再确认 | 菜单入口，再确认 | 菜单选 PASS，再确认 | 菜单选 PASS，再确认 |

长按默认用于取消或返回，不能既被当作“取消当前选牌”，又在同一事件中当作“立即 PASS”。若某硬件只有一个按钮，优先通过选项列表提供明确的返回和确认，不设计必须精确掌握毫秒时长的危险捷径。

目标列表排序应稳定：先按阵营筛选，再按 front、rear，排内按部署顺序排列。不得因为某目标战力变化而自动重新排序，使旋钮下一格选中另一张卡。

## 6. 战斗界面的共同结构

### 6.1 常驻状态

至少展示：第几小局、双方局积分、双方战力、双方剩余手牌数量、双方投入数、当前行动方、对方是否 PASS。窄屏可把局积分与手牌作为固定短行，详细单位放在二级页面。

双方排位是规则属性，不由屏幕上下决定。通常将对手后排放最上方、对手前排靠中线；自己前排靠中线、自己后排靠近下方。交换视角时，front／rear 值不能被交换。

### 6.2 单位最小显示

- 角色缩写或短名。
- 当前战力；详情中可看基础分与本局修正。
- 前排／后排位置。
- stable／防护状态。
- 是否为当前目标或待部署预览。

被减到 0 的单位仍须清楚留在场上，显示“0”，不能消失或绘成已经死亡。防护被消耗时显示一次简短事件，并改成失效状态。

### 6.3 数字手牌

全场开局 10 张都可选择，但不要求同一屏同时显示 10 张完整卡面。列表、分页、卡册条带、旋钮逐张翻阅均可。

每张手牌展示当前是否可出、基础分、可放排位和短效果。不可出的牌保留可查看状态，并给出准确原因：不是你的回合、本局已 PASS、本局投入已满、战术暂无目标。不要统一显示“能量不足”。

对手只看到手牌数；自己的手牌排序由本地偏好决定，不改变服务器上的卡片身份。

### 6.4 一次出牌流程

1. 选择一张本方手牌。可通过数字列表或可选 NFC 定位。
2. 显示卡片详情。若单位只有一条合法排位，自动填入并清楚显示；若两排均可，要求选择。
3. 若效果需要目标，聚焦合法目标；目标仍可选 stable／防护单位，但展示实际变化。
4. 显示确认摘要：将打出的牌、排位／战术、目标、己方战力变化、敌方战力变化、剩余手牌数、投入数。
5. 确认后进入提交等待；按钮禁用，原确认操作不可重复发送为另一个新行动。
6. 收到权威接受后统一更新卡、战力、名额与行动方；收到拒绝后恢复最新状态并解释原因。

实际变化预览必须基于同一规则引擎的试算或相同的只读计算，不在 UI 单独维护另一张“各角色大概效果”表。

### 6.5 确认摘要示例

- “Dial → 后排；另一排已有单位，获得 +2。我的战力 11 → 16；手牌 8 → 7；投入 2/5 → 3/5。”
- “加一把 → 探子；目标战力 4 → 6。战术不留场；投入 2/5 → 3/5。”
- “Cardputer → 后排，干扰 PaperMono。目标具有稳定，减分不会生效；仍消耗这张牌，Cardputer 提供 3 分。”
- “干扰信号 → Stamp；消耗目标防护，本次战力不变。仍消耗这张战术牌。”
- “这是本局第 5 次投入，成功出牌后将自动停止本局出牌。”

## 7. 大屏、手机与 PaperMono 类页面

### 7.1 宽屏默认布局

页面上方是局积分和当前行动，中间是四个排区，下方是本方数字手牌与行动按钮。侧边可以放本端已收到的公开记录与弃牌查看入口；没有侧边空间时折叠到详情。不把这份局部记录标为可恢复完整对局的回放。

手牌滚动不带动整个战场离开屏幕。查看详情时仍能看到当前总战力与投入上限。手机竖屏优先让四排变为紧凑条带，每排进入后查看单位；横屏不应成为必需条件。

### 7.2 电子墨水屏适配原则

- 以“一个被接受的行动 → 一个可读稳定画面”为默认更新单位。
- 适配器根据具体屏幕和驱动能力决定局刷、全刷、灰阶和清理周期；不要把某一型号的刷新模式写进玩法引擎。
- 页面不会要求持续移动的角色才能判断目标；所有关键信息都有静态终态。
- 有残影风险时，局末、切换主要页面或达到适配器阈值后做整屏清理。清理过程中可显示适当的硬件反馈；不会因此重复提交出牌。
- 不为倒计时每秒全屏刷新。低频更新剩余时间，在有状态事件时更新；真实截止时间由会话裁判保持。
- 避免黑白全屏闪烁作为每张卡的“攻击动画”。短事件条、数值前后对照和一次可选提示音即可。
- 支持“立即清屏”设备操作，但它只重绘当前状态，不重开比赛。

性能目标是输入有反馈、确认有结果、稳定画面无歧义。具体毫秒数必须在真实硬件测量后确定；不能用桌面浏览器渲染时间当作墨水屏硬件验收。

### 7.3 PaperMono 页面最小版本

首版可采用三页结构：战场总览、我的手牌、当前卡／目标确认。返回战场时保留未提交选择，但只在状态版本仍有效时允许提交；若对局状态变化则清除失效选择并提示重新选。

触控、实体按键或外接输入是否存在，由设备能力配置决定。不要在通用 UI 代码假定所有 PaperMono 装置都有相同按钮或触控驱动。

## 8. Dial 类圆屏与旋钮交互

以下以 240×240 的圆形设计画布作为参考布局，不替代实际设备能力配置。内容应能在其他尺寸下按同一语义重排。

### 8.1 不把完整桌面战场缩小

圆屏默认采用“概要 → 选牌 → 排位 → 目标 → 确认”分步流程。主屏只显示双方战力、手牌数量、投入数、局积分及一个清楚的行动入口。一次聚焦一张手牌，旋转切换，短按进入。

重要文字放入约 166×166 的居中安全区域；外围弧形空间只用于小图标或装饰。不要把关键数字放在圆形裁切区域的四角。具体可用区域需要根据表盘边缘和字体实际渲染验证。

### 8.2 圆屏页面表

| 页面 | 中央主要信息 | 旋转行为 | 短按 | 返回 |
|---|---|---|---|---|
| 战斗概要 | 我／敌战力、局积分、行动方、投入与余牌 | 出牌／查看场地／PASS／已收记录 | 进入所选项 | 会话菜单，可明确关闭房间；不判输赢 |
| 手牌翻阅 | 一张卡：短名、基础分、排位、效果短句、序号 | 上一张／下一张 | 进入这张卡 | 战斗概要 |
| 排位选择 | 该卡及前排／后排、条件加分预览 | 在合法排位间切换 | 选定排位 | 手牌页 |
| 目标选择 | 目标短名、所在排、当前分、预计结果 | 在稳定顺序的合法目标间切换 | 选定目标 | 排位／手牌页 |
| 出牌确认 | 牌名、目标、分数变化、投入变化 | 确认／返回 | 执行所选项 | 回到选择 |
| PASS 确认 | 本局当前比分、双方余牌、“本局不能再出牌” | 停止本局／返回 | 执行所选项 | 战斗概要 |
| 等待对方 | 对方回合／对方已 PASS、当前比分 | 查看场地／已收记录 | 查看详情 | 保持对局 |

单位无可选目标且允许空放时，不显示空白目标页；直接进入确认并说明效果略过。战术无目标时详情页提示“暂无目标”，仍可返回选择其他牌或 PASS。

### 8.3 防误触

- 所有消耗卡片和 PASS 的行为都必须经过明确确认页。
- 打开详情的同一次按钮抬起事件不能再次触发确认；输入适配器需要完成去抖和事件消费。
- 高速旋转跨过多张牌只改变焦点，不能连续出牌。
- NFC 识别多次只聚焦同一张牌，不叠加提交。
- 提交待确认时旋钮可以查看信息，但不能把另一张牌替换进已经发出的操作。
- 待提交操作的取消只是停止本地等待界面，不保证撤销已经抵达裁判的动作；默认不提供带误导的“撤销出牌”。

## 9. NFC 读取路由与明确反馈

### 9.1 场景与卡种矩阵

| 当前场景 | 玩家卡 | 英雄卡 | 未识别／不支持的卡 |
|---|---|---|---|
| 未登录首页 | 显示识别的玩家并进入登录流程 | “先登录，再到抽卡大厅领取” | “未识别卡片；可以继续使用数字试玩” |
| 已登录首页 | 当前卡进入资料；其他玩家需要明确切换 | 仅查看已识别角色／引导抽卡大厅 | 不改当前身份或对局 |
| 抽卡大厅 | 当前玩家身份确认；切换身份返回大厅前置流程 | 固定卡或盲盒领取流程 | 不计入每日额度 |
| 牌组编辑 | 不自动切换正在编辑的牌组归属 | 定位对应角色；可加入合法牌组 | 不影响已有选择 |
| 战斗 | 当前身份信息；其他玩家卡不能热切换比赛 | 只定位剩余数字手牌或提示已用／未入组 | 不提交行动，不扣牌 |
| 保存到玩家卡 | 校验目标并执行显式保存流程 | “请使用玩家卡” | 不写入，不误报保存成功 |
| 设备读卡自检 | 展示必要的诊断结果 | 展示必要的诊断结果 | 展示读卡失败；不走登录／领取流程 |

### 9.2 抽卡大厅流程

1. 明确显示当前登录玩家。
2. 显示本页用途：“刷英雄卡领取角色；同一张卡每个游戏日限领一次。”游戏日按 UTC+8。
3. 识别卡类别与卡号，查询当次资格。固定卡可预览固定模板；盲盒只展示奖池说明，不在确认前提前泄露随机结果。
4. 显示“领取”或“今天已经领过”。领取确认只提交一次；等待结果时防止重复请求生成新领取。
5. 成功后展示具体收藏／碎片结果与来源。失败按领取事务的持久化结果展示（可选服务端验证模式再以服务端回执为准），不凭读卡器提示音判定发奖成功。
6. 提供“查看卡册”和“继续对战”。不要强制用户把新角色立即加入当前进行中的比赛。

默认实现采用一次明确领取确认。若后续版本改为进入大厅后直接刷卡即确认，必须统一修改需求，并在大厅持续显示“刷卡即领取”；客户端不得自行改变消耗每日资格的时机。

### 9.3 玩家卡保存流程

保存页先显示要保存到哪个玩家、可保存进度概要，以及目前是否还有未同步变动。然后提示把玩家卡靠近并保持。

写入期间不允许用另一张英雄卡中途替换用途。只有规定的写入、读回与验证完成后，显示“已保存到玩家卡”；若结果未知，显示“尚未确认写入完成，请保持卡片或重新检查”。不要一收到 NFC 写入函数返回就先播放成功动画，再异步发现校验失败。

写入失败不修改游戏规则，不额外扣奖励，不把对局判负。原存档是否仍可恢复、如何选择新旧记录，按玩家卡保存契约处理，界面只展示可验证的事实。

## 10. 断线、跨设备恢复与可选异步

### 10.1 网络、房间与正常完场状态应能分清

| 状态 | 给用户看的文字 | 允许的操作 |
|---|---|---|
| 已连接，轮到自己 | “轮到你了” | 查看、选牌、提交 |
| 已连接，轮到对方 | “等待对方行动” | 查看场地、已收记录、自己的手牌；不提交 |
| 行动已发出，结果未知 | “正在确认这次出牌” | 查看，不发新的不同操作 |
| 连接断开／设备刚唤醒 | “正在恢复对局” | 查看最后确认状态；禁止从旧状态提交 |
| 房间暂停／等待恢复 | “对局已暂停，等待重新连接” | 查看最后确认状态、重连或明确关闭房间；不自动 PASS、不判负 |
| 房间已关闭（aborted） | “房间已关闭，本场未产生胜负” | 查看已确认比分记录、新建对局；不显示竞技胜负或增加胜场 |
| 规则正常完场（points） | 展示真实局积分与胜／负／平 | 查看比分结果、新建对局 |

重连成功时如果先前操作已被接受，直接呈现已出牌结果，不再让用户“重新确认一次”。如果操作被明确拒绝，回到可选择状态。若仍无法确定，不擅自返还卡片或提交补偿操作。

### 10.2 低功耗与异步（异步模式为可选 profile）

等待对手时可以进入低功耗显示或睡眠。睡眠前不会自动 PASS。唤醒后先同步，然后显示“轮到你”“对方尚未操作”或“对局已经结束”。

同一玩家从别的设备继续时，界面必须标清正在恢复同一场对局。该玩家的同时在线设备采用统一会话处理，不能各自发出一条合法但不同的下一手。

### 10.3 结果页来源

参考引擎在小局结算后会清场，末局也一样。客户端结果页必需读取 `round_results` 中已记录的小局比分／积分，并恢复自己的最新过滤视图；不能读取清场后的实时 board 然后把结算结果显示成“0 比 0”。

v1 不保证双方客户端收到或恢复完整 `round_ended` 事件。没有终盘场地记录时，只显示可信比分、局积分与最新手牌数量；手牌变化或本局投入明细仅在前后记录充分时显示。不得猜测最后一手的排位、目标或完整布局，也不因缺少回放而阻止继续对局。完整回放是裁判端本地日志的可选能力；不要求客户端提供该入口，不扩展 SNAPSHOT 保存完整历史。

小局结果页的“继续”只是关闭本地展示，不应额外发送一条推进玩法的行动。如果服务器已经进入下一小局，用户关闭结果页后直接显示新的行动方。

## 11. AI 模式的表现

- 显示对手为“教学 AI”或“练习 AI”，不假装真人。
- 可以在教学关展示脚本目标和提示；普通对战不显示 AI 私有手牌。
- AI 行动可以延迟一个短、可配置的阅读间隔，但决策不能等待玩家之后的本地选择来反向修改。
- AI 已经确定并提交的动作只渲染一次；跳过动画不会跳过规则。
- 赛后点评使用本局公开事实，例如“你用 3 张牌保住 7 张手牌进入下一局”，不要从玩家从未提交的候选点击推断其策略。
- AI 难度通过策略质量与搜索预算变化，不通过隐藏基础分、额外手牌或偷看对手状态变化。

## 13. 素材、组件与实现交付

首版应有以下可替换资源，不应将数值写死在图片里：

- 通用单位卡框、通用战术卡框、借用／自有展示标记。
- front、rear、盾、失效盾、稳定锁、PASS、小局胜／平／负符号。
- 12 个可用原型缩写或原创简笔角色占位，以及两张通用战术的独立图标。
- 战力数字、效果文案、玩家名称全部由数据和文本渲染。
- 主题 tokens、字号档位、输入映射和显示能力适配配置。
- 比分记录组件与本方私有手牌列表；客户端不必实现完整回放。
- 若实现裁判端本地日志复盘，其公开展示必须过滤私人手牌；该可选组件不等于远程客户端具备完整历史恢复能力。

可以共享数据与设计 tokens，但不要要求所有平台使用同一 DOM／WebView。原生 MCU 绘图、Flutter、Unity、原生移动、浏览器等实现只要保持规则和信息等价即可。

## 14. UI 验收用例

1. 把所有颜色移除，仍能分清目标、排位、防护、stable、余牌和投入上限。
2. 在圆屏安全区域内，用默认字号看清 16 与 14、3/5 与 4/5；截图无裁切。
3. 从手牌选 Dial，切换前／后排，确认摘要随条件正确变化；取消后不扣卡。
4. 用战术后投入 +1、手牌 -1、弃牌 +1，场上单位数不变。
5. 选择 stable 目标时提示战力不变；确认后卡照常消耗，不能借此无限试探而返还。
6. 本地双人交接页不显示上一位玩家手牌；另一方 PASS 后不再无意义交接。
7. 第五次投入被确认后立即显示自动 PASS，不再展示可用的第六张提交入口。
8. 断线时按确认、扫码或重启不会让旧操作重复应用。
9. 对战中连续扫英雄卡，收藏数量与每日领取资格不变化。
10. 从未扫过英雄卡的游客，使用免费阵容完成 AI 对战。
11. 拿走所有实体英雄卡后，已登录玩家仍能用数字手牌完成在线整场。
12. 小局结算后场地已经清空，结果页仍显示正确的上一局战力。
13. 调大字体后，目标和确认按钮仍可访问；长角色名可换行或进详情，不覆盖分数。
14. 屏幕整屏清理只发生显示变化，不发任何 gameplay command。
