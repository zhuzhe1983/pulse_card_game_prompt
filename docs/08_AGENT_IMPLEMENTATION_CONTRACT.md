# 08 · 开发代理实施契约与所需材料

## 1. 输出结构与责任分层

语言/框架由目标平台决定，概念模块必须保留清楚边界：`RulesEngine`、`ContentLoader`、`PlayerStore`、`ClaimService`、`CardReaderAdapter`、`CardCodec`、`TimeProvider`、`AuthorityAdapter`、`TransportAdapter`、`LobbyAdapter`、`ViewModel/UI`。允许同仓库不同目录；不强制某一种“万能框架”。

- RulesEngine：完整状态与命令到下一状态，整数和稳定顺序；核心逻辑无 IO。
- PlayerStore：本地事务、快照祖先索引、冲突备份、pending export、幂等操作 ID。
- ClaimService：按日去重、确定性抽样、原子收藏/钱包变更，不直接渲染。
- CardReaderAdapter：探测能力、读写物理介质、取消/移开/错误；不决定胜负或发奖。
- CardCodec：PCSV/NDEF/UID 标准化；不把 unknown 当 blank。
- Authority：认证身份到 seat、规则调用、持久幂等日志、按观看者过滤。
- Transport/Lobby：发现、认证、字节完整交付、重连；不重写游戏动作。
- UI：完整呈现可见状态、显式本地/卡保存状态；只提交意图。

## 2. 开发顺序

### 阶段 A：工程与兼容性探测

读目标配置和现有代码；核实真实板卡/读卡器/SDK。列出 supported / unsupported / untested 能力。保留现有用户文件，不能用“简化”理由重建覆盖工程。锁定依赖版本和构建方式。固件项目说明板型、分区、flash/PSRAM、Grove 引脚和供电；无材料不能编造引脚。

### 阶段 B：先完成可验证规则

移植 core v1 reducer 与 canonical 编码；加载同一 JSON 卡包。运行黄金向量，输出每一步 state hash、view hash。实现合法命令枚举与不读敌方隐藏手牌的教学 AI。先完成本地一整场，不从漂亮首页开始宣布完成。

### 阶段 C：完整本地玩家流程

实现持久化、玩家登录选择、收藏与两类英雄卡、游戏日、重复奖励、外观兑换、显式导出、容量预检和恢复。先用 MockReader 自动复现拔卡/满卡，再接真实 ReaderAdapter。MockReader UI 显示模拟标签，不伪装为实物。

### 阶段 D：互操作联机

有 IP 能力的目标接通 docs/12 的房间服务与 docs/04 协议；RF-only 目标可经实际桥接进入同一 authority，或按已定义配对的本地裁判 profile 互战，不把 JSON 相同等同于射频原生互通。无现成服务则附一个可运行的参考 authority（例如 Python/Node/Rust 任一适合环境的实现）。同一客户端开两个浏览器只是起点；必须给目标客户端和参考客户端对战脚本。加入丢包/重复/恢复，核对 privacy 和持久事务。

### 阶段 E：平台体验与交付

针对圆屏、电子纸、触屏与桌面输入调整界面；保留同样规则和完整信息。测核心流程、失败路径与资源上限。交付命令、源码、配置、测试报告和可复现截图/日志。没有设备时交付构建与 mock 测试结果，以及真实硬件待测清单，继续完成可做部分。

## 3. 状态与数据落盘建议

ESP32 可使用 LittleFS 文件与原子重命名/双记录 journal；Android/iOS/桌面可用 SQLite 事务；Web 可用 IndexedDB 单事务。具体库可选择，语义不可改变。对 flash 高频写入做去抖和事务批处理，但领取成功/出牌 accepted 前的必要提交不能延迟到“以后有空”。不要在每次 NFC polling 和每帧渲染时写 flash。

本地 profile record 至少包含：active snapshot、其 hash、祖先 ID 索引、最后一次从该玩家卡读到的 snapshot_id、最后验证导出的 snapshot_id/hash、pending export、冲突备份、读卡能力与错误日志。设备元数据不写入可携带 snapshot 的 hash；不能把连接 token 或服务器私钥塞入玩家卡。

## 4. 旧工程迁移

如果现有“RPG+宝可梦+卡片”工程存在：保留可复用的驱动、UI 外壳、角色图和用户数据。把旧战斗实现隔离为 legacy 模式；不能把 HP/经验加成偷偷带入 core v1。旧存档必须先给出字段样本和映射表才能迁移，不靠猜测重命名字段。迁移只建新备份与新快照，验证通过后再允许明确写卡；原始备份保留。

若旧模式仍需互战，使用不同 ruleset/protocol entry，不允许它自报 pcg.core.v1。用户说“兼容旧版”不意味着两个不同胜负算法能打同一局。

## 5. 材料分级：现在就能推进，哪些会影响真机

| 优先级 | 请项目所有者提供 | 为什么需要 | 暂缺时可以做什么 |
|---|---|---|---|
| P0 真机前 | 每种硬件完整型号/硬件版本，尤其 PaperMono 具体型号 | 同系列屏幕、主控、NFC 模块/引脚可能不同 | 纯规则、Web参考端、通用适配层 |
| P0 真卡前 | 官方赠卡的匿名扫描报告；是否 NDEF、稳定 UID、能否写、实际容量 | 决定 legacy UID 路径与发行描述符，不猜测官方卡格式 | MockReader 和 issued 测试卡 |
| P0 写存档前 | 准备购买/使用的玩家卡芯片与有效容量 | 决定 NDEF_SINGLE 或 RAW_DUAL，验证完整存档能装下 | 使用二进制虚拟卡故障注入 |
| P0 接线前 | Grove/USB 读卡器型号、供电、引脚、文档链接 | Grove 是连接形式；USB 设备协议也不同 | 驱动接口及 PC/SC bridge 规范 |
| P1 接现有工程 | 旧固件仓库、构建说明、匿名存档样例、已有角色图片 | 复用和旧数据迁移的精确依据 | 从零实现新基线，不伪造旧格式兼容 |
| P1 联网部署前 | 自托管/托管偏好、域名/证书/服务地址、是否仅朋友房 | 远程寻址和认证需要真实服务 | 本地双进程 authority +可配置端点 |
| P1 公测前 | 角色图使用许可、商标/发行范围、命名偏好 | 决定是否能公开使用 M5 外观/官方卡面 | 画简单占位轮廓并标明非最终素材 |
| P2 产品迭代 | 大致人数、目标时长、希望主打收藏还是竞技、实际试玩记录 | 决定平衡与运营投资，而非协议能否开始 | 按本包 DEFAULT 开发和记录 |

在真机需要之前无需等待全部材料。最有价值的首批附件是“旧工程 + 1 张玩家卡扫描报告 + 1 张英雄卡扫描报告 + 首发硬件型号”。切勿索要真实私钥或要求用户上传未脱敏的完整个人存档。

## 6. 每次 agent 交付必须说明

完成了哪些可运行路径；在哪里运行；如何构建；用了哪个 ruleset/content hash；哪些测试实际通过；哪些只是模拟；有哪些确切未完成与理由；目标读卡器是否可读/可写、容量、实测卡型；对接另一个客户端的步骤。不要用一句“理论上支持所有 ESP32/苹果/Web”替代这些证据。

禁止自行新增玩家付费、在线广告、隐形统计、云端覆盖、强制固件更新、硬件性能决定战力、发送私有手牌给对手等产品行为。可选内容必须开关清晰且不改变基线互通。
