# 00 · 产品目标、冻结决策与范围

版本：1.0.0；状态：可实施基线，尚未完成真实硬件认证与充分平衡测试。中文产品名「脉冲对决」，英文显示名 PULSE，技术 slug `pulse-card`。角色视觉和卡片印刷稿可以更换；更换显示名不能隐式改协议 ID。

族群扩展是未启用草案，见第 13、14 章。本章的冻结决策仍然只覆盖现有基础牌。

## 1. 要做成什么

一个以 M5 设备为角色灵感、用 NFC 实体卡建立收藏与身份、在不同屏幕和通信硬件上共享同一种策略对战的游戏。玩家拿起玩家卡登录，刷英雄卡认识新角色，使用收藏或公共借用模板组出 10 张牌，与 AI 或另一设备对战；离开前再刷玩家卡，带走已确认保存的进度。

核心体验是“我愿意为这一小局多花哪张牌”。首局落后不等于整场失败；保留资源、诱导投入、入场顺序与 PASS 决策形成复盘。NFC 提供仪式感、角色归属与实体交换，不负责制造卡牌本身缺乏的策略深度。

本规格借鉴经典昆特的多小局、保留手牌和 PASS 思路；具体牌数、投入上限、整数局积分和角色效果均为本项目原创首测设计，不是任何官方昆特规则的复刻声明。外部事实依据见第 10 章，产品设计无需假装存在外部背书。

## 2. 用户已经明确的需求（MUST）

| 编号 | 不可改变的要求 | 落地约束 |
|---|---|---|
| U01 | 两类卡：玩家卡、英雄卡 | 类型先识别，扫描上下文再路由，禁止拿未知卡做写入试验 |
| U02 | 先玩家卡登录，再英雄卡领取 | 试玩可打借用卡；持久收藏领取必须有已登录 player_id |
| U03 | 同一英雄卡每日一次 | 默认每玩家独立；本机玩家快照记录 card ID 与游戏日 |
| U04 | 再刷玩家卡才保存到卡 | 本机自动持久化与实体导出两个独立状态 |
| U05 | 同机再次登录时比较存档 | 已知同源且本机较新时用本机，卡不自动变化 |
| U06 | 未写入卡不能迁移 | 新设备只读到卡内最后一次成功导出的完整快照；对战服务器不偷偷同步收藏 |
| U07 | 多平台互战 | 相同规则、卡包 hash、数据结构、鉴权会话与裁判语义 |
| U08 | 不锁定 Wi-Fi/RF/ESP-NOW | TransportAdapter 独立；不兼容的物理层通过桥接 |
| U09 | 可用外接 Grove/USB 读卡器 | 必须逐设备验证电气/驱动/卡型/读写能力，不等于插头通用 |
| U10 | 老客户端与新版可处理 | 稳定 core v1、可协商卡包、独立存档版本、明确拒绝不兼容 |

## 3. 为消除歧义而给出的 DEFAULT

这些是可评审的初版产品决策，不声称用户已逐项指定。开发代理应直接按此实施；产品所有者将来可以通过新规格版本修改。

| 项目 | v1 默认 |
|---|---|
| “每天” | 固定游戏时区 UTC+08:00 的 00:00 切日，设备所在地时区不影响 |
| 一次的作用范围 | `(player_id, hero_card_id, game_day)`；别的玩家当天可刷同一实体卡 |
| 普通官方 UID 卡 | 经过实测且稳定的 NFC-A UID 经统一哈希形成 ID；本地发行映射可指定固定角色，否则明确按默认盲盒池 |
| 自发行英雄卡 | 写入 NDEF 游戏描述符，固定角色或盲盒池；ID 为 `issued:` 加 UUIDv4 |
| 初始资源 | 无收藏也有全部 14 模板的标准借用资格，推荐初始牌组为 8 单位 + 2 战术 |
| 盲盒 | 12 角色池；8 伙伴各 10%，4 英雄各 5%，合计 100%；战术不进池 |
| 稀有度 | 收藏分类与演出差异，不是对同模板追加战力 |
| 重复角色 | 同模板条目 `draw_count+1`，获得 10 碎片；没有第二份独占战斗加成 |
| 外观兑换 | 已收藏角色用 50 碎片解锁 `ink` 墨线外观；原型 `base` 免费，可切换；同名模板战力不变 |
| 角色成长 | v1 的 `mastery` 预留并保持 0；不实现未定义的战斗增益/经验经济 |
| 存档主权 | 玩家卡为携带媒介，本机持久数据为本机最新进度；不默认云端覆盖 |
| 默认线上模式 | 朋友房、标准 14 模板池、一个权威裁判、无自动倒计时判负 |
| 首发可信边界 | `casual_local`；提供可选服务端验证扩展边界，不宣称纯离线可防回滚 |
| 基础客户端交付 | 本地 AI、收藏/读写与互战；有 IP 能力默认 WSS，RF-only 可经已实现桥接进入同一裁判；不要求每端实现全部传输 |
| 首轮平衡测试 | 先固定推荐 10 张对称牌组，再评估开放 14 选 10 |

固定角色卡每天也只能领一次；已有该角色时按重复奖励处理。新日、换卡包、换客户端、改卡面显示名都不能绕过同日已提交领取账本。未登录刷英雄卡只显示说明，不扣次数；对战中将英雄卡当快捷选牌时也不触发领取。

## 4. 两条完整玩家旅程

### 4.1 新玩家

首次开机 → 选择试玩或扫描/创建玩家卡 → 识别玩家与本地/卡存档 → 查看借用牌组 → 刷英雄卡 → 预览卡模式并确认领取 → 本地原子提交 → 开盒展示个人收藏 → 与教学 AI 完成一场 → 看到“本机已保存，玩家卡未更新” → 点击保存或进入明确保存扫描上下文 → 再刷同一玩家卡 → 完整写入并回读验证 → 显示“玩家卡已更新，可在其他设备继续”。

创建玩家卡只能在用户明确选择“初始化玩家卡”后对已验证可写介质执行；不能把英雄卡或未识别卡自动格式化。新玩家 ID 和快照 ID 用真实随机 UUIDv4，不取 UID 作玩家 ID。

### 4.2 跨设备与离线朋友局

A 设备读到卡 S0 → 本地玩到 S3 → 不导出时，B 仍只能读 S0 → A 明确保存后卡变成 S3 → B 导入 S3 后产生 S4 → 写回成功后 A 再登录可比较已知历史并导入 S4。任何一步只进行了线上对战，都不自动把本机收藏转移到 B。

若 A 与 B 在同一个旧卡 S0 上分别发展，形成 A3 和 B2：它们是两个分支。不能按时间戳大的一边偷偷覆盖另一边，不能把两边碎片相加。备份两份，显示冲突原因；由用户选择保留哪一支，若要写回卡仍须显式保存。该冲突边界保护用户数据；它不改变普通同机“本机较新就用本机”的要求。

## 5. 玩法与收藏的关系

标准对局借用范围为 `content/core_pack.json.standard_loan_template_ids`，v1 覆盖全部 14 模板。收藏决定“这是我的哪位角色”、名字、外观和来源；同一模板的公用版与收藏版进入 reducer 后完全相同。对手只收到出场单位模板与可选展示，不收到玩家卡 UID、完整收藏、获取日期或私有存档。

可以制作固定角色的赠礼卡、活动卡和每日随机卡。卡片标签必须明确其模式、游戏日边界以及是否属于收藏稀有类别。重复奖励的抽取概率公开显示；v1 不加入付费抽取、现金交易或暗中改变概率。若未来改变商业模式，单独评审，不能让代理自行加入商店。

## 6. MVP、扩展与明确边界

**MUST：** 规则/收藏/每日领取/显式迁移、标准教学 AI、目标平台可用 UI、至少一种可互通网络路径、持久化与恢复、版本协商、能力检测与测试输出。

**MAY：** 同屏轮流对战、局域网发现、ESP-NOW、其他 RF、异步长期对局、服务器签发领取回执、观战 UI、纸卡打印器、手机作为 Grove/USB 桥。协议已预留观战投影，但客户端不必首版实现完整观战产品。

**不在 v1：** 真正全球限次、强防克隆玩家卡、自动房主迁移、P2P 公平密码学裁判、服务器跨设备同步收藏、自动强制胜负计时、新成长战力、多于 2 名玩家、交易市场、复杂连锁牌效。

## 7. 成功与失败的判定

首版成功：两个独立客户端可以完整打完同一局，得到相同公开结果；实体卡进度迁移没有含糊成功提示；新玩家 5 分钟内理解“抢分”和“留牌”的取舍。后者是待测目标。

试玩重点记录：玩家是否为了下一局主动放弃一局、是否能复述输在哪里、是否连续再来一局、战术牌是否成为必弃选项。不能用抽卡次数或页面停留替代玩法验证。每一项数值改动都发布新内容 hash，已经开始的对局继续锁定原包。
