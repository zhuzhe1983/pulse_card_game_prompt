# 03 · NFC、角色领取与玩家卡存档

本章是 `pcg` v1 的业务与存储协议。`CONTRACT.json`、本章、JSON Schema 与 `fixtures/` 必须一致；编码和确定性抽取的可执行定义见 [11_REFERENCE_AND_DATA_CONTRACT.md](11_REFERENCE_AND_DATA_CONTRACT.md)。文中的“必须”是实现要求，“推荐”是可替换的工程选择。实体卡兼容性须按 [05_PLATFORM_ADAPTERS.md](05_PLATFORM_ADAPTERS.md) 验收，不能仅凭卡片商品名宣布通过。

## 1. 已冻结的产品行为

1. 玩家先刷**玩家卡**登录。本机没有该玩家记录时，从卡内完整快照建立本机记录。
2. 登录后刷**英雄卡**领取固定角色或盲盒结果。英雄卡不保存玩家进度，不写每日使用标记。
3. 每日限制默认以 `(player_id, hero_card_id, game_day)` 为键。其他玩家可以在同一天刷同一张英雄卡；每个账户独立计算。
4. 领取成功后，角色、重复奖励、钱包变化和当日已用卡号必须在本机一次性提交。未成功持久化，不算领取成功。
5. 本机游戏进度随业务事务持久化，但**只有玩家明确再次刷玩家卡保存，才会写入玩家卡**。登录、抽卡、退出、联网、对战结束均不自动回写卡。
6. 同一设备再次登录同一玩家时，比较本机与卡上的内容修改时间，并核对谱系。确认本机较新，就使用本机且保留“尚未写卡”状态；不得用旧卡覆盖本机。
7. **只有完整写卡并读回验证成功，更新才具备离线迁移能力。**另一台设备看到的是卡上最近一次成功保存的版本。
8. 对战消息、房间重连、牌组校验和对局结果同步，不是收藏迁移通道；不得顺便向另一设备或云端替换完整玩家存档。

## 2. 卡片角色、标识与识别顺序

### 2.1 玩家卡

玩家卡存放本章定义的 `PlayerSnapshot`，包含收藏、牌组、钱包、当日领取记录和时间高水位。`player_id` 是应用生成的 UUID，不是物理 NFC UID。换一张容量更大的玩家卡，可以继续保存同一个 `player_id`。

卡片可读 UID、可读 NDEF、可写 NDEF、可写自定义应用文件，是不同能力。普通 UID 和文件哈希不是不可复制的所有权证明；v1 的登录语义是“读取持有的玩家档案”，不是金融级身份认证。[N03](10_SOURCES_AND_MATERIALS.md#n03)

### 2.2 英雄卡

英雄卡只有以下两种领取行为，二者均消耗该玩家当日对这张卡的资格：

| 类型 | 识别后做什么 | 必须记录 |
|---|---|---|
| 固定卡 | 按已安装内容包发放指定 `template_id` | 稳定卡号、最终模板、领取键、时间、内容池标识与哈希 |
| 盲盒卡 | 按冻结的池和确定性抽取算法产生一个模板 | 同上；随机算法直接复用参考实现 |

固定卡的重复角色如何转换、盲盒概率及保底规则，以内容和经济规则为准。本章不额外发奖励、不把固定卡解释为“每天重新创建一个新卡号”。池更新、换设备、换显示名称，都不改变同日资格的去重键。

识别顺序如下：

1. 优先识别有效的游戏发行 payload，读取稳定 `hero_card_id`。发行命名空间为 `issued:` 加规范小写 UUIDv4。
2. 没有发行 payload 时，可以通过本机已安装的 legacy 卡片映射，识别官方赠卡的固定角色／盲盒配置。
3. 未知卡只显示识别结果和“未登记为游戏卡”，不自动转成随机新英雄，不自动格式化。
4. 玩家卡和英雄卡在 v1 中是互斥角色。一个标签同时出现冲突的两种游戏角色记录时拒绝执行；不能因为登录状态不同就随意解释同一段数据。

`issued:` 只是稳定标识命名空间，不代表数据天然可信。发行签名只有在提供签名、公钥与验签规则并成功验签时才能显示为已认证；`casual_local` 不强制启用发行安全认证。

### 2.3 Legacy UID 规范化

技术名固定为小写 ASCII 枚举：`nfc-a`、`nfc-b`、`nfc-f`、`nfc-v`。v1 的默认 legacy 领取适配仅接收**已经确认 UID 稳定的 NFC-A 卡**。

```text
uid_hex = UID 字节的连续大写十六进制；无 0x、冒号、空格
identity_material = UTF8("pcg.hero.uid.v1\n" + technology + "\n" + uid_hex)
hero_card_id = "uid:" + lowercase_hex(SHA256(identity_material))
```

NFC-A 使用防冲突流程得到的实际 UID，通常为 4、7 或 10 字节。驱动负责处理级联协议中的 CT 字节；不得对最终 UID 中任意出现的 `88` 做字符串删除，也不得自行颠倒字节序。换 SDK 后须用同一实卡验证规范化结果相同。

随机 UID、会话 PUPI、空串、读卡失败后的随机 UUID，不能作为每日领取身份。后续支持 NFC-V／F 时必须明确各 SDK 的字节序和稳定性；仅增加枚举并不等于已通过兼容验收。Web NFC 不保证提供非空序列号，也不提供本规格所需的通用技术探测，因此不能承诺纯网页支持全部 legacy UID 卡。[W02](10_SOURCES_AND_MATERIALS.md#w02)

### 2.4 未登记 legacy 卡与身份一致性

未映射的稳定 NFC-A 卡，只有在成功探测并确认无有效游戏发行描述符，或已验证发行 catalog 明确标记 legacy UID 后，才允许用户明确登记成默认 m5.roles.v1 盲盒卡。未登记状态本身不发奖。不支持/失败的 NDEF 读取不能当作“无 NDEF”降级；仅 UID 读头需要已验证映射。否则同一发行卡可能被一个客户端认作 issued:、另一个认作 uid:，产生重复每日身份。未来有发行注册表时应将这些映射分发到各客户端，但不改变已经登记的身份。

## 3. PlayerSnapshot 与本机附加数据

### 3.1 随卡迁移的完整根对象

| 字段 | v1 语义 |
|---|---|
| `save_schema_version` | 整数 `1`，与 PCSV 头的 `snapshot_schema_version` 相同 |
| `snapshot_id` | 当前不可变快照的 UUIDv4；内容改变必须产生新 ID |
| `parent_snapshot_id` | 直接父快照 UUID；初始快照为 `null` |
| `history_tail` | 最多 16 个历史 UUID，按旧到新排列，不含当前 ID |
| `player_id` | 玩家 UUID；不因换卡或换设备改变 |
| `writer_device_id` | 创建此快照的设备安装实例 UUID；仅导出时不改 |
| `save_seq` | 同一谱系的内容修订计数，范围 `0..2^53-1`；不是全局同步时钟 |
| `modified_at_ms` | UTC 毫秒表示的逻辑内容更新时间，安全整数；不是最近一次写卡时间 |
| `game_calendar_offset_min` | 固定整数 `480` |
| `nickname` | 玩家昵称，遵守 Schema 长度约束 |
| `collection` | 完整收藏状态，以 Schema 定义为准 |
| `decks` | 完整牌组配置；不可只放当前对战牌组 |
| `wallet` | 完整钱包／材料余额 |
| `day_ledger` | 当前持有的每日领取账本，定义见下节 |
| `clock` | 绝对时间来源与高水位，定义见下节 |
| `extensions` | 可保留的扩展数据；同样计入存档容量 |

创建子快照时：`parent_snapshot_id = old.snapshot_id`，`history_tail = (old.history_tail + [old.snapshot_id])` 的末尾 16 项，`save_seq = old.save_seq + 1`，`writer_device_id = 当前设备`。对有有效时间的正常内容修改，`modified_at_ms = max(observed_utc_ms, old.modified_at_ms + 1)`；时间未知时只能维持逻辑递增，界面必须显示“时间未知”，不能把该值当作可信日历依据。到达安全整数上限时拒绝继续生成修订，不回绕。

导出同一个快照不改变 `snapshot_id`、`save_seq`、`modified_at_ms`、`writer_device_id`。若需要显示“上次写卡时间”，放入本机写卡回执；不能用 `exported_at` 覆盖内容时间。

### 3.2 不要求放入卡片的本机元数据

每设备按 `player_id` 隔离保存以下内容：

- 当前完整快照及其 canonical 明文哈希。
- `last_card_snapshot_id`、上次读到／验证写入的卡片哈希和写卡回执。
- 已验证过的本地祖先索引，帮助识别超过 `history_tail` 长度的谱系。
- 冲突双方的原始容器、解码快照、来源与选择记录。
- 本机领取／对战历史 journal、UI 设置、未完成写卡操作记录。

`last_card_snapshot_id` 表示曾实际读到或验证过的卡上版本，不能在本机内容更新时顺便更新。历史 journal 可以保留更多天；卡片必须至少包含当前账本规定的全部同日资格，不得为了腾容量悄悄删掉当日已领取卡号。

## 4. 游戏日与每日领取事务

### 4.1 固定日历

```text
day_id = floor((utc_ms + 28_800_000) / 86_400_000)
```

这相当于固定 UTC+08:00 的自然日，用于本游戏的 Asia/Shanghai 日界线。它不读取手机当前显示时区，不应用设备切换时区来刷新资格，也不用运行时长代替 UTC。人类可读日期由 `day_id` 换算，仅用于界面。

v1 参考实现的有效领取时间范围为 UTC `2000-01-01T00:00:00.000Z` 至 `2100-01-01T00:00:00.000Z`（两端包含），即 `946684800000..4102444800000` 毫秒。范围外返回时间不可用；范围内也仍需有效的来源状态，不能只看整数大小。

```text
day_ledger = {
  day_id: integer,
  claims: [{
    hero_card_id, template_id, claim_id, claimed_at_ms, pool_id, pool_hash
  }]
}

clock = {
  high_water_utc_ms: safe_integer,
  high_water_day_id: integer,
  last_source: "unknown" | "manual" | "device" | "network" | "server"
}
```

初始时间未知时，高水位为 `0`，`last_source = "unknown"`。没有有效绝对日期时，拒绝领取，但允许训练、查看收藏和保存已有存档。RTC 存在不代表 RTC 已设置正确；驱动必须明确给出时间是否有效。

若观测日早于 `clock.high_water_day_id`，返回 `CLOCK_ROLLBACK`，保留账本并暂停新领取；不得退回旧日或清空 claims。相同日内正常校时不会刷新资格，高水位只增不减。向未来改日期再改回来，可能需要等日历追上或明确执行时间修复；时间修复是有记录的管理动作，不能隐蔽地重置领取次数。

新日首次成功领取时，原子地建立新日账本，再写入本次 claim；旧日统计可留本机 journal。仅打开界面、读玩家卡或计算“今天还没领”不要求生成一个空的新存档版本。

### 4.2 领取键与抽取分工

```text
claim_id = lowercase_hex(SHA256(PCG-C14N-1({
  "domain": "pcg.claim.v1",
  "player_id": player_id,
  "hero_card_id": hero_card_id,
  "day_id": day_id
})))
```

其中 SHA-256 输入是 canonical JSON 的 UTF-8 字节。`pool_id`、`pool_hash` 和客户端版本不进入去重键。盲盒抽取种子包含池哈希，具体 ordinal 抽样和固定卡结果记录方式必须直接使用参考实现及黄金向量，不另用 `Math.random()`、语言内建 `hash()` 或各平台独立随机流程。

### 4.3 本地领取的事务边界

执行顺序必须为：

1. 确认已登录、没有未解决的存档冲突；识别合法英雄卡和当前内容配置。
2. 获取有效 `day_id`；校验时间高水位；查找当前 `(player_id, hero_card_id, day_id)` 是否已经提交。
3. 在该玩家的串行事务内重新检查资格，冻结内容池，计算固定／盲盒结果和重复补偿。
4. 同时修改收藏、钱包、`day_ledger.claims`、时间高水位以及快照谱系。
5. 将完整新快照持久化成功后，才发出 `HeroClaimCommitted` 并播放最终结果。

事务失败时，旧快照继续有效，不扣资格、不扣碎片、不显示最终中奖成功。事务已成功但界面或设备随后中断时，下次刷同一卡返回已提交结果；不得再次发放。只依靠 UI 按钮禁用不足以防重复，底层事务必须按 `claim_id` 幂等。

每个玩家的每个 `day_ledger` 内，`hero_card_id` 必须唯一。不同玩家共用同一实体英雄卡，分别在自己的账本记录，互不消耗。英雄卡在这个过程中没有任何写操作。

## 5. 业务状态机与重复感应

| 状态 | 允许的输入 | 处理与下一状态 |
|---|---|---|
| `LOGGED_OUT` | 玩家卡 | 读取、校验、对账；进入 `ACTIVE` 或 `CONFLICT` |
| `LOGGED_OUT` | 英雄卡 | 提示先刷玩家卡；不领取、不登记当日资格 |
| `ACTIVE` 且处于抽卡大厅 | 英雄卡的新一次感应，玩家确认领取 | 执行原子领取；成功后仍是 `ACTIVE`，本机可能比卡新；对战/卡册扫描只定位或查看，不领奖 |
| `ACTIVE` | 明确保存意图 | 冻结待保存版本，进入 `SAVE_ARMED` |
| `SAVE_ARMED` | 当前玩家卡 | 重新读卡、对账、检查容量，然后进入 `WRITING` |
| `SAVE_ARMED` | 他人玩家卡／英雄卡 | 拒绝写入并说明对象错误 |
| `WRITING` | 读写完成 | 进入 `VERIFYING`；此时还不能宣告保存成功 |
| `VERIFYING` | 新鲜读回数据匹配 | 记录写卡回执，进入 `ACTIVE` |
| `VERIFYING` | 无法立即重新读取 | 进入 `WAIT_VERIFY_RETAP`，要求重新贴卡完成验证 |
| `CONFLICT` | 选择一份完整副本 | 两份均先备份；选中副本变成当前版本；回到 `ACTIVE` |

持续把同一张卡放在天线上，不是一次次新的刷卡动作。可以确认离场的驱动应在稳定检测到移开后再重新武装；不提供可靠离场事件的 API 必须使用单次扫描会话或明确 UI 操作来重新武装。特别是登录后的同一轮检测回调，不能被误解释为“再次刷玩家卡保存”。

在 ESP32 等可以可靠检测移开／再贴的设备上，主动再次贴当前玩家卡可直接作为保存意图，无需强行增加额外确认页。在 iOS 或纯 Web 会话中，可以用“保存到玩家卡”按钮建立一次写会话，然后要求玩家再贴卡；这仍然满足主动刷卡保存，不是后台自动同步。平台差异见第 05 章。

换玩家时，本机已经持久化的进度继续保留。若当前玩家比卡新，界面显示尚未写卡状态；不能自动把当前玩家数据写到新玩家卡上。对战进行中或还有未提交业务事务时，不开始存档写入；先结束当前安全边界，再要求明确的保存操作，不能在后台悄悄排队写卡。

## 6. 登录时的版本选择

### 6.1 先验证，再比较

只有完整容器校验、解压、canonical 校验和 Schema 校验通过的快照，才参与比较。比较的是 payload 的 `modified_at_ms`，不是卡片文件时间、写卡时间、NFC 扫描时间或 `slot_generation`。

“A 是 B 的祖先”需要在 B 的 `parent_snapshot_id`、`history_tail` 或本机已经验证过的祖先索引中找到 A。`save_seq` 大、时间新、`writer_device_id` 相同，都不能单独证明祖先关系。

| 本机 L 与卡上 C 的关系 | 必须行为 |
|---|---|
| 本机没有该 `player_id` | 原子导入 C；登录完成；不回写 |
| ID 和明文哈希相同 | 使用已有相同版本；不新建修订、不写卡 |
| C 是 L 的已知祖先，L 的 seq 和修改时间均更大 | 使用 L，标记比卡新；不自动写卡 |
| L 是 C 的已知祖先，C 的 seq 和修改时间均更大 | 备份 L，原子导入 C；不回写 |
| 同一 ID 对应不同哈希 | 冲突或损坏；保留原件，不自动择一 |
| 修改时间相同但 ID／哈希不同 | 冲突；不能按设备名或读取顺序猜测 |
| 已知谱系与 seq／时间先后矛盾 | 冲突；不能仅因为时间更大覆盖 |
| 两个不同 ID 的先后关系不能证明 | 冲突，包括并行分支；不同 writer 尤须保守处理 |
| 卡上是未来不可写版本 | 可按兼容规则只读；旧客户端不得降级覆盖 |

冲突页显示双方的修改时间、seq、设备标签、收藏数和钱包摘要，用户选择**整份副本**。选择前保存双方原始字节和校验值。不得自动相加碎片、合并领取奖励、取两个账户余额的最大值，或把两个分支的盲盒结果都收入收藏。

选择一份副本不是一次新的领取，不需要伪造新的奖励事务。下一次真正修改以选中的快照为父；放弃的分支保留在本机冲突备份中。没有已验证副本时，读取失败不能解释为空白新玩家。

### 6.2 写入前必须再读一次

保存按钮按下后，卡上版本可能已经被另一设备修改。写前必须重新读取当前卡，并用当前本机快照进行同样的对账。如果发现新的分支，进入冲突处理；不能因为“登录时读过”就覆盖。

若当前卡上已经是相同快照，记录“已一致”，无需消耗一次写入。如果卡上是本机的正常旧祖先，允许保存较新的本机。若卡上是本机的较新后代，先按规则导入；不把旧本机写回去。

## 7. 保存事务与迁移承诺

### 7.1 唯一成功路径

```text
明确保存意图
→ 本机最新完整快照已持久化
→ 读目标卡并对账
→ 冻结该快照并编码、测量容量
→ 写卡
→ 从卡重新读取完整数据
→ 解压与 SHA-256 / 头 / Schema 校验
→ 与待写版本的 snapshot_id、完整明文哈希一致
→ 本机记录已验证回执
→ 显示“已保存，可换设备”
```

写入过程中暂停该玩家新的内容修改，避免 UI 同时抽卡导致“刚保存完又少了一张”。不要求暂停网络心跳或对战房间的只读消息。

写卡只导出已经存在的不可变快照。卡写失败、卡移开、电池断电或读回不匹配时，本机当前快照不回滚，也不从钱包中撤销已成功的领取；显示“进度在本机，写卡未验证成功”。

### 7.2 失败语义

| 情况 | 卡片承诺 | 本机与 UI |
|---|---|---|
| 本机持久化失败 | 不开始写卡 | 保留旧版本，报告本机保存失败 |
| 容量未知或容量不足 | 不开始覆盖 | 显示所需／可用字节；保留本机，可换大卡 |
| 卡只读、权限不足、型号未适配 | 不写锁位、不自动格式化 | 提示该卡不能用于此保存 profile |
| 写操作报错 | 不承诺卡仍可读 | 本机有效；可显式重试或修复 |
| API 返回成功但未读回 | 仍未完成迁移确认 | 保持 `VERIFYING` / `WAIT_VERIFY_RETAP` |
| 读回内容或哈希不一致 | 保存失败 | 保留本机和故障记录，不更新“已写卡”标记 |
| 写成功后本机回执落盘失败 | 卡可能已经有效 | 下次重新读卡确认；不能凭缺回执再发奖励 |

断电恢复后，如有 pending write 回执，先读卡核对其目标 `snapshot_id` 和哈希。匹配则补记成功；不匹配则保留本机并等待用户下一次保存，不自动重写。

## 8. PCSV v1 二进制容器

### 8.1 明文编码

payload 是完整 `PlayerSnapshot` 的 `PCG-C14N-1` UTF-8 JSON。它是本项目受限 canonical JSON，**不是完整 RFC 8785 JCS**：

- 对象键必须是非空 ASCII，按 ASCII 顺序排列。
- 字符串值保留原 Unicode 标量，不做 NFC／NFD Unicode normalization；不允许孤立代理项。
- 使用 JSON 必需的转义，不增加无意义空格或换行。
- 数值仅允许安全整数 `[-9007199254740991, 9007199254740991]`；禁止 float、NaN、Infinity；具体字段可再限制为非负。
- 数组保持原有顺序；最大嵌套深度为 32。
- 解压后的明文最多 `65536` 字节。

逐字节输出以参考实现与 fixtures 为准。SHA-256 始终计算**完整、解压后的 canonical 明文字节**，其中包括 `snapshot_id`；`snapshot_id` 本身是 UUID，不参与递归求哈希。

### 8.2 精确 96 字节头

所有数值为无符号 little-endian。UUID 是 RFC 常规字节顺序的 16 字节；不是 Windows GUID 的混合端序布局。

| 偏移 | 长度 | 字段 | v1 值／校验 |
|---:|---:|---|---|
| 0 | 4 | `magic` | ASCII `PCSV`：`50 43 53 56` |
| 4 | 1 | `container_version` | `1` |
| 5 | 1 | `storage_profile` | `1=NDEF_SINGLE`；`2=RAW_DUAL` |
| 6 | 1 | `codec` | `0=canonical JSON`；`1=zlib` |
| 7 | 1 | `flags` | v1 为 `0`；未知位不能忽略后覆盖 |
| 8 | 2 | `header_bytes` | `96` |
| 10 | 2 | `snapshot_schema_version` | 与 payload `save_schema_version` 相同 |
| 12 | 4 | `stored_len` | 头后有效存储数据长度，不含填充 |
| 16 | 4 | `plain_len` | 解压后的 UTF-8 长度，`1..65536` |
| 20 | 4 | `slot_generation` | 物理容器写入代次；首次写入为 `1` |
| 24 | 16 | `snapshot_uuid` | 与 payload `snapshot_id` 相同 |
| 40 | 32 | `payload_sha256` | 完整解压后 canonical 明文的 SHA-256 |
| 72 | 8 | `modified_at_ms` | 与 payload 相同且在安全整数范围内 |
| 80 | 8 | `save_seq` | 与 payload 相同且在安全整数范围内 |
| 88 | 4 | `header_crc32` | 下述 CRC，覆盖字节 `[0, 88)` |
| 92 | 4 | `commit_marker` | 有效为 ASCII `DONE`：`44 4F 4E 45` |

CRC 为 CRC-32/ISO-HDLC：反射多项式 `0xEDB88320`，初始值 `0xFFFFFFFF`，最终 xor `0xFFFFFFFF`，输入／输出反射；等价于 `zlib.crc32(header[0:88]) & 0xFFFFFFFF`。CRC 不覆盖自身及 commit marker。CRC 与 SHA-256 用于损坏检测，均不是来源认证。

`codec=1` 指 RFC 1950 zlib 包装、内部 DEFLATE；不是 gzip，也不是裸 DEFLATE。禁止 preset dictionary。解码器必须限制输出长度，恰好消费 `stored_len` 字节，只接受一个完整压缩流，拒绝尾随数据、截断流和解压长度不匹配。不同压缩器可以生成不同压缩字节，但必须解出同一个 canonical payload；互操作比对以明文哈希为准。

`slot_generation` 与 `save_seq` 相互独立。重新导出同一份内容可以产生新的物理代次；不得把代次当作玩家内容的新旧顺序。达到 `0xFFFFFFFF` 后拒写，不能静默回绕；如需重新配置卡片，走显式初始化流程。

### 8.3 容器解析顺序

1. 检查头长度、magic、版本、profile、flags、marker、header CRC。
2. 检查 `stored_len`、`plain_len` 和实际剩余容量，先做边界检查再分配内存。
3. 读取正好 `stored_len` 字节，按 codec 解码，确认明文长度不超过上限。
4. 校验 SHA-256；严格解析 JSON；拒绝重复对象键、非法 UTF-8 和不支持的值。
5. 重新 canonical 编码并要求与原明文字节相同；验证 Schema。
6. 比较头与 payload 的 schema、UUID、seq、修改时间，全部相同才接受。

## 9. 两个存储 profile 与真实容量

### 9.1 `NDEF_SINGLE`：一条完整 NDEF 记录

使用一个 MIME record，类型为 ASCII `application/vnd.pulsecard.save`，共 30 字节；无 record ID。record payload 为 `96B PCSV 头 + stored payload`。v1 的参考编码固定使用非 short-record、非 chunked 的单条记录（MB=1、ME=1、SR=0、IL=0、TNF=MIME，首字节 `0xC2`）。

```text
NDEF message bytes = 6 + 30 + 96 + stored_len = 132 + stored_len
```

因此，若平台**实际报告的最大 NDEF message 长度**是 8192 字节，`stored_len` 最多为 8060。这个 8192 不包含标签自身 CC、TLV、文件管理和 NLEN 等存储开销；不能直接拿芯片广告容量代入。

高层 NDEF API 通常覆盖整条消息。即使放两份 record，也不等于两个独立随机写槽；掉电时可能连整个 NDEF 消息都不可读。本 profile 的 `DONE` 只用于格式有效性，**不承诺写入原子性或保留旧快照**。写失败的恢复源是本机已持久化副本。只有获得特定卡型／驱动的实测保证，才可增加更强的硬件能力声明。[A02](10_SOURCES_AND_MATERIALS.md#a02) [D02](10_SOURCES_AND_MATERIALS.md#d02) [W02](10_SOURCES_AND_MATERIALS.md#w02)

玩家卡是游戏专用卡。若当前 NDEF 消息还有未知业务记录，v1 不默默删除它们：应拒绝专用卡写入，或在独立初始化流程中明确处理。不得将旅游票、门禁卡等未知卡自动转换为存档卡。

### 9.2 `RAW_DUAL`：可靠随机写入的双槽

本 profile 的**逻辑有效区**固定为 8192 字节。它可以映射到一个合适的应用文件，也可以映射到两个独立 4096 字节文件，但驱动必须保持以下逻辑布局：

| 区域 | 逻辑偏移 | 长度 | 内容 |
|---|---:|---:|---|
| slot 0 | 0 | 4096 | 96 字节头 + 最多 4000 字节 stored payload |
| slot 1 | 4096 | 4096 | 同上 |

头之外的尾部为无意义填充，不属于哈希范围。每槽独立校验。只有明确的新卡初始化流程可以建立首份快照；虚拟卡以全零 8192 字节表示未初始化卡，首写 slot 0、generation=1。一个非空但没有有效槽的卡是损坏／未知卡，不能自动当作新卡覆盖。

存在有效槽时，选择最高有效 generation 作为已提交版本，下一次写另一槽，generation 加一。两个有效槽的 `player_id` 不同、同 snapshot_id 但内容 hash 不同，或 generation 相同但内容不同，都属于容器冲突，不按槽号猜测。给卡换绑定玩家必须走显式重新初始化流程，不能留下混合玩家的两个有效槽。

扫描两个槽时，必须区分“普通损坏／未提交槽”和“可识别但本端不理解的未来格式”。发现未来容器版本、codec、flags 或未来 Schema，不得把它一律当坏槽忽略，再选旧 v1 槽进行覆盖；保留原字节并进入只读／升级处理。允许回退的是已经确认无效的中断写槽，不是可能有效的未来存档。

严格写入步骤：

1. 保持当前有效槽不变，选另一个槽为目标。
2. 将目标 `commit_marker` 清为 `00 00 00 00`，读回确认无效后才改目标其他内容。
3. 写目标 payload 和头的前 92 字节；不要触碰另一槽。
4. 重新读取目标内容，按“未提交”模式校验除 marker 外的完整预期数据。
5. 最后写 `DONE` marker，再读回整个槽，通过正常解析器验证。
6. 保留旧槽；不必再写一个共享“当前槽指针”。

这个恢复模型以以下能力为前提：驱动确实支持独立地址／文件写入；写目标槽的掉电不会重写另一槽；底层写粒度、擦除粒度、卡上事务／备份文件行为已经核实；底层不会把整个应用文件透明重写。若这些条件不成立，必须降级为 `NDEF_SINGLE` 或拒绝声明 `RAW_DUAL`。

双槽保障是“在已验证故障模型内，提交失败仍保留旧有效槽”，不是“任意 NFC 卡永不损坏”。不得把 NDEF message 中两个数组元素叫作抗断电双槽。首次初始化前没有历史有效槽，也不存在可恢复的旧卡存档。

### 9.3 容量判断与选卡

| 标签／卡族 | 官方容量事实 | 对本项目的含义 |
|---|---|---|
| NTAG213 | 144 字节用户读写区 | 可用于已验证 UID 身份识别或极短记录；本项目 JSON 英雄描述符也须测长度，不承诺装入；不能当完整玩家存档卡 |
| NTAG215 | 504 字节用户读写区 | 同上，不能按“支持 NFC”就承诺玩家快照可容纳 |
| NTAG216 | 888 字节用户读写区 | 数据增长后很容易超出；不是推荐完整存档介质 |
| NTAG424 DNA | Type 4；416 字节总文件存储，其中 NDEF 文件 256 字节 | Type 4 表示协议，不代表大容量 |
| MIFARE DESFire EV3 | 官方系列提供 2/4/8/16 KB 档位和可配置文件系统 | 候选大容量卡；实际应用／NDEF 文件可用空间须初始化后查询 |

容量依据来自 [N01](10_SOURCES_AND_MATERIALS.md#n01)、[N02](10_SOURCES_AND_MATERIALS.md#n02)、[N04](10_SOURCES_AND_MATERIALS.md#n04)。`KB` 商品标注与本规格的 `KiB=1024 bytes` 不能混用；采购验收必须记录实际字节数。

推荐从**格式化后有效区达到 8 KiB 级以上**的卡型开始评估，优先验证 NFC-A / Type 4 的跨平台路径。标称 8 KB 芯片可能扣除文件／应用开销后不能提供本规格完整 8192 字节有效区；必要时选更大芯片或明确选择较小 NDEF profile 容量，不能虚报。

每次写入都必须序列化实际快照、计算实际压缩长度和完整容器长度，再与目标能力比较。启用 zlib 是优化，不是“以后都能放下”的承诺。超容量时：

- 返回容量错误并显示所需／可用字节。
- 保留完整本机存档，继续允许本机游戏。
- 允许使用更大、已验收的玩家卡重新保存。
- 不删当日领取记录、不丢扩展字段、不截断收藏，不用 URL／玩家 ID 代替完整快照冒充迁移成功。

## 10. 未来版本、损坏与信任层

未知字段必须原样保留其语义值并参与 canonical 编码和哈希。旧端无法保留未来字段，或未来字段超出 `PCG-C14N-1` 子集时，只读或拒绝写入；不得反序列化成旧结构后丢掉字段再保存。未知 `save_schema_version`、容器版本、codec 或 flags，同样不得降级覆盖。

默认信任层是 `casual_local`：本机是当前进度的持久化权威，卡是用户明确导出的离线副本。校验和、确定性 claim_id 和时间高水位能避免常见重复回调、误操作和单机回拨，但**无法在完全离线的多设备之间证明全球只领取一次**。同一旧卡快照可在两台设备上产生分支，改时钟／恢复旧备份也不能靠普通标签彻底防止。

可选 `server_verified` 可以让服务端签发每日领取回执、验证时间和资格，或者将竞技牌组限定为服务端认可集合；它是独立能力，不得成为本地模式的强制联网条件。服务器也不得把在线对战接入解释为自动云迁移授权。

## 11. 最小验收项目

完整恢复测试见 [07_ACCEPTANCE_AND_RECOVERY.md](07_ACCEPTANCE_AND_RECOVERY.md)。本章至少要求：

1. 玩家卡只登录，保持在读头上不触发写卡；移开后再次明确保存才写。
2. 固定／盲盒卡同玩家同日重复扫描只产生一个领取；另一玩家可以领取。
3. 本地事务前后分别模拟崩溃，奖励和账本始终同时存在或同时不存在。
4. 本机较新、卡较新、同时间异 hash、并行分支、谱系超出 16 代均有明确处理。
5. 领取后不写卡换设备，只能看到旧卡版本；验证写卡后换设备能恢复完整收藏及当日资格。
6. NDEF 模式写一半失败，本机仍完整；不能假定卡上旧消息必然可读。
7. RAW 模式在清 marker、写 payload、写头、最终 marker 各阶段掉电，只选择校验通过的槽。
8. 容量边界、解压超限、未知字段、坏 CRC／SHA、非法 UTF-8、重复 JSON key 均能拒绝。
9. Web／iOS 无法即时新鲜读回时停在待验证状态，不能提前显示“可迁移”。
10. 虚拟卡文件适配与真机采用相同容器和业务状态机；虚拟测试通过不等于硬件掉电测试通过。
