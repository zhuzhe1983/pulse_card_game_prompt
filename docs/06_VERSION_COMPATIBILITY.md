# 06 · 版本与兼容策略

> 目标：独立开发的 ESP32、Android、iOS、macOS、Windows、Linux、Web 客户端可以共享同一场对战；增加设备、展示或卡片时，不把所有现存设备一起变成不可用。本文定义发布与升级契约，不表示每个客户端已实现全部功能。

## 1. 五个版本轴，内容另用精确哈希锁定

不要用一个“App v2”决定所有兼容性。以下版本轴独立变化：

| 轴 | 示例 | 由谁判断兼容 | 变化规则 |
|---|---|---|---|
| 应用版本 `app_version` | `0.1.0` | 平台发布器/安全策略 | 可修UI、驱动和功耗，不自动改变战斗规则 |
| 线路协议 `protocol_version` | `1.0` | HELLO/CAPS | 明确协商双方实现的相同版本；基线PCG/1.0 |
| 规则契约 `rule_id` / 状态 `ruleset_id` | `pcg.core.v1` | 引擎与SELECT/READY | 语义不可变；新行为需新ID或明确的新规则扩展 |
| 保存格式 `save_schema_version` | 已发布存档schema规定的整数版本 | 存档读取器/迁移器 | 旧程序不能直接改写未来格式；备份并显式迁移 |
| 实体卡格式 `container_version` / `hero_schema_version` | 已发布卡片schema规定的版本 | CardReader/卡片解析器 | 能读NFC不代表理解卡片内容；未知格式不猜测 |

内容另有 `content_pack_id`（例如 `m5.core.v1`）、`content_version`（发布标签）和 **`content_hash`**（精确规则内容的SHA-256）。version便于人读，hash用于证明双方装载了同一份规则材料。改了卡片数值或合法排位，即使还叫同一个模板名，也不能继续用原hash。

`pcg.core.v1` 的语义继续冻结，给已经按三局点数实现的裁判和黄金向量使用。单局回合战使用新编号 `pcg.clash.v0`，试玩卡表在 `content/clash_playtest.json`，不写入 `m5.core.v1` 的内容哈希。旧联机消息在迁移完成前仍只承载 `pcg.core.v1`。

PCG-F1 的 `frame_version=1` 只是数据报封装版本。它不同于 PCG envelope 1.0，也不同于 ESP-NOW 硬件/SDK所谓的 v1/v2；禁止把这几个“1”当作同一含义。

保存/实体卡文档如果使用带命名空间的实际版本字段，以它们的schema为准；本表表达独立的生命周期，不要求把两个版本字段硬塞进战斗envelope。

## 2. 一场对战的兼容判定

能一起开局须同时满足：

1. 双方通过认证连接到同一个AuthorityAdapter；已协商的PCG版本相同。
2. SELECT指定的规则ID被客户端实际实现，且实现通过该规则ID的golden fixtures。
3. 客户端已验证本地内容包，对SELECT的`content_hash`作精确一致比较。只比较pack名、版本字符串或拥有某张NFC卡不够。
4. SELECT的每个required_feature与required_opcode都存在于客户端能力集（trait以`trait:`前缀纳入opcode数组）；所有选定卡片满足内容schema和该引擎的约束。
5. 客户端在 READY 中回显同一个 selection、rule 与 content_hash，并提交有顺序的 `deck_template_ids[10]`。authority 按房间允许池与规则验证每人的牌组；所有牌组有效且最后一个玩家 READY 之前，不能开始。

如下情况可以互战：M5Dial App0.1.0与iPhone App0.8.0都实现PCG1.0、`pcg.core.v1`和同一content_hash。反过来，两台都显示App0.8.0但加载了不同数值包，仍不能进入同局。

```text
can_start = authenticated
         AND same_selected_wire_version
         AND exact_rule_id_supported
         AND exact_content_hash_loaded
         AND all_required_features_supported
         AND all_required_opcodes_supported
         AND all_submitted_decks_valid
         AND all_players_ready_for_same_selection
```

这不是客户端自由裁决的布尔值；authority必须最终检查所有已认证玩家的READY。客户端也必须本地验证，不能盲目相信房主写来的“compatible=true”。

## 3. 哪些升级可以独立发布

| 改动 | 应变化的版本/材料 | 旧客户端的行为 |
|---|---|---|
| 修复按键、旋钮、E-Ink刷新或断线提示 | app_version | 规则/协议不变则正常互战 |
| 新设备，仅新增Transport/Screen/Input Adapter | app_version及平台能力 | 运行同PCG与同规则测试；不建立独立游戏分支 |
| 角色新头像、音效、翻译 | 展示资源版本；必要时内容发布标签 | 缺资源用本地fallback；不能影响分数和合法动作 |
| 新卡只组合已支持opcode，数值均在既定范围 | 新content_version与content_hash | 能完整验证schema和opcode时可加载后READY |
| 卡片原有分数、目标、合法排位或效果参数变化 | 新content_version与content_hash；保留旧manifest | 进行中的旧hash对局保持原值；新局由房间明确选择 |
| 新opcode、改变目标选择时序、改变计分/通过规则 | 新rule_id或明确的已协商规则扩展；通常也新hash | 不认识则拒绝该模式，可继续旧core模式 |
| 新可省略展示消息 | 协商的optional feature / `X_*` 类型 | 不认识就按PCG规则确认并忽略 |
| 新必需消息、改变原字段含义或字段类型 | 新wire版本/必需feature | 无共同版本时拒绝连接，不近似解释 |
| 新存档布局 | 新save schema与迁移器 | 不支持的旧客户端只读/拒绝修改，保留原始字节 |
| 新NFC卡载荷格式或身份机制 | 新card format及解析能力 | 可提示“需要支持此格式的版本”；不生成猜测角色 |

### 3.1 展示更新不能伪装成规则更新

展示字段只能出现在明确的`presentation`或资源分支中。新客户端可以理解更多纯展示字段；旧客户端忽略它们时，合法动作、随机流程、分数、目标、出牌次数和结果必须完全一样。

`content_hash`计算范围由内容包规格规定，wire层不另发明第二种hash算法。只有内容规格**明确排除**的展示资源可以独立更换而不改hash；如果某个展示字段仍位于被hash的manifest范围，修改它也必须产生新hash。发布器不能“认为只是头像”就继续冒用旧散列值。

### 3.2 新卡能否热加载

符合以下全部条件，新卡可以走数据包热加载，而不要求刷全部固件：

- 卡包schema被客户端支持；数值/长度/枚举都在基线界限内。
- 效果只用客户端已经实现且通过测试的opcode与参数结构。
- 包中没有脚本、远程执行表达式、动态原生代码或未知强制语义。
- 卡包按规格验证hash与发布来源；验证通过后以不可变文件/记录安装。
- 内存、完整snapshot大小、实例数和JSON深度仍在PCG/1.0上限内。
- 仅在**新局**或未开局的新SELECT后启用，不在一局中途替换。

能识别template_id、能画卡面、能显示effect说明，三者都不能替代opcode支持。若新牌包含未实现的效果，旧客户端可在收藏图鉴里以“暂不支持对战”显示纯展示信息；不得把它当作无效果牌出场。

## 4. 保留一个稳定的基础模式

每个发布周期 SHOULD 保留`pcg.core.v1`实现、受支持的基础内容manifest及对应golden fixtures。更新包可以增加模式，不必替换已有core引擎。资源紧张的ESP32可以只装core与少量已验证包；手机/Web可同时支持多个规则，但具体每局只能锁定一个。

界面建议区分“可对战”和“需要新能力”，而不是看应用版本是否最新。创建房间时列出实际共同支持的规则/卡包；缺新内容的朋友可以选择大家都有的旧基础包。若没有共同受支持规则，就明确说明所缺ID/效果能力，不能自动把不同卡改成近似效果。

旧内容manifest是复盘、重连、存档和排查问题的依据，SHOULD 保留只读副本。若服务因安全或严重规则问题禁用某个旧hash，应同时保留其解释材料用于历史查看；不要把旧记录指向修正后的新数值。

每个已开始的match至少固定：match_id、规则ID、内容hash、内容包标识、参与者、初始完整状态/必要种子、动作日志与结果日志。种子及完整状态仅由authority保存，不下发对手。重放使用原规则与原manifest，不按“今日最新牌面”重新计算旧比赛。

## 5. 不允许悄悄变化的契约

### 5.1 相同ID意味着相同语义

以下改变不能继续假称原来的规则ID：回合顺序、通过后是否还能出牌、结算时机、平局处理、稳定/护盾优先级、目标合法性、随机算法、实例ID生成方式、动作revision增长方式。修复实现使其回到已经冻结的规范属于应用修复；改变规范本身则属于新规则契约。

同一个content_hash不能对应两份不同规则材料。SHA256是内容一致性标识，不是发布者签名或身份认证；客户端需要通过可信发布通路/已有签名机制确认来源。校验hash不意味着可以执行任意来源的代码。

### 5.2 协议的向前兼容有范围

PCG1.0已知消息使用封闭schema，未知规则字段按错误处理，避免`target_instance_id`拼错仍被当作无目标。只有`presentation`内未知字段和明确可省略的`X_*`消息可忽略。

后来增加的新必需能力必须在HELLO/SELECT中显式协商。服务器不得给旧客户端发新字段并寄望它“忽略也差不多”。若新消息是可省略展示消息，用`X_*`；若缺它会改变玩法、身份、安全或持久化行为，它就不是optional。

wire minor版本的新增能力也必须取双方实际实现的交集，不能仅因主版本都为1就按最新版解析。每条消息的protocol_version等于本session已协商的版本，禁止混发。

## 6. 存档读写和迁移

旧应用不得把未知未来save读成空收藏后覆盖。存档读取采用如下策略：

| 存档情况 | 允许行为 | 禁止行为 |
|---|---|---|
| schema已支持，规则/内容已安装 | 正常读写、启动该规则的离线模式 | 自动切换到新hash重新计算 |
| schema已支持，缺旧内容包 | 保留数据并提示安装该hash的包；展示已知元数据 | 用“相同名字”的最新卡包顶替 |
| schema比客户端新 | 保留原始文件；只读已明确可解析的安全元数据，或明确拒绝打开 | 去掉未知字段再保存、初始化成新空档 |
| 老schema且有已验证迁移器 | 先备份，迁移到新副本，验证成功后原子切换 | 边解析边原地覆盖；失败后丢弃旧档 |
| hash/校验失败或内容损坏 | 隔离损坏副本、提供恢复/重新获取路径 | 静默把未知值变成0或无效果牌 |

迁移器 MUST 是版本对版本的确定过程，并记录from/to版本、原文件摘要、完成状态。应保留原始备份、验证新文件schema与引用内容，然后原子替换指针。写入中断后只能看到完整旧档或完整新档。降级应用可以继续读其认识的旧档副本；不得把未来档“降级保存”而删除它不认识的内容。

账号云存档的并发冲突必须由存档服务版本号/ETag或等价控制处理；PCG对战的revision不是账号收藏档的revision。不能因为最后一次联网较晚，就用旧设备的空列表覆盖服务器收藏。

进行中的match恢复要求原规则、原hash和原裁判日志仍可用。没有这些材料就明确拒绝恢复；显示历史摘要可以，但不可编造同一match的延续结果。

## 7. 实体NFC卡兼容

CardReaderAdapter负责从设备可用读卡器读取字节；CardParser负责验证玩家卡 container_version／英雄卡 hero_schema_version 和内容。新增读卡器驱动不必改变规则；新增卡格式也不能强迫已发行旧卡报废。

兼容客户端 SHOULD 继续支持已发布的基础英雄卡格式。它可以把实体卡映射到同一template/个人收藏条目，再由当前房间选择的内容包解释战斗值。卡上的展示名、旧印刷数值和设备本地缓存都不能覆盖authority已经锁定的manifest。

未知卡格式、未知必需字段或不支持的身份机制，应提示具体能力缺口，并保留可安全显示的卡面信息。不要仅凭读到了UID，就把卡认作可信授权、生成永久资产或把未知效果默认为none。原始UID与身份证明不得随battle COMMAND或对手snapshot传播。

将卡面展示资源与规则模板分离，有利于同一实体卡跨多个内容版本继续使用；版本选择必须在房间中明确。收藏身份变化和转移按卡片/所有权规格处理，不由battle协议猜测。

## 8. 哪些情况才要求升级

可以要求升级的范围应尽量是**具体服务或模式**：

- 修复认证、密钥处理、数据损坏等已知安全问题，当前在线服务不能安全继续接受该版本。
- 用户选择的模式确实需要客户端没有实现的必需协议能力、opcode或save/card格式。
- 服务明确停止支持某个已存在的线路版本，并给出可验证的替代支持信息。

仅因有新头像、更多设备适配、某人装了新版本，或运营想统一版本号，不应阻止旧基础模式。在线服务拒绝旧客户端时，旧应用仍可使用自己已支持、已保存且有效的离线规则/卡包和旧存档；不能为了逼在线更新而擦除它们。也不能承诺未来所有系统平台永远允许安装旧应用；这是平台生命周期，和游戏自己的版本拒绝策略不同。

用户取消升级后，应保留当前档案与卡片数据。无法玩新模式时显示所缺能力及能继续玩的模式。不能用“可能不兼容”替代明确的required_feature/opcode/schema原因。

## 9. 给独立AI coding agent的发布要求

每个平台实现者交付时必须声明：

1. app/platform版本、支持的PCG线路版本、PCG-F1或流式Adapter情况。
2. 实现的rule_id、required opcode/trait集合、可加载的内容schema范围与实际manifest hash。
3. 可读可写的save版本、可读card格式；对于未来格式的只读/拒绝策略。
4. 对本项目共同golden fixtures、canonical JSON字节向量、二进制帧向量和错误案例的测试结果。
5. 明确的认证/authority模式：本地可信房主或专用服务；不要用硬件名称替代安全与兼容声明。

不允许平台各自“优化”规范：例如Android用浮点算分、iOS根据卡面说明推断效果、ESP32把未知字段默认为0、Web用最新内容覆盖选定hash，都属于不兼容实现。必须修复到共同契约，或声明新的不兼容规则/协议版本并明确协商。

## 10. 最小兼容验收矩阵

| A | B / 输入 | 预期 |
|---|---|---|
| ESP32旧App，PCG1.0，core.v1，hash H | iOS新App，同PCG/规则/H | 能互战，UI差异不影响结果 |
| 两端同App号、同pack名 | 内容hash H与H2不同 | 不开局；等待共同内容选择 |
| 旧客户端支持现有opcode | 新数据包只含现有opcode且验证通过 | 可以加载、READY、互战 |
| 旧客户端能显示模板 | 新包需要未知opcode | 不能READY；可以继续旧core模式 |
| 旧PCG1.0客户端 | 未知`X_ROOM_EMOTE` | 忽略显示扩展，状态不变 |
| 旧PCG1.0客户端 | 新必需消息/未协商feature | 明确拒绝，不能跳过后继续 |
| 旧save写入器 | 未来save schema | 原文件字节不变，不生成空档覆盖 |
| 新save写入器 | 迁移途中断电 | 完整旧副本或验证后的新副本可恢复 |
| 进行中的hash H对局 | 发布了H2平衡包 | 本局仍按H；新局才能SELECT H2 |
| 旧卡格式 + 新读卡器 | 同规则模板映射 | 老卡继续使用，战斗数值由所选manifest决定 |
| 未知card格式 | 读取到了UID | 明确不支持；不猜测角色/所有权/效果 |
| 旧在线客户端被安全策略拒绝 | 已知旧离线存档与包 | 在线拒绝不破坏离线已知数据 |

所有案例的共同前提是“实现和材料真的在场”，不是版本字符串写对即可。`04_WIRE_PROTOCOL.md`的精确握手、schema、视图隔离与幂等约束共同构成互战契约。
