【以下全部是给 coding agent 的执行指令】
你是本项目的实现工程师。请直接开发目标平台的可运行客户端，持续完成已授权的代码、构建与验证工作。先阅读完整规格，不要把任务替换为概念方案、静态界面或另写一种牌类玩法。不要擅自部署公开服务、发布到应用商店或写入未知实体卡。

1. 先读取 README.md、CONTRACT.json、docs/00_PRODUCT_AND_DECISIONS.md、docs/01_GAMEPLAY.md、docs/03_NFC_PLAYER_SAVE.md、docs/04_WIRE_PROTOCOL.md、docs/06_VERSION_COMPATIBILITY.md 与 docs/12_LOBBY_AND_SESSION.md。随后读目标硬件适配、风格、验收、参考数据章节。不要因文件多而只读摘要。
2. 检查现有仓库、实际依赖、板卡与读卡器资料。按 templates/TARGET_PROFILE.json 补全目标配置。用户没给目标时，先做 Web 开发基线、可切换 MockReader 和 WSS 连接，以及本地裁判服务；如明确给了目标，不得换成自己更熟悉的平台。没有实物可以实现并测试适配边界，但不得声称真机已通。
3. 以 CONTRACT.json + schemas + content/core_pack.json + golden fixtures 为共同契约。docs 解释产品行为，reference/ 是可执行的确定性参考。发现矛盾时记录具体字段和案例，按已冻结的同版本向量验证；不得修改向量使自己的不同规则通过。没有授权不要改协议、数值、牌数、日期算法、存档迁移方式或核心 opcode。
4. 依次完成：纯规则与向量验证 → 本地可玩 UI/AI → 玩家快照与模拟读卡 → 真实 ReaderAdapter → 通用 WSS 联机与恢复 → 目标额外传输 → 可访问性/性能/失败恢复。可以并行开发独立适配器，但不能把尚未定义的业务逻辑藏在 UI 回调中。
5. 规则必须是确定性 reducer；网络、NFC、文件系统、时钟、语言与动画全部通过适配器。battle 单元不访问随机时钟、NFC UID 或平台 UI。客户端可以预览，唯一 authority 才能裁决。禁止双方各自接受自己的结果。
6. 两种实体卡严格区分：玩家卡登录/显式保存；英雄卡固定领取或每日盲盒。claim/login/export/battle shortcut 是不同扫描上下文。刷英雄卡不保存玩家进度，登录玩家卡不自动把较新本机进度写回。只有完整快照写入后回读验证成功，才显示“可迁移”。
7. 同一玩家同一英雄卡同一游戏日只领取一次；领取结果、去重账本与本地快照一起原子提交。断电重试不能重抽。不要把 NFC UID 当成不可伪造密钥，或声称离线账本能防跨设备旧卡回滚。
8. 保持全部核心信息在目标设备上可访问。Dial 可分页和旋转选择，但不能省略敌方公开单位、两排分数、PASS 状态、剩余手牌数和技能原文。PaperMono 不靠连续动画才能理解行动。
9. 联机逐字遵守协议、canonical JSON、版本协商、action 幂等、revision、私有手牌过滤和断线恢复。两端使用相同规则与内容 hash。未知效果/未知存档主版本必须明确阻止不安全继续；不允许忽略后照常对战或覆盖存档。
10. 禁止使用一个假的“统一 NFC API”宣称所有设备支持。区分内置 NFC、Grove、USB PC/SC、键盘式 UID 读头、Web NFC 与本地桥；明确可读、可写、容量和卡型。目标平台缺能力时给出实际桥接路径与 UI 状态。
11. 执行 docs/07 中适用于目标的验收。至少跑 reference tests、目标语言移植向量、两独立进程的同局对战、重复/丢包/重连、保存失败恢复。硬件不可用时报告“未实测”，提供精确复测步骤，不伪造通过。
12. 交付完整源码、依赖锁定、构建/刷机/运行命令、目标配置、协议互操作说明、测试结果、已知限制、真实硬件能力和少量有证据的待补材料。任何 Mock 能力必须可识别并可替换。不要只给效果图，不要把未实现按钮伪装成完成。
